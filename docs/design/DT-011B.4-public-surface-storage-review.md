# DT-011B.4 — Public Surface, Uploads & Storage Security Review

- **Status:** Proposed
- **Sprint:** 11B.4
- **Depende de:** `DT-011B.1` (plano/rubric de severidade reaproveitados), `DT-011B.3` (autorização/multi-tenancy — três achados daquela auditoria pertencem exatamente a este escopo e são reafirmados aqui, não reinvestigados do zero)
- **Escopo:** auditoria apenas — nenhum código, migration, teste, commit ou push nesta tarefa; nenhuma vulnerabilidade foi corrigida

---

## 1. Objetivo

Executar a terceira subsprint do plano de `DT-011B.1`: auditoria completa da superfície pública da aplicação e de todo o pipeline de upload, armazenamento, acesso e distribuição de arquivos (logo, galeria, PDF de orçamento, link de partilha) do Contractor Platform. Toda conclusão é baseada em leitura direta do código listado no escopo obrigatório; nenhum achado foi assumido sem evidência de arquivo/classe/método.

## 2. Escopo

Backend: `StorageService`/`LocalStorageService`, `ImageUploadPolicy`, `GalleryImageService`, `CompanyService.uploadLogo`/`deleteLogo`, `GalleryService`, `EstimatePdfRenderer`, `EstimatePdfDocumentFactory`, `EstimatePdfService`, `EstimateShareService`/`EstimateShareController`/`PublicEstimateShareController`, `PublicSiteController`, `PublicTenantController`, `PublicGalleryController`, `PublicServiceController`, `StorageWebConfig` (resource handler de `/uploads/**`), `SecurityConfig`, `StorageProperties`.

Frontend: upload de galeria (`UploadArea.tsx`, `ImagePreview.tsx`), upload de branding/logo (`BrandingPage.tsx`), resolução de asset (`resolveAdminAssetUrl` em `assets.ts`, `resolvePublicAssetUrl` em `public-site.ts`), `SiteHeader.tsx`, página/hook de partilha pública (`PublicEstimateSharePage.tsx`, `estimate-share-api.ts`), `next.config.ts` (necessário para avaliar `images.remotePatterns`, diretamente relevante à distribuição pública de assets).

## 3. Arquivos analisados

Todos os arquivos do escopo obrigatório foram lidos integralmente, mais `frontend/next.config.ts` (não listado explicitamente, mas é onde `images.remotePatterns` — a configuração que rege como o Next.js processa/serve URLs de imagem externas — está definida; necessário para avaliar o item "Public URLs"/"Image Processing" do escopo) e `frontend/src/features/public-site/mappers/branding.ts` (validação de cor usada nos assets de branding, relevante a "Filename Injection"/sanitização de valores vindos do backend antes de uso no DOM).

## 4. Arquitetura atual de uploads

Um único backend de armazenamento (`LocalStorageService implements StorageService`) usado por três fluxos de upload (logo, galeria antes/depois) e um consumidor de leitura (PDF de orçamento, que lê o logo já armazenado). Todos os três fluxos de upload passam por `ImageUploadPolicy.validate(file)` antes de qualquer escrita em disco — validação em quatro camadas: tipo vazio/tamanho (5 MB), `Content-Type` numa allowlist de 3 valores (`image/png`, `image/jpeg`, `image/webp`), extensão do nome original compatível com o `Content-Type` declarado, e assinatura binária (magic bytes) compatível com o formato declarado. Nenhuma etapa de reprocessamento/recodificação de imagem existe em nenhum ponto do pipeline — o arquivo validado é gravado exatamente como recebido.

Nome de arquivo em disco é sempre gerado pelo servidor (`UUID.randomUUID() + extensão`) — o nome original enviado pelo cliente nunca é usado além de extrair sua extensão (últimos caracteres após o último `.`). URL pública retornada é sempre `/uploads/{folder}/{uuid}.{ext}`, onde `{folder}` é montado internamente a partir do `companyId` do principal autenticado (`"company/" + companyId + "/logo"` ou `"/gallery"`), nunca a partir de entrada do cliente.

## 5. Fluxo Logo

`POST /company/logo` (`CompanyController.uploadLogo`, `hasRole('OWNER')`) → `CompanyService.uploadLogo(companyId, file)`: valida (`ImageUploadPolicy`), busca a `Branding` existente da empresa (`brandingRepository.findByCompanyId(companyId)`, nunca por um id vindo do cliente), apaga o logo anterior se existir (`storageService.delete(branding.getLogoUrl())`), armazena o novo sob `company/{companyId}/logo`, persiste a nova URL. `DELETE /company/logo` (`deleteLogo`) segue o mesmo padrão de busca por `companyId`, sem aceitar nenhum identificador do cliente.

## 6. Fluxo Gallery

`POST /gallery/{id}/before-image` e `/after-image` (`GalleryController`, `hasRole('OWNER')`) → `GalleryService.uploadBeforeImage`/`uploadAfterImage(companyId, id, file)`: resolve o item por `findByIdAndCompanyId(id, companyId)` (auditado em `DT-011B.3`, confirmado sem exceção), apaga a imagem anterior daquele slot se existir, delega a validação e o armazenamento a `GalleryImageService.storeImage(companyId, file)` (que só chama `ImageUploadPolicy.validate` + `StorageService.store`, nunca toca o repositório — separação de responsabilidade limpa, documentada no próprio javadoc da classe). Exclusão de item (`GalleryService.deleteItem`) apaga corretamente as duas imagens (antes/depois) antes de remover o registro do banco.

## 7. Fluxo PDF

`EstimatePdfService.generatePdf(companyId, estimateId)`: resolve o orçamento por `findDetailByIdAndCompanyId` (escopo por empresa confirmado), carrega `Branding` da mesma empresa, resolve os bytes do logo via `storageService.load(branding.getLogoUrl())` — devolve `byte[]`, nunca uma `String`/URL. `EstimatePdfRenderer.renderHeader` consome esse valor com `Image.getInstance(seller.logo())`, onde `seller.logo()` é tipado como `byte[]` (`EstimatePdfDocument.SellerInfo`). Essa distinção é a que importa para SSRF: a sobrecarga `Image.getInstance(byte[])` do OpenPDF nunca faz I/O de rede — só decodifica bytes já em memória. Se em algum ponto futuro esse valor fosse trocado por uma `String` (URL), a sobrecarga correspondente do OpenPDF *buscaria* a URL remotamente, o que seria uma classe de vulnerabilidade real (SSRF via geração de PDF) — não é o caso hoje, mas vale registrar como invariante a preservar (ver `SEC-STORAGE-04` em Melhorias arquiteturais).

Nome do arquivo de download é sanitizado antes de entrar no header `Content-Disposition`: `EstimatePdfService.buildFilename` aplica `estimateNumber.replaceAll("[^A-Za-z0-9-_]", "")` — fecha a classe de injeção de cabeçalho HTTP (CRLF/aspas) via um número de orçamento malicioso, mesmo que essa string já seja gerada internamente (`EstimateNumberGenerator`, fora do escopo desta auditoria) e não literalmente controlável pelo cliente hoje.

## 8. Fluxo Estimate Share

`EstimateShareService` (auditado em profundidade em `DT-011B.3 §10`): criação/status/revogação são `OWNER`-only e escopadas por `companyId`; resolução pública (`getPublicView`/`getPublicPdf`) é por hash SHA-256 do token (160 bits de entropia, `SecureTokenGenerator`), nunca por id sequencial. `getPublicPdf` reaproveita literalmente `EstimatePdfService.generatePdf(share.getCompanyId(), share.getEstimateId())` — mesmo caminho de código, mesmo escopo por empresa, do fluxo autenticado. Reafirmado aqui (não reinvestigado): nem `getPublicView` nem `getPublicPdf` verificam `Company.status` — ver `SEC-TENANT-02` (`DT-011B.3`), dentro do escopo desta auditoria também.

No frontend, `frontend/src/app/share/[token]/page.tsx` define `robots: { index: false, follow: false }` — impede que o link (que contém um token secreto na própria URL, ao contrário do link de reset de senha que usa fragmento) seja indexado/cacheado por motores de busca, uma mitigação real e correta contra vazamento de token via crawling.

## 9. Fluxo Public Landing

`GET /public/sites/{slug}` (`PublicSiteController` → `CompanyService.getPublicSite`) é o único dos três endpoints "por slug" que verifica `CompanyStatus.ACTIVE` antes de responder. `GET /public/sites/{slug}/gallery` (`PublicGalleryController`) e `GET /public/sites/{slug}/services` (`PublicServiceController`) não replicam essa checagem — reafirmado aqui como `SEC-TENANT-01` (`DT-011B.3`), dentro do escopo desta auditoria também (ambos os controllers estavam explicitamente listados no escopo obrigatório desta tarefa).

No frontend, `PublicSiteIntegrationShell` dispara as três chamadas (`usePublicSite`, `usePublicServices`, `usePublicGallery`) como requisições HTTP independentes — nenhuma delas depende do resultado das outras para decidir se deve ou não renderizar, o que é exatamente por que a checagem de status ausente em duas delas é observável de fora (a página principal falha graciosamente com 404, mas as chamadas de galeria/serviços, se feitas diretamente, não).

## 10. Fluxo /uploads/**

`StorageWebConfig.addResourceHandlers` registra `/uploads/**` como um `ResourceHandlerRegistry` padrão do Spring MVC, apontando para `Path.of(properties.getBasePath()).toAbsolutePath().normalize()`, com `CacheControl.maxAge(30 dias).cachePublic()`. `SecurityConfig` inclui `/uploads/**` na lista `permitAll` — sem nenhuma filtragem de autenticação/autorização, por desenho (logo e imagens de galeria são ativos de marketing público enquanto a empresa está ativa).

Duas camadas independentes de proteção contra path traversal foram verificadas nesta auditoria:
1. **Escrita/leitura interna** (`LocalStorageService.store`/`delete`/`load`) — `normalize()` + `startsWith(baseDir)` explícito em cada método; nenhum caminho controlado pelo usuário chega a `delete`/`load` em nenhum módulo (sempre um valor já persistido pelo próprio `store`).
2. **Servir via HTTP** (`ResourceHttpRequestHandler`, mecanismo interno do Spring por trás de `addResourceHandler`) — resolve e valida que o caminho requisitado permanece dentro do `storageLocation` configurado, independentemente da camada 1.

Nenhuma das duas apresentou falha nesta auditoria — path traversal está fechado nos dois pontos onde poderia ocorrer.

O gap identificado nesta seção não é de acesso indevido a um arquivo de OUTRA empresa (isso está corretamente isolado por convenção de path — `company/{companyId}/...`), mas de **persistência indefinida**: nada nesse fluxo tem qualquer noção de `Company.status` — arquivos de uma empresa desativada continuam servíveis para sempre por quem já conhece a URL. Reafirmado aqui como `SEC-TENANT-03` (`DT-011B.3`).

## 12. Inventário dos controles existentes

| Controle | Onde | Cobertura verificada |
|---|---|---|
| Allowlist de `Content-Type` (3 valores) | `ImageUploadPolicy.ALLOWED_CONTENT_TYPES` | PNG/JPEG/WebP apenas — SVG explicitamente fora, fechando XSS via SVG com `<script>` embutido |
| Extensão compatível com `Content-Type` | `ImageUploadPolicy.EXTENSIONS_BY_CONTENT_TYPE` | Fecha dupla-extensão como vetor de bypass — mesmo `foo.php.png`, a extensão usada é sempre a última, e ainda precisa bater com a assinatura binária real |
| Assinatura binária (magic bytes) | `ImageUploadPolicy.hasExpectedSignature` | PNG/JPEG/WebP verificados byte a byte — um arquivo executável renomeado para `.png` é rejeitado mesmo com `Content-Type`/extensão forjados |
| Nome de arquivo sempre gerado pelo servidor | `LocalStorageService.store` (`UUID.randomUUID() + extension(...)`) | Nome original do cliente nunca chega ao disco além da extensão |
| Path traversal (escrita/leitura interna) | `LocalStorageService.store`/`delete`/`load` | `normalize()` + `startsWith(baseDir)` em cada método |
| Path traversal (servir via HTTP) | `ResourceHttpRequestHandler` (Spring, via `StorageWebConfig`) | Camada independente, redundante com a anterior |
| Sanitização de `Content-Disposition` | `EstimatePdfService.buildFilename` | Regex de allowlist de caracteres antes de montar o header |
| Imagem do logo no PDF via bytes, nunca URL | `EstimatePdfDocument.SellerInfo.logo (byte[])`, `EstimatePdfRenderer.renderHeader` | Fecha SSRF via geração de PDF |
| Token de partilha opaco, não sequencial | `EstimateShareService` (`SecureTokenGenerator`, 160 bits) | Confirmado em `DT-011B.3`; reafirmado aqui por estar em escopo |
| `robots: noindex` na página de partilha | `frontend/src/app/share/[token]/page.tsx` | Evita vazamento de token via indexação/cache de motor de busca |
| Validação de cor (`isSafeHexColor`) antes de uso em estilo inline | `frontend/src/features/public-site/mappers/branding.ts` | Fecha injeção via valor de cor malformado vindo da API |
| CSP, X-Frame-Options, Referrer-Policy, Permissions-Policy | `next.config.ts` (`headers()`) | Presentes; `script-src` inclui `'unsafe-inline' 'unsafe-eval'` — ver `SEC-STORAGE-03` |

## 13. Achados

### Vulnerabilidades

#### SEC-STORAGE-01 — SSRF via Next.js Image Optimization (`remotePatterns` com hostname wildcard)

- **Severidade:** High
- **Categoria OWASP/CWE:** CWE-918 (Server-Side Request Forgery) / OWASP A10:2021 — Server-Side Request Forgery
- **Evidência:** `frontend/next.config.ts`, bloco `images.remotePatterns`:
  ```
  remotePatterns: [
    { protocol: "https", hostname: "**" },
    { protocol: "http", hostname: "**" },
  ]
  ```
- **Descrição:** O endpoint embutido do Next.js para otimização de imagens (`/_next/image?url=<url>&w=...&q=...`) é servido publicamente pelo processo do frontend e, quando `remotePatterns` permite qualquer hostname (como aqui, para `http` e `https`), aceita **qualquer URL externa** como parâmetro `url` e a busca **a partir do servidor Next.js**, não do navegador do visitante. Isso transforma um recurso de UI (otimização de imagem) num proxy HTTP genérico controlado por um parâmetro de URL público.
- **Impacto:** Um atacante não autenticado pode usar esse endpoint como uma primitiva de SSRF contra a rede interna onde o container do frontend roda — sondar portas/serviços internos (`backend:8080`, `postgres:5432`, outros containers do mesmo `docker-compose`), ou, dependendo do provedor de infraestrutura de produção, atingir endpoints de metadata de nuvem (ex.: `169.254.169.254` em AWS/GCP/Azure) que normalmente não são alcançáveis publicamente. A resposta ao atacante fica limitada pelo comportamento do otimizador de imagem do Next.js (ele espera uma resposta de imagem válida para retornar algo útil ao chamador), mas mesmo um oráculo de "erro vs. sucesso"/diferença de tempo de resposta já é suficiente para port-scanning e reconhecimento de rede interna — a classe de dano clássica de SSRF.
- **Cenário de exploração:** `GET https://<domínio>/_next/image?url=http://backend:8080/actuator/health&w=256&q=75` (ou qualquer outro host/porta interna) — requisição pública, sem autenticação, sem qualquer relação com um tenant específico.
- **Recomendação:** Restringir `remotePatterns` à(s) origem(ns) que de fato precisam ser otimizadas — hoje, isso é o próprio backend servindo `/uploads/**` (mesma origem via Caddy, ou o hostname real de produção) — nunca um wildcard `"**"`. Se nenhuma imagem de fora do próprio domínio precisa passar pelo otimizador, considerar remover `remotePatterns` completamente (o Next.js já permite imagens same-origin sem essa configuração).
- **Nota de implementação (Sprint 11B.6B):** **Corrigido.** `remotePatterns` agora contém uma única entrada, derivada dinamicamente de `NEXT_PUBLIC_API_BASE_URL` (`protocol`/`hostname`/`port` do próprio backend configurado, `pathname: "/uploads/**"`) — nenhum wildcard `"**"` em hostname, para nenhum protocolo. Teste dedicado (`next.config.test.ts`) garante que um hostname `"**"` nunca é retornado e que o padrão fica restrito à origem configurada. Cobertura: `next.config.test.ts` (frontend).

#### SEC-STORAGE-02 — Metadados EXIF não são removidos de imagens enviadas

- **Severidade:** Low
- **Categoria OWASP/CWE:** CWE-200 (Exposure of Sensitive Information) — recomendação explícita do OWASP File Upload Cheat Sheet ("Strip metadata... from images")
- **Evidência:** `ImageUploadPolicy.validate` (checa tamanho/tipo/extensão/assinatura, nunca reprocessa o conteúdo) e `LocalStorageService.store` (`Files.copy(file.getInputStream(), targetDir.resolve(filename), ...)` — cópia binária direta, sem decodificação/recodificação).
- **Descrição:** Nenhuma etapa do pipeline de upload (logo ou galeria) remove metadados EXIF. Fotos de "antes/depois" de obra tiradas por telemóvel frequentemente incluem coordenadas GPS, data/hora exata e, por vezes, modelo do aparelho nos metadados EXIF — que são preservados integralmente e servidos publicamente (sem autenticação) assim que a imagem é publicada na galeria.
- **Impacto:** Exposição involuntária da localização exata (endereço residencial do cliente final, no caso de fotos de obra) a qualquer visitante da landing pública que inspecione os metadados do arquivo de imagem — um vazamento de privacidade para o cliente final do contratante (OWNER), não para o próprio Contractor Platform.
- **Cenário de exploração:** Baixar qualquer imagem de `/uploads/company/{id}/gallery/{uuid}.jpg` e inspecionar seus metadados EXIF com uma ferramenta comum (`exiftool`, ou o próprio Explorador de Arquivos/Finder) — nenhuma autenticação necessária, já que a imagem já é pública por desenho.
- **Recomendação:** Adicionar uma etapa de stripping de metadados (ex.: reprocessar a imagem com uma biblioteca que descarte EXIF ao salvar) ao pipeline de upload, antes de `LocalStorageService.store`. Proporcional ao MVP: pode ser adiado, mas deve ser uma decisão consciente, não uma omissão.

### Melhorias arquiteturais

#### SEC-STORAGE-03 — CSP do frontend permite `'unsafe-inline'` e `'unsafe-eval'` em `script-src`

- **Classificação:** Melhoria arquitetural (não uma vulnerabilidade isolada de upload/storage — observada no mesmo arquivo do achado `SEC-STORAGE-01`)
- **Evidência:** `frontend/next.config.ts`, `headers()` → `"script-src 'self' 'unsafe-inline' 'unsafe-eval'"`.
- **Descrição:** Com `'unsafe-inline'`/`'unsafe-eval'`, a CSP deixa de oferecer proteção efetiva contra XSS (o principal benefício de uma CSP restritiva) — qualquer script injetado inline, ou `eval()`/`Function()` de uma string, ainda executa. Isso não é, por si só, uma vulnerabilidade de upload/armazenamento, mas reduz a defesa em profundidade disponível caso um XSS seja introduzido em qualquer outro ponto da aplicação (incluindo, hipoteticamente, um nome de arquivo ou legenda de galeria mal escapado no futuro).
- **Recomendação:** Fora de escopo corrigir nesta auditoria (exigiria uma estratégia de nonce/hash compatível com o modelo de renderização do Next.js, um esforço maior que uma correção pontual) — registrar como item de hardening a avaliar numa subsprint de segurança de frontend dedicada.

#### SEC-STORAGE-04 — Nenhuma salvaguarda estrutural impede que `EstimatePdfDocument.SellerInfo.logo` volte a ser uma URL no futuro

- **Classificação:** Melhoria arquitetural (preventiva — não há vulnerabilidade hoje)
- **Evidência:** `EstimatePdfDocument.SellerInfo.logo` é tipado como `byte[]` (correto, ver §7); nada além da disciplina de tipo impede uma futura refatoração de trocá-lo por `String` (URL) e usar a sobrecarga `Image.getInstance(String)` do OpenPDF, que faz I/O de rede.
- **Descrição:** Puramente preventivo — documentar explicitamente por que `logo` deve continuar sendo `byte[]`, para que uma futura mudança não reintroduza SSRF via geração de PDF sem que o autor perceba a implicação de segurança.
- **Recomendação:** Um comentário no próprio record (`EstimatePdfDocument.SellerInfo`) explicando essa decisão seria suficiente — não requer mudança de comportamento, só de documentação.

#### SEC-STORAGE-05 — Armazenamento de arquivo e persistência no banco não são transacionais entre si

- **Classificação:** Melhoria arquitetural
- **Evidência:** `CompanyService.uploadLogo`, `GalleryService.uploadBeforeImage`/`uploadAfterImage` — `storageService.store(...)` (I/O de disco, sem rollback possível) sempre acontece antes de `repository.save(...)` (transação Spring/JPA, com rollback possível). Se `save()` falhar por qualquer motivo após `store()` já ter escrito o arquivo, o arquivo fica órfão em disco, sem nenhum registro no banco apontando para ele.
- **Descrição:** Não é uma falha de controle de acesso — o arquivo órfão continua isolado por `companyId` no path, então não há exposição cross-tenant. É um problema de consistência/higiene de armazenamento (item "Orphan files"/"Storage consistency" do escopo desta auditoria).
- **Recomendação:** Sem ação obrigatória — mesma classe de problema em qualquer sistema que combine armazenamento de arquivo local com uma transação de banco separada. Se vier a importar, um job de limpeza periódica (comparando arquivos em disco contra URLs referenciadas no banco) resolveria sem mudar o fluxo de escrita.

## 14. Pontos fortes

- **Validação de upload em quatro camadas, sem nenhuma exceção encontrada** — tamanho, `Content-Type` allowlist, extensão compatível, assinatura binária — aplicada identicamente a logo e às duas imagens de galeria.
- **SVG explicitamente bloqueado** — fecha a classe mais comum de XSS via upload de imagem (SVG com `<script>`/`onload` embutido).
- **Dupla extensão neutralizada por desenho** — o nome final em disco é sempre `UUID + extensão-verificada-por-magic-bytes`, nunca o nome original do cliente.
- **Path traversal fechado em duas camadas independentes** — escrita/leitura interna (`LocalStorageService`) e o resource handler HTTP do próprio Spring — nenhuma das duas depende da outra para estar correta.
- **Logo do PDF consumido como `byte[]`, nunca como URL** — fecha SSRF via geração de PDF antes que pudesse existir.
- **Sanitização de `Content-Disposition`** — regex de allowlist de caracteres no nome do arquivo de download.
- **Reuso de código entre fluxo autenticado e público** — `EstimatePdfService.generatePdf` é literalmente a mesma chamada nos dois casos, herdando o mesmo escopo por `companyId` sem duplicar lógica nem introduzir uma segunda superfície de erro.
- **Token de partilha opaco de 160 bits + página de partilha marcada `noindex`** — fecha tanto força bruta quanto vazamento via indexação de motor de busca.
- **Validação de cor (`isSafeHexColor`) antes de uso em estilo inline** — previne injeção via um valor de branding malformado.
- **Cache público de 30 dias em `/uploads/**` é seguro dado o desenho de URL imutável** — cada upload gera um nome novo (UUID), então não há risco de servir conteúdo desatualizado/incorreto sob uma URL já em cache.

## 15. Riscos aceitos

Nenhum achado novo desta auditoria (`SEC-STORAGE-01`, `02`) corresponde a um risco já documentado/aceito anteriormente — ambos são achados genuínos desta rodada. Os três achados reafirmados de `DT-011B.3` seguem o mesmo status daquele documento: identificados, não corrigidos, sem decisão formal de aceitação de risco registrada — permanecem como pendências abertas, não como riscos aceitos.

## 16. Recomendações

Ordenadas por severidade:

1. **`SEC-STORAGE-01`** — Restringir `images.remotePatterns` em `next.config.ts` a origens conhecidas (nunca `hostname: "**"`); avaliar se a otimização de imagem externa é sequer necessária dado que todos os assets hoje são same-origin (`/uploads/**` via Caddy).
2. **`SEC-TENANT-01`/`SEC-TENANT-02`** (reafirmados) — Ver recomendação já registrada em `DT-011B.3 §16`.
3. **`SEC-STORAGE-02`** — Avaliar stripping de EXIF no pipeline de upload, como decisão consciente de produto/prazo, não como omissão.
4. **`SEC-TENANT-03`** (reafirmado) — Ver `DT-011B.3 §16`.
5. **`SEC-STORAGE-03`/`04`/`05`** — Sem ação obrigatória; registradas como melhorias arquiteturais para backlog.

Nenhuma destas recomendações foi implementada nesta tarefa.

## 17. Conclusão

O pipeline de upload propriamente dito (validação, geração de nome, path traversal, autorização de escrita) é a área mais rigorosamente fechada de toda a base de código auditada nesta série — quatro camadas de validação de arquivo, duas camadas independentes de proteção contra path traversal, e nenhuma exceção ao padrão de nome gerado pelo servidor foram encontradas em nenhum dos três fluxos de upload (logo, galeria antes, galeria depois). O consumo do logo na geração de PDF é seguro por construção (bytes, nunca URL), fechando uma classe de SSRF que o próprio código já evita corretamente.

O achado mais significativo desta rodada (`SEC-STORAGE-01`) não está no backend nem no pipeline de upload em si, mas numa configuração do Next.js (`remotePatterns` com hostname wildcard) que expõe um proxy HTTP server-side não intencional — uma classe de risco (SSRF) diferente de tudo encontrado nas duas auditorias anteriores desta série, e que vale a pena corrigir antes da exposição pública real (Sprint 11C), já que o endpoint correspondente (`/_next/image`) é público por natureza e não depende de nenhuma pré-condição para ser alcançado.
