## 11. Auth / Admin bootstrap

- `PlatformAdminBootstrapRunner` — idempotente **por e-mail configurado**
  especificamente (não "qualquer SUPER_ADMIN existente") — nuance
  operacional real: trocar `PLATFORM_ADMIN_BOOTSTRAP_EMAIL` num redeploy cria
  um **segundo** admin, não promove/reseta o existente (RR-15, baixa
  severidade, documentar).
- Falha o boot se só uma das duas variáveis estiver setada — confirmado.
- Senha nunca logada — confirmado.
- Login, refresh, invite, forgot/reset password, logout — todos existem, sem
  dependência de seed/fixture de teste no código principal.
- **Rate limiting tem dois buracos reais**: `POST /auth/register` (endpoint
  público de self-serve) e `POST /auth/refresh` **não** têm regra em
  `AuthRateLimitFilter.resolveRule()` — só `login`/`forgot-password`/
  `reset-password`/`invite-accept`/`admin-password-reset` têm (RR-06/RR-07).
  O flag `AUTH_RATE_LIMIT_ENABLED` tem default seguro (`true`), então isso
  **não** é um caso de "desligado silenciosamente" — é uma lacuna de
  cobertura, não de configuração.

## 12. Frontend build-time config — item crítico

- `frontend/Dockerfile:27-33` — três `ARG`/`ENV` (`NEXT_PUBLIC_API_BASE_URL`,
  `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN`), só na stage de
  build, inlinados no bundle cliente.
- `publish-images.yml:123-132` **já tem** um gate que falha o job se
  `vars.NEXT_PUBLIC_API_BASE_URL`/`SITE_URL`/`PLATFORM_BASE_DOMAIN`
  (GitHub Actions Variables) estiverem vazias — mecanismo de
  `DT-011A.4` confirmado implementado e funcional.
- **O gate confirma "não-vazio", nunca "correto".** Como nenhum domínio real
  foi adquirido ainda (`DT-012.4 §18`, pendência em aberto), é razoável supor
  que os valores atuais dessas Variables no GitHub **não** são o domínio de
  produção real — não é possível confirmar o valor atual a partir do
  repositório (estado externo ao Git, `gh` CLI indisponível neste ambiente
  para checar diretamente).
- `next.config.ts` usa `NEXT_PUBLIC_API_BASE_URL` para montar o `connect-src`
  do CSP **em build-time**, e o valor é inlinado no bundle cliente — **não é
  relido em runtime pelo servidor Next.js**. Confirmado: mudar o domínio
  depois exige rebuild+republish completo via CI, **não** um simples
  `docker compose up -d`/recriação de container.
- **Resposta direta às perguntas do item 10 da tarefa:**
  - *Como a imagem saberá o domínio real?* — só se as GitHub Actions
    Variables forem atualizadas para o domínio real **e** o workflow for
    disparado de novo (`workflow_dispatch` ou novo push relevante) **antes**
    do primeiro `docker compose pull` na VPS.
  - *`publish-images.yml` recebe esses valores hoje?* — sim, mecanismo
    existe e é obrigatório (falha se vazio).
  - *A mesma imagem pode ser promovida entre ambientes?* — **não** — os
    valores são fixados por imagem, não por ambiente de deploy; "promover" a
    mesma imagem de staging→produção com domínios diferentes exigiria
    rebuild.
  - *Mudar domínio exige rebuild?* — **sim**, confirmado.
  - *O primeiro deploy falhará porque a imagem foi construída com
    localhost/default?* — **classificado como blocker (RR-02)**: não é
    certeza absoluta (não consigo ler o valor atual das Variables), mas dado
    que nenhum domínio real existe ainda, a probabilidade de a última imagem
    publicada em `main` ter um valor de placeholder/incorreto é alta o
    suficiente para tratar como bloqueador a ser fechado *antes* do primeiro
    `docker compose pull`, não descoberto depois.

## 13. Health / Startup order

- Cadeia real (não a linear ingênua): `postgres(healthy)` → `backend(healthy)`;
  `frontend` **não depende de** `backend` (design deliberado, já documentado);
  `caddy` depende de **ambos** `frontend(healthy)` e `backend(healthy)`.
- Timings: backend `start_period 45s` + `retries 3 × interval 30s` ≈ **135s**
  de janela total antes de `unhealthy`. Postgres: `start_period 10s` + `5×10s`
  ≈ 60s, folgado para `pg_isready` num cluster recém-inicializado.
- **Risco real, não confirmado**: 135s pode ser justo para cold-start de JVM
  (Java 25) + Flyway (14 migrations) rodando sob `cpus: "1.0"` (limite de
  cgroup) numa VPS de vCPU compartilhado (CPX32), especialmente se houver
  *CPU steal* de vizinhos — cenário que nunca foi testado contra hardware
  real (só validado em Sprints 12.2/12.3 contra a máquina de desenvolvimento).
- **Consequência se o backend nunca ficar `healthy`**: `caddy` (que depende
  de `service_healthy` para os dois upstreams) **nunca chega a iniciar** — não
  é um estado degradado, é ausência total de qualquer processo escutando
  80/443. Sem sintoma via HTTP; só visível via `docker compose ps`/`logs` por
  SSH. Já parcialmente coberto em `runbook.md §23` linha 2 (troubleshooting),
  mas a implicação exata ("Caddy não sobe, ponto") não estava explícita.
