## 2. Contexto

As Sprints 11A.1–11A.4 estabeleceram containers de produção, configuração `prod`, Caddy como único ponto de entrada e um pipeline de imagens versionadas por SHA — mas **nenhum dos dados que o sistema efetivamente persiste tem qualquer proteção contra perda**. `postgres_data` e `backend_storage` são volumes Docker locais na futura VPS única; se essa VPS falhar, for corrompida por um deploy ruim, ou sofrer uma migration destrutiva, não existe hoje nenhum caminho de recuperação além de "esperar que não aconteça". O rollback de imagem (11A.4) resolve reverter *código*; não resolve reverter *dados* — essa lacuna é o objeto desta sprint.

### 5.3 `backend_storage` — o que de fato existe ali

`backend/src/main/java/.../StorageProperties.java`: `app.storage.base-path`, default `./storage`, sobrescrito para `/app/storage` via `STORAGE_PATH` no `Dockerfile`.

`LocalStorageService.store(folder, file)` grava em `<base>/<folder>/<UUID>.<ext>`. Os dois únicos chamadores confirmam a estrutura real em disco:

```java
// CompanyService.java
String folder = "company/" + companyId + "/logo";
// GalleryImageService.java
return storageService.store("company/" + companyId + "/gallery", file);
```

**Confirmado: existe informação de tenant no filesystem.** A árvore é `company/<companyId>/{logo,gallery}/<uuid>.<ext>` — `companyId` é a mesma chave primária da tabela `companies` no PostgreSQL. Isso cria um **acoplamento de consistência entre os dois backups** (§12): um restore de Postgres e um restore de `backend_storage` tirados em momentos diferentes podem produzir pastas órfãs (`companyId` que já não existe no banco restaurado) ou referências quebradas (banco menciona uma logo cujo arquivo não foi capturado ainda) — não é um bug, é uma implicação a documentar e mitigar operacionalmente (backups do banco e dos arquivos rodando na mesma janela, mesmo não sendo transacionalmente atômicos entre si).

**Não existe nenhum outro dado persistente fora de `postgres_data`, `backend_storage`, `caddy_data`/`caddy_config`.** Confirmado: `EstimatePdfService` gera PDFs inteiramente em memória a cada requisição (já documentado desde a 11A.1, `infra/README.md`) — não há um terceiro diretório de "arquivos gerados".

### 5.4 Atomicidade de escrita — não é atômica (confirmado no código, não presumido)

```java
Files.copy(file.getInputStream(), targetDir.resolve(filename), StandardCopyOption.REPLACE_EXISTING);
```

Isso grava **diretamente no nome de arquivo final**, sem escrever primeiro num arquivo temporário e mover atomicamente (`Files.move` com `ATOMIC_MOVE`). Um backup que capture o arquivo exatamente durante esse `copy` pode ler um arquivo truncado/parcial. O risco prático é estreito, não amplo: cada upload recebe um **nome de arquivo novo (`UUID.randomUUID()`)** — nunca sobrescreve um arquivo já existente e completo; e o registro no banco (`branding.setLogoUrl(...)`, etc.) só é gravado **depois** que `store()` retorna com sucesso. Ou seja: o único arquivo que pode ser capturado incompleto é um upload em voo naquele instante exato, cujo registro no banco também ainda não existe — na pior hipótese, o próximo backup diário captura a versão completa e o registro correspondente já existe. Documentado como risco aceito em §12, não como problema resolvido.

## 8. Backup do PostgreSQL

### 8.1 Comparação de estratégias

| Opção | Consistência | Portabilidade | Restore | Avaliação |
|---|---|---|---|---|
| **A — Snapshot bruto do volume Docker** | Só é confiável se o Postgres estiver parado, ou com snapshot de filesystem (LVM/ZFS/btrfs) coordenado — nenhum dos dois existe hoje | Baixa — atrelado à versão exata do Postgres/formato interno do datadir | Substituir o volume inteiro; sem restore seletivo | Rejeitada — exigiria parar o banco (downtime) ou infraestrutura de snapshot que a VPS ainda nem existe para ter |
| **B — `pg_dump` lógico (formato custom)** | **Total** — snapshot MVCC consistente no início do dump, não bloqueia escritores | Alta — independe do datadir físico, restaura em qualquer instalação Postgres compatível | `pg_restore` seletivo (schema, tabela, dados), paralelizável | **Escolhida** |
| **C — `pg_dumpall`** | Total, mesma base do `pg_dump` | Só texto plano (sem `--format=custom`), sem restore seletivo/paralelo | Restore via `psql`, tudo ou nada | Rejeitada como escolha principal — este projeto tem um único banco/role, não precisa do "dump de todos os bancos + roles" que justificaria `pg_dumpall`; ver nota abaixo |
| **D — Backup físico/contínuo (pgBackRest, WAL-G, streaming+PITR)** | Total, com granularidade de PITR | Alta, mas com complexidade operacional real (arquivamento de WAL, slots de replicação) | Restore a qualquer segundo | Rejeitada por desproporção — nenhuma exigência de PITR/HA nesta fase (explicitamente fora de escopo); revisitar só se o volume de escrita ou o número de clientes justificar |

**Confirmo a preferência inicial do usuário: `pg_dump --format=custom`.** É a opção mais simples que ainda garante um restore confiável, sem downtime no backup, portátil entre versões menores do Postgres, e compatível com o tamanho atual do banco (10 migrations, um cliente).

Nota sobre roles/globais: como há apenas um `POSTGRES_USER` (`platform`), criado pela própria imagem oficial do Postgres a partir de `POSTGRES_USER`/`POSTGRES_PASSWORD` (recriável a partir de `production.env` num restore completo), não há necessidade de `pg_dumpall --globals-only` agora. Registrado como algo a reconsiderar somente se múltiplas roles/bancos existirem no futuro.

### 8.2 Comando conceitual

Executado **dentro do container `postgres`** (via `docker exec`), reaproveitando o binário `pg_dump` já embutido na imagem `postgres:17-alpine` — garante que a versão do `pg_dump` é sempre idêntica à do servidor, sem instalar nada a mais no host nem versionar dependências separadas.

```bash
# host, dentro do futuro backup-postgres.sh (conceitual — não criado nesta tarefa)
TS="$(date -u +%Y%m%dT%H%M%SZ)"
DUMP_FILE="platform_db_${TS}.dump"

docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" postgres \
  pg_dump \
    --format=custom \
    --compress=6 \
    --username="$POSTGRES_USER" \
    --dbname="$POSTGRES_DB" \
    --file="/tmp/${DUMP_FILE}"

docker cp "postgres:/tmp/${DUMP_FILE}" "${STAGING_DIR}/${DUMP_FILE}"
docker exec postgres rm -f "/tmp/${DUMP_FILE}"
```

- **Usuário:** `$POSTGRES_USER` (já existe, mesmo usuário da aplicação — não é criado um usuário de backup dedicado no Postgres nesta sprint; suficiente para um único tenant de banco).
- **Banco:** `$POSTGRES_DB`.
- **Formato:** `--format=custom` (`.dump`) — permite `pg_restore` seletivo e paralelo.
- **Compressão:** nível moderado (6) do próprio `pg_dump` — ver §8.3 sobre por que não duplicar compressão com o Restic.
- **Nome do arquivo:** `platform_db_<UTC-timestamp-ISO-compacto>.dump` — ordenável lexicograficamente, sem ambiguidade de fuso.
- **Senha:** passada via `PGPASSWORD` como variável de ambiente do processo `docker exec` (não como argumento de `pg_dump`, nunca aparece em `ps`/histórico de shell) — e o próprio valor já é o `POSTGRES_PASSWORD` que o container `postgres` já conhece (nenhum segredo novo é criado ou distribuído só para isso).
- **Comportamento em erro:** o script (futuro) verifica o exit code de `pg_dump`; se não-zero, **não** prossegue para `restic backup` com um dump ruim, apaga qualquer arquivo parcial do staging e finaliza com erro visível (systemd/journalctl, §22/§23). Uma validação adicional simples e barata: `pg_restore --list "$DUMP_FILE" >/dev/null` — se o dump não é sequer legível como catálogo, o backup é considerado falho antes de subir para o Storage Box.

### 8.3 Compressão — evitar dupla compressão

`pg_dump --compress=6` já produz um arquivo compacto. O Restic (desde a v0.14+) também comprime por padrão. Comprimir dados já comprimidos desperdiça CPU sem ganho de espaço relevante — a escolha aqui é deixar o `pg_dump` comprimir (o artefato resultante é autossuficiente e portátil mesmo fora do Restic, útil para inspeção/restore manual) e aceitar que o Restic não vai conseguir comprimir muito mais em cima disso — não é um problema, é o comportamento esperado e documentado.

### 8.4 Nota de implementação (pós-11A.5, registrada na Sprint 11A.6)

O desenho acima (§8.2) descreve a entrega do arquivo staged ao Restic via bind
mount direto do diretório de staging (`-v "${STAGING_DIR}:/staging:ro"`). A
implementação real (`infra/backup/scripts/lib.sh#send_staging_to_restic`,
usada por `backup-postgres.sh`) faz algo ligeiramente diferente: copia o
staging para um **volume Docker nomeado efêmero** antes de chamar
`restic backup`, em vez de montar o diretório do host diretamente.

Isso não muda a decisão original (ainda é "staging local, validado, depois
entregue ao Restic") — é um refinamento descoberto durante a validação real:
em pelo menos um ambiente Docker testado, `restic backup` lendo um arquivo via
bind mount de host apresentou falhas de leitura (`input/output error`)
inconsistentes com o mesmo arquivo lido por outras ferramentas (`cat`/`cp`) no
mesmo mount. Usar um volume nomeado como intermediário elimina essa classe de
problema em qualquer host Docker, ao custo de uma cópia extra (via um
container utilitário efêmero, não o `docker cp` de/para o container do
Postgres que o pseudo-código acima usa). O comando conceitual em §8.2
permanece como registro da decisão original — o comportamento real e testado
está no script.

## 9. Backup do Filesystem (`backend_storage`)

### 9.1 Opções avaliadas

| Opção | Trade-off |
|---|---|
| Copiar o volume para staging antes do Restic | Dobra o uso de disco temporariamente; não resolve consistência (a cópia em si sofre o mesmo risco de capturar um arquivo em voo) — só adiciona uma etapa sem benefício real |
| Montar o volume **read-only** num container auxiliar e rodar Restic sobre esse mount | **Escolhida** — sem cópia extra, sem risco de o processo de backup escrever acidentalmente no storage da aplicação |
| Restic diretamente sobre o mount, sem read-only | Funciona, mas perde a garantia trivial de "o backup nunca pode corromper o storage" que o `:ro` dá de graça |
| Pausar escrita (parar/pausar o container `backend`) durante o backup | Introduz downtime de upload por causa de uma tarefa de manutenção — desproporcional dado que o risco real é estreito (§5.4) |
| Aceitar backup crash-consistent, sem pausar nada | **Escolhida, em conjunto com a opção acima** |

### 9.2 Decisão e trade-off explícito

Restic roda num **container utilitário efêmero** que monta `backend_storage:/data:ro` (somente leitura) e lê diretamente daquele mount — sem cópia de staging, sem pausar o container `backend`. Isso aceita explicitamente um backup **crash-consistent, não transacionalmente atômico**: um upload em andamento no exato instante do backup pode aparecer incompleto num snapshot específico. Dado que (confirmado em §5.4) cada arquivo tem nome único e o registro de banco correspondente só existe após a gravação terminar, o pior cenário prático é um arquivo órfão-incompleto num snapshot antigo que o snapshot seguinte já substitui pela versão completa — nunca uma corrupção de um arquivo que já estava em uso pela aplicação. Aceito como trade-off proporcional; não é o mesmo padrão de garantia que o `pg_dump` dá para o banco, e isso é documentado, não escondido.

## 11. Configuração/Segredos — `production.env`

**`production.env` contém segredos (`POSTGRES_PASSWORD`, `JWT_SECRET`) e não pode virar uma cópia solta, insegura, em texto plano.**

| Opção | Avaliação |
|---|---|
| Backup criptografado via Restic | **Escolhida** — Restic já criptografa client-side antes de qualquer byte sair da VPS (ver §14); incluir `production.env` **dentro do repositório Restic** é tão seguro quanto qualquer outro dado ali, e resolve exatamente o problema de "como reconstituo a config depois de perder a VPS inteira" sem introduzir uma segunda ferramenta |

| Arquivo de recuperação operacional (runbook) | **Complementar** — um documento (não criado nesta tarefa, listado em §29) que aponta *onde* cada segredo mora (ex.: "RESTIC_PASSWORD: cofre X, entrada Y"), sem conter nenhum valor real; seguro de versionar |

## 12. Restic

### 12.1 Onde roda

**Confirmo a preferência do usuário:** Restic roda no **host/VPS**, nunca dentro do container da aplicação (backend/frontend) — separa claramente responsabilidade operacional de responsabilidade de aplicação, e evita inchar a imagem de produção com uma ferramenta que ela não precisa em runtime. Concretamente, via a imagem oficial `restic/restic` (Docker Hub), invocada de forma efêmera (`docker run --rm`) pelos scripts host-side — não um binário instalado via `apt` no host. Justificativa: a VPS já vai depender de Docker para tudo (11A.1–11A.4); manter Restic também como container mantém um único mecanismo de execução/atualização, sem uma segunda cadeia de instalação/patch de pacotes do SO.

### 12.2 Configuração

| Item | Valor conceitual |
|---|---|
| `RESTIC_REPOSITORY` | `sftp:<storagebox-user>@<storagebox-host>:/contractor-platform` (placeholder — nenhum valor real definido nesta tarefa) |
| `RESTIC_PASSWORD_FILE` | Preferido sobre `RESTIC_PASSWORD` — arquivo host-only (`/etc/contractor-platform/restic-password`, `chmod 600`), nunca aparece em `docker inspect`/ambiente de processo listável |
| Cache | Diretório/volume persistente para `~/.cache/restic` — não deve ser apagado a cada execução (evita reprocessar metadados a cada backup); ele mesmo **não** entra no conteúdo do backup (§20) |
| Locks | `restic backup` já cria lock automaticamente; um processo interrompido (queda de rede, kill) pode deixar lock órfão — `restic unlock` é o procedimento de recuperação, e o plano de testes (§30) inclui simular exatamente esse cenário |
| Snapshots | Uma tag por tipo de conteúdo (`--tag postgres`, `--tag backend-storage`, `--tag config`) — permite `forget`/`restore` filtrarem por tipo sem misturar políticas de retenção |
| `forget`/`prune` | Executado logo após um backup bem-sucedido, aplicando a política de §15 |
| `check` | Execução periódica (não a cada backup — custo cresce com o tamanho do repositório) — ver §21 |
| `restore` | `restic restore <snapshot> --target <dir>` (snapshot inteiro) e `restic dump <snapshot> <path>` (arquivo único) — os dois fluxos são desenhados em §18/§19 |

## 13. Hetzner Storage Box — Protocolo

| Protocolo | Suporte nativo no Restic? | Avaliação |
|---|---|---|
| **SFTP/SSH** | Sim — backend `sftp` nativo, usa `ssh`/binário `sftp` do sistema | **Escolhido** — autenticação por chave SSH (sem senha trafegando), protocolo simples, amplamente documentado tanto por Restic quanto pela própria Hetzner para Storage Box |
| WebDAV | Não nativo — exigiria `rclone` como camada intermediária | Rejeitado — complexidade extra sem necessidade, quando SFTP já resolve nativamente |
| SMB | Não nativo | Rejeitado, mesma razão |
| Borg-specific | Restic não é Borg — não aplicável | N/A |

Nenhuma conta real, hostname ou usuário são definidos nesta tarefa — apenas o protocolo (SFTP) é decidido.

## 14. Criptografia

- Restic criptografa **todo o conteúdo** do repositório (dados + metadados + nomes de arquivo internos) client-side, antes de qualquer byte sair da VPS — o que chega à Storage Box já está cifrado; a Storage Box em si nunca vê texto plano.
- A senha do repositório (`RESTIC_PASSWORD`) é a única chave que decifra tudo — **não pode viver dentro do próprio repositório** (problema circular: não dá para recuperar a senha decifrando um repositório que só se abre com ela). Vive em: (1) arquivo host-only (`RESTIC_PASSWORD_FILE`, `chmod 600`) para uso operacional do dia a dia; (2) uma cópia num password manager, como último recurso se a VPS inteira (incluindo esse arquivo) for perdida.
- **Risco de perder `RESTIC_PASSWORD`:** é equivalente a perder o backup inteiro — sem a senha, o repositório é criptograficamente inacessível, não há "recuperação de senha" do lado do Restic. Por isso a cópia externa (password manager) não é opcional, é o que evita esse ponto único de falha.
- **Separação explícita:** a credencial de acesso à Storage Box (chave SSH/usuário) autoriza *chegar* ao repositório; `RESTIC_PASSWORD` autoriza *ler* o conteúdo depois de chegar lá. São dois segredos independentes, armazenados separadamente — perder um não compromete automaticamente o outro.
- Nenhuma dessas credenciais entra neste repositório Git, em nenhum momento.

## 15. Retenção

Proposta: **7 diários + 4 semanais + 6 mensais** (por tipo de conteúdo — banco e arquivos retidos com a mesma política).

Justificativa (não é apenas repetir o exemplo do pedido):

- **7 diários** cobrem o cenário mais comum — um problema notado dentro da mesma semana (erro de operação, exclusão acidental, migration ruim detectada rápido).
- **4 semanais** cobrem cerca de um mês de granularidade mais grossa, para problemas notados um pouco mais tarde sem precisar guardar todo dia individualmente.
- **6 mensais** cobrem meio ano — proporcional a "recém em produção com um cliente", não a uma exigência regulatória de retenção longa (nenhuma foi mencionada). Não há camada anual: não há hoje necessidade de retenção multi-ano, e adicionar uma agora seria antecipar um requisito que não existe.
- Custo da Storage Box é baixo o suficiente (armazenamento em disco, não por operação) para essa retenção não ser uma pressão financeira relevante — a decisão é guiada por utilidade operacional, não por economia de espaço.
- `restic forget --prune` com este esquema mantém o número de snapshots pequeno o bastante para que `check`/`prune` continuem rápidos no volume de dados atual (banco pequeno, poucos uploads).

Revisar quando o volume de dados ou o número de clientes crescer o suficiente para tornar essa política sensivelmente cara ou insuficiente.

## 16. Frequência

| Conteúdo | Frequência proposta | Premissa (RPO) |
|---|---|---|
| PostgreSQL | 1×/dia | Aceita perder até ~24h de escrita em caso de restore — não há SLA acordado com o cliente que exija menos |
| `backend_storage` | 1×/dia, na mesma janela | Uploads (logo/galeria) não são de alta frequência hoje; o mesmo RPO de 24h se aplica |

Diário (não 2×/dia nem horário) porque: (1) nenhum RPO mais agressivo foi acordado ou é assumido aqui; (2) o volume de escrita atual (um cliente, poucas operações por dia) não justifica a complexidade extra de janelas mais frequentes; (3) rodar banco e arquivos na mesma janela reduz a divergência de consistência entre os dois discutida em §5.3. Isso é declarado como premissa, não como promessa — se o cliente real precisar de um RPO menor, é uma decisão de negócio a revisar, não algo que este DT presume.

## 17. RPO e RTO

- **RPO ≤ 24h** — decorre diretamente da frequência diária (§16). Não é uma garantia contratual; é o que a frequência escolhida produz.
- **RTO ≤ algumas horas** (ordem de grandeza: 2–4h para uma recuperação total documentada em §19, presumindo operador humano seguindo o runbook) — cobre: provisionar/reinstalar Docker numa VPS nova, `docker compose pull` das imagens do GHCR, restaurar `production.env`, restaurar o dump do Postgres, restaurar `backend_storage`, subir o stack, smoke test.
- **Não há alta disponibilidade.** Um único VPS, um único Postgres, sem failover automático, sem standby quente. RTO depende de um humano executando passos manuais — isso é declarado explicitamente para não sugerir uma garantia que a arquitetura atual não entrega.

## 18. Restore de PostgreSQL — passo a passo

1. **Parar escrita:** parar (ou colocar em modo somente-leitura, se existir) o container `backend` — evita novas escritas contra um banco que está prestes a ser substituído.
2. **Criar banco limpo:** subir um Postgres vazio (container novo ou mesmo container com `postgres_data` recriado) com as mesmas `POSTGRES_DB`/`POSTGRES_USER`/`POSTGRES_PASSWORD` de `production.env` restaurado.
3. **Restaurar o dump:** `pg_restore --clean --if-exists --no-owner --dbname="$POSTGRES_DB" <arquivo.dump>` (obtido via `restic dump <snapshot> <path>` ou `restic restore` para um diretório temporário).
4. **Validar Flyway/schema:** subir o backend apontando para esse banco restaurado com `SPRING_PROFILES_ACTIVE=prod` — o Flyway roda `DbValidate`/`DbMigrate` no boot; se o dump já contém a tabela `flyway_schema_history` na versão esperada, o boot deve reportar "Schema is up to date", exatamente como observado nos testes de integração locais (`o.f.core.internal.command.DbValidate: Successfully validated N migrations`).
5. **Subir a aplicação:** `docker compose up -d` normalmente.
6. **Smoke test:** login com um usuário conhecido, listar clientes/orçamentos, confirmar que os dados restaurados aparecem — equivalente ao que já se faz manualmente nas validações funcionais das sprints anteriores (11A.3), mas focado em dado, não em roteamento.

---

## 19. Restore de `backend_storage` — passo a passo

1. **Localizar snapshot:** `restic snapshots --tag backend-storage` (mais recente, ou um específico por data).
2. **Restaurar para diretório temporário:** `restic restore <snapshot-id> --target /tmp/restore-storage` — nunca restaurar direto por cima do volume em produção sem antes inspecionar.
3. **Validar conteúdo:** conferir que a árvore `company/<id>/{logo,gallery}/...` está presente e os arquivos não estão vazios/truncados (ver risco de atomicidade, §5.4) — uma checagem simples de tamanho > 0 já cobre o caso mais provável.
4. **Substituir/montar o volume:** copiar o conteúdo validado para dentro do volume `backend_storage` real (ou, para um arquivo único apagado por engano, copiar só aquele arquivo — cenário A de §27).
5. **Permissões:** o `backend/Dockerfile` roda como usuário não-root fixo (`platform:1000`) — os arquivos restaurados precisam pertencer a esse UID/GID (`chown -R 1000:1000`) para o container conseguir servi-los/gravar novos.
6. **Subir a aplicação:** `docker compose up -d backend` (ou stack completa) e confirmar via `/uploads/**` (Caddy) que os arquivos restaurados são servidos corretamente.

2. Instalar Docker Engine + Docker Compose v2.

## 21. Integridade

- **`restic check`** — periódico (ex.: semanal), verifica a estrutura do repositório e (com `--read-data-subset=<n>`) uma amostra dos dados sem precisar baixar tudo a cada vez; uma verificação completa (`--read-data`) menos frequente (ex.: mensal), já que o custo cresce com o tamanho do repositório.
- **Verificação de snapshot:** conferir que cada execução de backup de fato produziu um snapshot novo (`restic snapshots --tag <tipo> --latest 1`) — um backup "que rodou sem erro" mas não gerou snapshot (ex.: lock preso, path vazio) é uma falha silenciosa a detectar.
- **Teste de restore periódico:** a única forma de saber que um backup é restaurável é restaurá-lo de fato, periodicamente (não só na primeira vez) — ver plano de testes (§30). **Backup sem teste de restore não é considerado suficiente nesta sprint.**

## 22. Automação Futura

**Confirmo a preferência do usuário: systemd timer**, não cron. Justificativa própria, não só aceitação: a VPS alvo é um host Linux com systemd como PID 1 (nenhuma dependência nova); `systemctl status`/`journalctl -u` dão visibilidade de último exit code, última execução e próxima execução agendada de graça — exatamente o que §23 (observabilidade) precisa sem introduzir Prometheus/Grafana. Cron exigiria redirecionar logs manualmente para algum lugar pesquisável; systemd timer já entrega isso.

**Não implementado nesta tarefa** — nomes de unidades (`backup-postgres.service`/`.timer`, etc.) ficam listados em §26 como previsão, não criados.

## 23. Segurança

| Aspecto | Decisão |
|---|---|
| Usuário que executa o backup | Usuário dedicado não-root na VPS (não `root`), membro do grupo `docker` — nota honesta: acesso ao socket Docker é efetivamente equivalente a root no host; é uma limitação conhecida de qualquer automação baseada em Docker, mitigada por não dar a esse usuário shell interativo/sudo além do necessário |
| `chmod` | `RESTIC_PASSWORD_FILE` e chave SSH da Storage Box: `600`, donos pelo usuário de backup; diretório de staging do dump: `700` |
| `umask` | `077` no contexto de execução dos scripts — qualquer arquivo criado incidentalmente nasce acessível só ao dono |
| Logs sem segredos | Nenhum script deve ecoar `PGPASSWORD`/`RESTIC_PASSWORD`/credenciais da Storage Box; saída de comandos redirecionada para `journalctl` normalmente, sem `set -x` em torno dos comandos que carregam segredo |
| Arquivos temporários / limpeza de dumps locais | O dump do Postgres em staging é **efêmero** — apagado logo após entrar com sucesso no Restic (e também apagado em caso de falha, via `trap`/lógica equivalente no script futuro) — nunca acumula no disco local da VPS |
| Acesso aos volumes | Containers utilitários montam `backend_storage` **read-only** durante o backup (§9) |

## 27. Cenários de Desastre

| Cenário | O backup resolve? | Como |
|---|---|---|
| **A — Arquivo individual apagado** | Sim | `restic restore --include <path>` ou `restic dump` do snapshot mais recente que ainda o contém; sem downtime, sem restore total |
| **B — Uploads inteiros perdidos** | Sim | Restore completo de `backend_storage` (§19); gap de RPO até ~24h |
| **C — Banco corrompido** | Sim | Restore completo de PostgreSQL (§18); gap de RPO até ~24h; downtime durante o restore |
| **D — VPS perdida inteira** | Sim | Disaster recovery total (§20); RTO de algumas horas, dependente de execução manual do runbook |
| **E — Deploy ruim sem perda de banco** | **Não é um problema de backup** | Resolvido por rollback de imagem GHCR (`APP_VERSION=<sha-anterior>`, Sprint 11A.4) — nenhuma restauração de dado é necessária |
| **F — Migration destrutiva** | Sim, **só via backup** | Rollback de imagem **não desfaz** a migration já aplicada (Flyway é forward-only, sem downgrade automático); a única saída é restaurar o Postgres a partir de um snapshot anterior à migration, aceitando perder qualquer escrita entre esse snapshot e o incidente |

## 28. Rollback (imagem) vs. Restore (dado)

**Deixado explícito:** rollback de imagem GHCR (`APP_VERSION=<sha-anterior>`, DT-011A.4) reverte **código**, nunca **dado**. Uma migration destrutiva que já rodou contra o banco permanece aplicada mesmo depois de o container voltar para uma versão mais antiga — o código antigo pode inclusive quebrar contra um schema que ele não reconhece (risco já registrado no DT-011A.4 §18). Restore (esta sprint) é o único mecanismo que reverte dado, e é inerentemente mais custoso (downtime, possível perda do intervalo desde o último snapshot) que um rollback de imagem. **Nenhum downgrade automático de migration Flyway é implementado ou planejado.**

## 30. Plano de Testes (futuro)

1. Criar um registro no banco (ex.: um cliente de teste).
2. Fazer upload de um arquivo (logo ou galeria).

## 34. Alternativas Rejeitadas

| Alternativa | Por que foi rejeitada |
|---|---|
| Snapshot bruto do volume Docker (opção A, §8.1) | Exige parar o Postgres ou infraestrutura de snapshot de filesystem que não existe |
| `pg_dumpall` como formato principal | Sem restore seletivo/paralelo, só texto plano; desnecessário para um único banco/role |
| Backup físico/contínuo com PITR (WAL-G, pgBackRest) | Complexidade operacional desproporcional a um MVP sem exigência de PITR/HA |
| WebDAV/SMB para a Storage Box | Exigiriam `rclone` ou não têm suporte nativo no Restic; SFTP já resolve nativamente |
| Restic dentro do container da aplicação | Mistura responsabilidade de app com responsabilidade operacional; infla a imagem de produção |
| Serviço `backup` permanente no `docker-compose.prod.yml` | Um serviço "sempre up" para uma tarefa inerentemente periódica é um modelo errado — systemd timer + containers efêmeros encaixa melhor |
| Vault/secret manager enterprise | Desproporcional a um único VPS/cliente; password manager já resolve o problema real (guardar 2–3 segredos fora do Restic) |
| GitHub Secrets para credenciais de backup da VPS | Não há job de CI que precise alcançar a Storage Box; GitHub Secrets são para o pipeline (11A.4), não para segredos operacionais de runtime da VPS |
| Cron em vez de systemd timer | Perde a visibilidade nativa de `journalctl`/`systemctl status` sem esforço extra de redirecionamento de log |
