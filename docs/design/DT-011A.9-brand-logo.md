## 1. Estado atual encontrado

Inspeção completa do código real (não presumido). **Achado central: a funcionalidade pedida já existe, ponta a ponta, no backend.**

### Branding / Company
- `Branding` (`company/domain/Branding.java`) já tem `logoUrl` (`@Column(name = "logo_url")`) desde a migration `V2__create_company_core_tables.sql:34` (`logo_url TEXT`) — **nenhuma migration nova é necessária**.
- `Company` **não** tem nenhum campo de logo — corretamente, logo é atributo de marca (Branding), não de cadastro (Company).
- `BrandingResponse` (DTO retornado por `GET /branding/me` e também pelas operações de logo) **já inclui `logoUrl`**.
- `BrandingController` (`/branding/me`, GET/PUT) já existe — cobre cores, tagline, about/footer, quotation prefix, signature name. **Não** tem endpoint de upload/delete de logo.

### Upload/delete de logo — já implementado, num lugar diferente do `/branding`
- `CompanyController` já expõe:
  - `POST /company/logo` (multipart, `@PreAuthorize("hasRole('OWNER')")`) → `CompanyService.uploadLogo(principal.companyId(), file)`
  - `DELETE /company/logo` (`@PreAuthorize("hasRole('OWNER')")`) → `CompanyService.deleteLogo(principal.companyId())`
- Ambos usam **`principal.companyId()`** (derivado do JWT, nunca de parâmetro de request) — isolamento por tenant já garantido, sem input do cliente.
- `CompanyService.uploadLogo`: valida via `ImageUploadPolicy`, **apaga o arquivo antigo antes de gravar o novo** (`storageService.delete(branding.getLogoUrl())` se existir), grava em `"company/" + companyId + "/logo"`, atualiza `Branding.logoUrl`, retorna `BrandingResponse` (mesma forma de `/branding/me`).
- `CompanyService.deleteLogo`: apaga o arquivo (se existir) e limpa `logoUrl` para `null`.

### Storage — já é uma abstração reaproveitável, sem acoplamento a Gallery
- `StorageService` (interface, `common/storage`) — `store(folder, file) -> url`, `delete(url)`, `load(url) -> Optional<byte[]>`. Comentário no código já documenta a intenção: "Implementations may target local disk, Supabase, S3, etc."
- `LocalStorageService` (única implementação hoje): grava em `{STORAGE_PATH}/{folder}/{UUID-aleatório}.{ext}` — **nome de arquivo nunca vem do cliente** (gerado via `UUID.randomUUID()`), e todo path é `normalize()`d e verificado com `startsWith(baseDir)` tanto em `store` quanto em `delete`/`load` — proteção de path traversal já existe e é exercitada tanto para `folder` (entrada do código, não do usuário) quanto para `storedPath` (valor gravado no banco, nunca aceito bruto do cliente em nenhum endpoint).
- `ImageUploadPolicy` (já usada por Gallery **e** por Company/logo): tamanho máximo 5 MB, `Content-Type` restrito a `image/png|jpeg|webp`, extensão do nome do arquivo cruzada com o `Content-Type`, e **validação de assinatura binária real** (magic bytes de PNG/JPEG/WebP) — não confia só no header declarado pelo cliente.
- `GalleryImageService` (equivalente do lado da Gallery) e `CompanyService.uploadLogo`/`deleteLogo` (lado do logo) **já são duas orquestrações independentes e finas sobre o mesmo `StorageService`/`ImageUploadPolicy` compartilhado** — nenhuma depende da outra, nenhum acoplamento Branding↔Gallery existe hoje. Ou seja: **o reaproveitamento pedido já está feito**, não como uma dependência direta, mas como duas implementações-irmãs sobre a mesma infraestrutura comum.
- `/uploads/**` é servido como recurso estático (`StorageWebConfig`, `ResourceHandlerRegistry`) a partir de `STORAGE_PATH`, com cache de 30 dias.

### Public Site
- `CompanyService.getPublicSite(slug)` já monta `PublicSiteBrandingResponse(branding.getLogoUrl(), ...)` — **a landing pública já recebe a logo**, sem nenhuma mudança necessária.

- `@PreAuthorize("hasRole('OWNER')")` já impede SUPER_ADMIN (que nunca tem `ROLE_OWNER`) de acessar esses endpoints — não há concessão implícita de acesso.

### Testes já existentes

## 2. Gaps

Depois da inspeção, **não há gap funcional, de dados, de segurança ou de storage**. Os únicos pontos reais de atenção são:

1. **Ergonomia de API**: o upload/delete de logo vive em `/company/logo`, enquanto os demais campos de marca vivem em `/branding/me`. A tela "Branding" do frontend precisará chamar dois recursos diferentes para uma única tela — não é um defeito, mas é uma decisão a registrar explicitamente (§3).
2. **Gap de teste (não de código)**: nenhum teste hoje verifica o caminho ponta-a-ponta "upload via `/company/logo`" → "`GET /public/sites/{slug}` reflete a nova logo". Os testes existentes cobrem `CompanyService`/`CompanyController` isoladamente; falta uma prova de integração completa.

## 3. Decisão arquitetural

**Não criar nenhum endpoint novo, nenhuma entidade nova, nenhuma migration.** A funcionalidade pedida — OWNER faz upload/altera/remove a logo pela tela Branding, e a landing pública consome essa logo — **já está implementada em produção-pronta desde sprints anteriores**.

Único ponto de decisão real: **manter `POST/DELETE /company/logo` onde estão** (não movê-los para `/branding/logo`). Justificativa: mover exigiria alterar um contrato já testado e possivelmente já consumido, sem nenhum ganho funcional — só estético. A tela "Branding" do frontend simplesmente consome **dois recursos** para uma tela (`/branding/me` para texto/cores, `/company/logo` para a imagem) — isso já é exatamente como o Codex terá que integrar, e é a menor mudança possível (na verdade, zero mudança de backend).

## 4. Modelo de dados

Inalterado. `brandings.logo_url` (`TEXT`, nullable) já existe desde `V2`. Nenhuma migration nesta sprint.

## 5. Contratos HTTP exatos (já existentes, congelados — nenhuma mudança)

### `GET /branding/me` (autenticado, qualquer papel com sessão válida)
Response `200`:
```json
{
  "id": "uuid", "companyId": "uuid",
  "logoUrl": "/uploads/company/{companyId}/logo/{uuid}.png",
  "primaryColor": "#1E40AF", "secondaryColor": "#3B82F6", "accentColor": "#F59E0B",
  "tagline": "...", "aboutText": "...", "footerText": "...",
  "quotationPrefix": "...", "signatureName": "..."
}
```

### `PUT /branding/me` (`hasRole('OWNER')`)
Request: `UpdateBrandingRequest` (todos os campos opcionais, cores validadas como hex `#RRGGBB`). Não altera `logoUrl` — campo não faz parte deste request.

### `POST /company/logo` (multipart, `hasRole('OWNER')`)
Request: `multipart/form-data`, campo `file`. Response `200`: `BrandingResponse` (mesma forma de `/branding/me`, já com o novo `logoUrl`).
Erros: `400` arquivo vazio/tipo inválido/assinatura não corresponde (`ImageUploadPolicy`, `BusinessRuleException` → `422` na verdade — ver `GlobalExceptionHandler`, `BusinessRuleException` mapeia para `422 Unprocessable Entity`, não `400`), `401` sem sessão/conta inativa, `403` não-OWNER.

### `DELETE /company/logo` (`hasRole('OWNER')`)
Response `204`. Idempotente (sem logo existente → no-op, ainda `204`).

**Nenhum destes três contratos muda nesta sprint.**

## 7. Fluxo upload/replace/delete

Já implementado, sem mudanças:

1. **Upload inicial**: `POST /company/logo` com `Branding.logoUrl == null` → valida → grava novo arquivo → seta `logoUrl`.
2. **Substituição**: `POST /company/logo` com `logoUrl` já preenchido → valida o novo arquivo → **apaga o arquivo antigo primeiro** → grava o novo → atualiza `logoUrl`. (Ordem importa: se a validação do novo arquivo falhar, o antigo nunca é tocado — `imageUploadPolicy.validate(file)` roda antes de qualquer `storageService.delete`.)
3. **Remoção**: `DELETE /company/logo` → se `logoUrl != null`, apaga o arquivo e limpa `logoUrl`; se já `null`, no-op idempotente.
4. **Arquivo antigo órfão**: nunca acontece — apagar sempre acontece antes ou junto da atualização do banco, dentro da mesma transação Spring (`@Transactional` em `CompanyService`); uma falha de storage lança `StorageException` (500), a transação do banco reverte, `logoUrl` não muda — nunca fica um `logoUrl` apontando para um arquivo que não existe mais por causa desta operação (o único jeito de isso acontecer é um apagamento manual do arquivo por fora da aplicação, fora do escopo desta sprint).

O frontend público (landing) já recebe o campo `logoUrl` na resposta de `GET /public/sites/{slug}` — a integração pedida pelo enunciado ("a logo será consumida pela landing pública multi-tenant") **já existe**.

## 9. Segurança e tenant isolation

Todos os pontos pedidos já estão cobertos pelo código existente:
- **OWNER só altera a própria company**: `principal.companyId()` (do JWT, nunca de input do cliente) é a única fonte de `companyId` usada em `uploadLogo`/`deleteLogo` — não há parâmetro de company id no request.
- **SUPER_ADMIN não tem acesso implícito**: `@PreAuthorize("hasRole('OWNER')")` — SUPER_ADMIN nunca tem essa authority (Sprint 11A.7), então recebe `403` como qualquer outro papel.
- **MIME/extensão real**: `ImageUploadPolicy` já valida `Content-Type` declarado + extensão do nome do arquivo + assinatura binária (magic bytes) — três camadas, não confia em nenhuma isoladamente.
- **Path traversal / nome de arquivo controlado**: `LocalStorageService` nunca usa o nome de arquivo original do cliente para gravar — gera `UUID.randomUUID()` + extensão normalizada; todo path é `normalize()`d e verificado contra o diretório-base antes de qualquer operação de I/O.
- **Company INACTIVE**: bloqueado pelo `ActiveAccountFilter` (Sprint 11A.7) antes mesmo de o request chegar ao controller — nenhuma checagem adicional necessária em `CompanyService`.
- **Arquivo inexistente no delete/replace**: `StorageService.delete`/`load` já tratam `storedPath` nulo/inexistente sem lançar exceção (no-op ou `Optional.empty()`).

## 10. Comportamento local e produção

Já funciona igual nos dois ambientes, sem mudança: `StorageService` é uma interface — hoje só há `LocalStorageService` (grava em `STORAGE_PATH`, serve via `/uploads/**`). Uma futura implementação S3/Supabase (fora de escopo desta sprint, não pedida) implementaria a mesma interface sem exigir nenhuma mudança em `CompanyService`/`BrandingService`/`GalleryImageService`/`ImageUploadPolicy` — a "solução multi-tenant, não específica de JR Pinturas" já é exatamente isso: `companyId` sempre vem do JWT, a pasta é sempre `company/{companyId}/logo`, para qualquer tenant, sem exceção.

A tela "Branding" do frontend deve:
- Usar `GET /branding/me` para carregar o estado atual (incluindo `logoUrl` já presente na resposta).
