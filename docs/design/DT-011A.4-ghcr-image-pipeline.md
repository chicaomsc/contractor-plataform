## 2. Contexto

As Sprints 11A.1–11A.3 já deixaram o `docker-compose.prod.yml` **parametrizado** para consumir imagens publicadas (`BACKEND_IMAGE`, `FRONTEND_IMAGE`, `APP_VERSION`), mas **nada publica essas imagens ainda**. Hoje, a única forma de obter `ghcr.io/.../contractor-platform-backend:local` é rodar `docker compose build` localmente — o que exige Java/Maven e Node/npm disponíveis onde o build acontece.

A Sprint 11A.4 fecha essa lacuna: GitHub Actions builda as duas imagens com Docker Buildx e publica no GHCR, taggeadas de forma imutável pelo commit SHA. Isso é o que permite, mais tarde (Sprint 11B, fora do escopo aqui), a VPS rodar apenas `docker compose pull && docker compose up -d` — nunca `mvn`/`npm` na VPS.

### 5.5 `docker-compose.prod.yml` — o fluxo `pull`/`up` já é suportado?

Sim, conceitualmente, **já funciona hoje** sem qualquer alteração estrutural:

- O bloco `build:` continuar presente no Compose não é um problema — ele só é relevante para quem roda `docker compose build` localmente (desenvolvimento/validação, como fizemos na Sprint 11A.3); a VPS nunca precisa dele.

## 6. Arquitetura Proposta

```
Pull Request → main            GitHub Actions (backend-ci.yml / frontend-ci.yml, inalterados)
                                  → lint, testes, build de validação — NUNCA publica imagem

Push em main (após merge)      GitHub Actions (NOVO: publish-images.yml)
                                  → Docker Buildx
                                  → GHCR
                                       ├── ghcr.io/chicaomsc/contractor-platform-backend:<sha>
                                       └── ghcr.io/chicaomsc/contractor-platform-frontend:<sha>

workflow_dispatch                Re-publicação manual de qualquer ref (ver §8)

VPS (Sprint 11B, fora de escopo) APP_VERSION=<sha> docker compose pull
                                  APP_VERSION=<sha> docker compose up -d
```

**Decisão-chave (responde à questão 11 do pedido): workflow novo e separado, não extensão do CI existente.** `backend-ci.yml`/`frontend-ci.yml` respondem a "o código está correto?" (responsabilidade de qualidade); o novo workflow responde a "este commit deve virar um artefato publicado?" (responsabilidade de release). São preocupações diferentes com gatilhos, permissões e riscos diferentes (o segundo escreve em um registro externo, o primeiro não) — separar reduz a superfície de `packages: write` ao mínimo necessário e evita tocar em workflows que já funcionam. Nenhum workflow existente é modificado.

## 7. Fluxo PR → CI

**Sem mudança.** `backend-ci.yml` e `frontend-ci.yml` continuam exatamente como estão: rodam em todo PR para `main`, validam código, **nunca** constroem ou publicam imagem Docker. Isso já satisfaz literalmente a preferência declarada ("PR: valida código, NÃO publica imagem de produção") sem qualquer alteração.

**Considerado e não incluído nesta proposta:** um job de "`docker build` sem push" em PRs que tocam `backend/Dockerfile`/`frontend/Dockerfile`, só para validar que o Dockerfile ainda builda. É barato e não viola "não publicar em todo PR" (build ≠ push), mas não foi pedido explicitamente e adicionaria mais uma peça móvel. Registrado como recomendação futura de baixo custo (§21/§24), não como parte desta entrega.

## 8. Fluxo main → build → GHCR

### 8.1 Trigger

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'backend/**'
      - 'frontend/**'
      - '.github/workflows/publish-images.yml'
  workflow_dispatch:
    inputs:
      ref:
        description: 'Git ref (branch, tag ou SHA) a construir e publicar'
        required: false
        default: ''
```

- `push` em `main`: cobre o fluxo principal (merge de PR → publica).
- `workflow_dispatch`: cobre republicação manual de um ref específico sem precisar de um novo commit — útil para (a) primeira publicação antes de qualquer push novo, (b) reprocessar um build que falhou por instabilidade de infraestrutura, (c) **republicar um valor diferente de `NEXT_PUBLIC_*`** depois de atualizar as GitHub Actions Variables, sem tocar em código (ver §12.4 — resolve o problema de "ainda não temos domínio real" sem exigir um commit vazio).
- `pull_request` **não** é gatilho deste workflow — respeitando "PR não publica imagem".

### 8.2 Escopo de build por push

Ambos os jobs (`backend`, `frontend`) rodam sempre que o workflow é disparado, mesmo que só um dos dois diretórios tenha mudado. **Decisão deliberada de simplicidade:** filtrar por job qual imagem precisa de rebuild (`dorny/paths-filter` ou `git diff`) economizaria ~20–40s de CI ocasionalmente, mas adiciona uma dependência e uma superfície de bugs (diff de squash-merge, force-push) desproporcional ao benefício neste estágio (1 cliente, builds já rápidos — build completo do frontend levou ~20s na validação da Sprint 11A.3). Rejeitado por ora; documentado como otimização futura de baixo valor atual em §22.

### 8.3 Concorrência

```yaml
concurrency:
  group: publish-images-${{ github.ref }}
  cancel-in-progress: false
```

Evita duas publicações simultâneas do mesmo ref pisarem uma na outra; `cancel-in-progress: false` porque cancelar um push já em andamento no meio de um `docker push` pode deixar o registry em estado parcial — melhor esperar terminar.

## 10. Estratégia de Tags

Cada build publica **3 tags para o mesmo digest** (nenhum build extra — `docker/build-push-action` aceita múltiplas tags em um único build):

| Tag | Mutável? | Uso |
|---|---|---|
| `:<full-sha>` (40 chars, `git rev-parse HEAD`) | **Não** | Referência canônica para deploy/rollback — é o valor de `APP_VERSION` |
| `:<short-sha>` (7 chars, `git rev-parse --short HEAD`) | **Não** | Alias de conveniência — mesmo digest, mais fácil de digitar manualmente numa sessão SSH futura |
| `:main` | **Sim** (aponta sempre para o build mais recente de `main`) | **Só para inspeção humana no GHCR** ("qual é o build mais recente?") — nunca usado como `APP_VERSION` |

**`:latest` não é publicada.** Em vez de publicar e apenas orientar "não use `:latest` para deploy", a tag simplesmente não é criada — remove a tentação por completo em vez de depender de disciplina.

Full-SHA e short-SHA resolvem para o mesmo manifesto; qualquer um serve como `APP_VERSION`. Full-SHA é recomendado como a referência "oficial" documentada (zero ambiguidade, idêntico ao que `git rev-parse HEAD` produz), short-SHA como conveniência aceita para digitação manual.

## 11. Estratégia de `APP_VERSION`

Nenhuma mudança estrutural necessária em `docker-compose.prod.yml` (já confirmado em §5.5). O fluxo conceitual da VPS (fora de escopo implementar, mas validado conceitualmente aqui):

```bash
export APP_VERSION=<sha>
docker compose --env-file infra/env/production.env -f infra/compose/docker-compose.prod.yml pull
docker compose --env-file infra/env/production.env -f infra/compose/docker-compose.prod.yml up -d
```

Isso funciona porque:
1. `image:` já é `${BACKEND_IMAGE:-...}:${APP_VERSION:-local}` / equivalente para frontend — 100% parametrizado.
2. `pull` busca exatamente essa tag no GHCR.
3. `up -d` (sem `--build`) usa a imagem já pulled, nunca reconstrói.

**Ajuste necessário (não estrutural, só de valor-default):** os defaults em `docker-compose.prod.yml` e `production.env.example` apontam para `ghcr.io/chicaodw/...` (owner errado, §5.2). Corrigir para `ghcr.io/chicaomsc/...` — listado em §23 como arquivo a alterar na implementação.

## 12. Análise de `NEXT_PUBLIC_*` e Multi-tenancy

### 12.1 O que foi encontrado

- O backend é genuinamente multi-tenant desde a concepção — ADR-000 registra que a alternativa "A3 — Começar como produto single-tenant" foi **rejeitada** explicitamente ("A adição retroativa de `company_id` gera migrações custosas... o custo de incluí-lo desde o início é mínimo"). Isolamento multi-tenant por `company_id` está implementado e testado (roadmap confirma testes cross-tenant para customer/estimate/service).
- O frontend, no entanto, tem **um** ponto de acoplamento a um tenant específico em build-time: `NEXT_PUBLIC_COMPANY_SLUG`, consumido só por `app/(public)/page.tsx`, decide qual empresa é renderizada na landing pública (`/`) de uma imagem já publicada.
- Isso não é um bug introduzido agora nem uma contradição do ADR-000 — é uma simplificação operacional já documentada implicitamente no comentário do próprio `frontend/Dockerfile` ("Given this deployment currently serves a single tenant, baking them in at build time... is the proportionate choice") e no roadmap ("JR Pinturas renderiza pela landing multi-tenant existente... sem hardcode permanente do tenant" — a *lógica* de renderização é genérica; o *slug* servido em `/` é que é fixado por build).

### 12.2 Por que isso importa para o pipeline GHCR especificamente

Antes desta sprint, essa amarração só existia localmente (`docker compose build`, valores de `production.env`). A partir do momento em que uma imagem **publicada e versionada por SHA** existe no GHCR, ela se torna um artefato redistribuível — e alguém (inclusive o próprio time, no futuro) pode presumir, pelo nome genérico `contractor-platform-frontend`, que a imagem serve qualquer tenant. Ela não serve: serve exatamente a empresa cujo slug foi passado como `--build-arg` naquele build.

**Isto não deve ser aceito silenciosamente** (conforme instrução explícita) — três opções foram avaliadas:

| Opção | Descrição | Avaliação |
|---|---|---|
| **A — Build único por tenant, hoje** (recomendada) | Mantém o modelo atual (1 imagem = 1 tenant fixado por build-arg), mas torna os valores explícitos e rastreáveis: build args vêm de **GitHub Actions Variables** (não hardcoded no workflow), e a imagem recebe um **label OCI** registrando o slug usado (`org.opencontainers.image.description` ou label customizado, ex. `io.chicaodw.tenant=jr-pinturas`) | Proporcional ao MVP (1 cliente real hoje). Custo: uma linha de label no Dockerfile. Não resolve multi-tenant de fato, mas impede a imagem de *parecer* genérica sem ser. |
| **B — Resolução de tenant em runtime** (ex. middleware Next.js mapeia `Host`/domínio → slug via chamada à API, elimina `NEXT_PUBLIC_COMPANY_SLUG`) | Solução arquiteturalmente correta para multi-tenant real no frontend | **Rejeitada nesta sprint** — é a "grande refatoração" que a tarefa pede explicitamente para não fazer agora. Registrada como dívida técnica futura (§26), a ser considerada quando um 2º cliente for onboardado. |
| **C — Build paramétrico por cliente (matriz de build)** | CI builda N imagens, uma por tenant conhecido, tags `frontend:<sha>-<tenant>` | Rejeitada por ora — não há 2º cliente ainda; adicionar a matriz agora é complexidade sem uso real. Vira natural quando (B) não for prioritária mas 2 clientes precisarem coexistir. |

**Recomendação:** opção A. Isso mantém o escopo desta sprint estritamente dentro do pipeline de CI/CD, sem tocar em `page.tsx` ou em lógica de roteamento, e sem fingir que o problema não existe.

### 12.3 Os 3 ARGs e a origem de cada valor

| ARG | Segredo? | Fonte proposta no workflow |
|---|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | Não (mas específico do ambiente-alvo) | `vars.NEXT_PUBLIC_API_BASE_URL` (GitHub Actions **Variable**, não secret) |
| `NEXT_PUBLIC_COMPANY_SLUG` | Não (mas específico do tenant, ver §12.2) | `vars.NEXT_PUBLIC_COMPANY_SLUG` |
| `NEXT_PUBLIC_SITE_URL` | Não | `vars.NEXT_PUBLIC_SITE_URL` |

Nenhum dos três é segredo — todos acabam visíveis no bundle JS do browser após o build (fato já documentado desde a Sprint 11A.2). Usar GitHub Actions **Variables** (não Secrets) é o tratamento correto: não passam por mascaramento de log desnecessário, e ficam editáveis por qualquer colaborador com permissão de escrita no repo, sem exigir acesso a Secrets.

### 12.4 O problema do domínio ainda não existir

`NEXT_PUBLIC_API_BASE_URL`/`NEXT_PUBLIC_SITE_URL` deveriam, em produção real, apontar para o domínio público que o Caddy serve (Sprint 11A.3) — mas nenhum domínio real foi configurado ainda (Cloudflare/DNS são Sprint 11C+). Usar GitHub Actions Variables resolve isso de forma limpa: quando o domínio existir, atualiza-se o valor da Variable e dispara-se `workflow_dispatch` para republicar — **sem** alterar o workflow ou o código. Até lá, a Variable pode apontar para um valor de staging/placeholder documentado (não um domínio inventado).

## 13. Estratégia de Cache

```yaml
cache-from: type=gha,scope=backend    # (ou scope=frontend, por job)
cache-to: type=gha,mode=max,scope=backend
```

- Cache do Buildx via GitHub Actions cache (`type=gha`) — sem infraestrutura extra, sem custo adicional mensurável (cache do GHA é gratuito dentro dos limites padrão do repositório).
- `scope=backend`/`scope=frontend` evita que o cache de uma imagem invalide/colida com o da outra.
- **Não** propor cache mount do BuildKit para `~/.m2`/`~/.npm` (`--mount=type=cache`) agora — os Dockerfiles já fazem cache em camada por `COPY pom.xml`/`COPY package.json` antes do código-fonte (Sprint 11A.1), o que já dá a maior parte do ganho de "não re-baixar dependências a cada commit". Adicionar cache mounts seria um segundo mecanismo de cache sobreposto sem benefício mensurável comprovado neste volume de commits — registrado como otimização futura **se** os tempos de build se tornarem um problema real (§22).

## 14. Plataforma Docker Alvo

**Somente `linux/amd64`.**

- A VPS alvo (Hetzner, Sprint 11B) é x86_64.
- Os runners `ubuntu-latest` do GitHub Actions já são nativamente `amd64` — um build single-platform não precisa de emulação QEMU, é o caminho mais rápido possível.
- Publicar também `linux/arm64` exigiria emulação QEMU no runner (não há runner arm64 nativo gratuito para builds públicos padrão), o que **aumenta sensivelmente o tempo de build** (tipicamente 2–4× mais lento para o estágio emulado) sem nenhum consumidor real da arquitetura — o desenvolvimento local em Apple Silicon roda `docker compose build` localmente (nativo arm64 no Mac), nunca consome a imagem publicada pelo GHCR para isso.
- **Rejeitado por ora:** multi-arch. Reavaliar somente se um alvo de produção arm64 (ex. Graviton) entrar em cogitação — não é o caso hoje.

## 15. Permissões GitHub Necessárias

```yaml
permissions:
  contents: read
  packages: write
```

- Declarado no nível do workflow (aplica-se a todos os jobs) — sem escopos adicionais (`id-token`, `issues`, etc. não são necessários para este fluxo).
- `GITHUB_TOKEN` (automático, por execução, expira ao final do job) é suficiente para autenticar no GHCR via `docker/login-action` quando o pacote pertence ao mesmo repositório/owner que gera o token — **nenhum PAT é necessário** para publicar.
- PAT só se tornaria necessário no lado do **pull** (VPS, fora de escopo) **se** o pacote GHCR for privado — ver §20 sobre a decisão de visibilidade, e §26 (pendência futura).

## 16. Tratamento de Secrets

| Categoria | Exemplos | Onde vive | Nesta pipeline |
|---|---|---|---|
| Configuração pública de build | `NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_COMPANY_SLUG`, `NEXT_PUBLIC_SITE_URL` | GitHub Actions **Variables** (`vars.*`) | Passados como `--build-arg`, ficam visíveis no bundle JS por design — não são segredo |
| Segredo de runtime | `JWT_SECRET`, `POSTGRES_PASSWORD`, `APP_CORS_ALLOWED_ORIGINS` (sensível o suficiente para não logar) | `infra/env/production.env` na VPS (nunca commitado) | **Nunca** tocados por este pipeline — não existem no contexto de build, não são `--build-arg`, não entram em nenhuma camada de imagem |
| Credencial de registry | Token de push ao GHCR | `secrets.GITHUB_TOKEN` (automático) | Usado só em `docker/login-action`, nunca logado, nunca em build arg |

Regra dura mantida: **nenhum segredo de runtime pode ser `--build-arg`** — isso ficaria permanentemente legível na camada da imagem (`docker history`) mesmo que nunca apareça em log. Os três `NEXT_PUBLIC_*` são a única categoria de "config de build" que este pipeline manipula, e nenhum deles é segredo.

## 17. Rollback

Mecanismo (conceitual — a execução real na VPS é Sprint 11B):

```bash
export APP_VERSION=<sha-anterior>
docker compose --env-file infra/env/production.env -f infra/compose/docker-compose.prod.yml pull
docker compose --env-file infra/env/production.env -f infra/compose/docker-compose.prod.yml up -d
```

Funciona porque toda imagem publicada por esta pipeline é imutável e referenciável por SHA indefinidamente (sem política de retenção que as apague — §19). Rollback é literalmente trocar o valor de uma variável de ambiente e repetir `pull`/`up -d`.

**Aviso explícito (pedido pelo usuário): rollback de container não é rollback de banco de dados.** Ver §18.

## 18. Implicações do Flyway

- Flyway, como configurado neste projeto, é **forward-only** — não há migrations "undo" (esse recurso é parte paga do Flyway Teams/Enterprise e não está em uso aqui).
- Se o container do backend for revertido para uma versão de código mais antiga **depois** que uma migration mais nova já rodou contra o banco, o código antigo passa a rodar contra um schema que ele não conhece. Isso é seguro **somente se** a migration aplicada foi estritamente aditiva/retrocompatível (ex.: nova coluna nullable, nova tabela) — é inseguro se a migration removeu/renomeou uma coluna, alterou um tipo, ou tornou algo `NOT NULL` que o código antigo não preenche.
- **Nenhum downgrade automático de migration é implementado ou recomendado nesta sprint.** Uma reversão de schema genuína exigiria uma migration "de volta" escrita e revisada manualmente, ou uma restauração a partir de backup (backup é Sprint 11A.5, fora de escopo).
- **Recomendação de processo (documentação, não ferramenta):** escrever migrations aditivas/retrocompatíveis sempre que possível, especificamente para manter rollback de container seguro por padrão. Isso é uma prática a documentar no `infra/README.md` na implementação (§23), não uma mudança de código nesta sprint.

## 19. Supply Chain — Proporcional ao MVP

| Item | Classificação | Justificativa |
|---|---|---|
| Pin de actions por tag de major version (`@v4`, já em uso) | **Necessário agora** (já é a prática atual) | Aceitável para um repo pequeno, mantido por 1–2 pessoas; trocar para pin por SHA em `checkout`/`setup-node`/`setup-java` teria custo de manutenção (atualizar SHAs manualmente) desproporcional ao risco atual |
| Pin por SHA especificamente para `docker/login-action` e `docker/build-push-action` (as duas ações com acesso a credenciais/push) | **Recomendado** | Risco um pouco maior que as demais (escrevem no registry) — pin por SHA nessas duas é barato e mitiga supply-chain attack via tag flutuante comprometida, sem exigir reescrever todo o workflow |
| Provenance de build (`provenance: true` no `build-push-action`) | **Recomendado** (essencialmente gratuito) | `docker/build-push-action` já suporta nativamente, custo de CI desprezível, gera atestado verificável da origem do build |
| SBOM (`sbom: true`) | **Recomendado** (gratuito) | Mesma lógica — opt-in barato, útil se um cliente futuro pedir inventário de dependências |
| Scanning de vulnerabilidade (ex. Trivy, não bloqueante) | **Recomendado** | Barato de adicionar como job informativo (não falha o pipeline); valioso dado que a imagem lida com uploads/dados de cliente — mas não é bloqueio de lançamento nesta sprint |
| Assinatura de imagem (cosign/sigstore) | **Futuro** | Exige infraestrutura de verificação no lado do pull (VPS) que não existe e não é necessária para 1 cliente sem exigência de compliance hoje |

Nenhum destes itens vira parte obrigatória do workflow proposto em §8 — os marcados "recomendado" podem ser adicionados na implementação com custo marginal; os "futuro" ficam fora.

## 20. Custos

- **GitHub Actions:** repositório é **público** (confirmado em §5.1) → minutos de Actions são **ilimitados e gratuitos** para repositórios públicos. Custo marginal desta pipeline: **$0**, contanto que o repositório permaneça público.
- **GHCR (armazenamento + banda):** pacotes **públicos** também têm armazenamento/banda gratuitos e ilimitados. Pacotes **privados** em conta pessoal têm cota gratuita limitada (e custo acima dela).
- **Decisão pendente (humana, não técnica):** manter os pacotes GHCR públicos (custo zero, consistente com o repositório já ser público) ou torná-los privados (o binário/bundle compilado circula menos livremente, mesmo que o código-fonte já seja público) — ver questão no relatório final.
- **Sem infraestrutura nova:** nenhum runner self-hosted, nenhum serviço gerenciado adicional (ECR/ECS/Kubernetes seguem fora do escopo, como já era).

## 21. Riscos e Trade-offs

| Risco | Mitigação/Aceite |
|---|---|
| Imagem frontend fica presa a um tenant (`NEXT_PUBLIC_COMPANY_SLUG`) mas com nome genérico | Aceito para o MVP (opção A, §12.2); label OCI registra o tenant baked-in; refatoração para runtime fica documentada como dívida futura |
| Rollback de container ≠ rollback de banco (Flyway forward-only) | Documentado explicitamente (§18); disciplina de migrations aditivas recomendada, não imposta por ferramenta |
| Build sempre roda para as duas imagens, mesmo sem mudança em uma delas | Aceito — custo de CI desprezível (repo público, minutos grátis; build individual leva segundos) |
| Pacote GHCR público expõe o binário/bundle compilado | Repositório já é público (código-fonte já visível); decisão de visibilidade do pacote é independente e fica para o humano decidir (§20) |
| `workflow_dispatch` republicando um ref antigo por engano | Input `ref` é opcional e explícito; nenhuma automação dispara isso sozinha; poderia futuramente usar GitHub Environments com aprovação manual (fora de escopo agora) |
| Ausência de scanning/assinatura de imagem nesta sprint | Classificado como recomendado/futuro em §19, não bloqueante para o objetivo desta sprint (ter imagens publicadas e versionadas) |
| Dois workflows (`*-ci.yml` e o novo) disparando em paralelo no mesmo push a `main` | Não há dependência entre eles por design (§6) — ambos podem rodar simultaneamente sem conflito, já que não compartilham recursos mutáveis |

## 22. Alternativas Rejeitadas

| Alternativa | Por que foi rejeitada |
|---|---|
| Runner self-hosted para os builds | Custo/manutenção de infraestrutura extra sem necessidade — runners `ubuntu-latest` gratuitos já atendem |
| Docker Hub em vez de GHCR | Exigiria conta/billing separados; GHCR já é gratuito e integrado à autenticação do próprio repositório via `GITHUB_TOKEN` |
| Multi-arch (`linux/amd64` + `linux/arm64`) agora | Sem consumidor real de arm64 em produção; aumento real de tempo de CI via emulação QEMU sem benefício atual (§14) |
| PAT dedicado em vez de `GITHUB_TOKEN` | Segredo adicional para gerenciar/rotacionar sem necessidade — `GITHUB_TOKEN` já tem permissão suficiente para push no próprio namespace |
| Gate via `workflow_run` (publicar só após CI terminar) | Adiciona indireção/atraso e complexidade de depuração; branch protection (PR obrigatório + CI obrigatório antes do merge) já garante que só código validado chega a `main` |
| Path do pacote aninhado por repositório (`.../contractor-plataform/backend`) | Quebraria a convenção plana já usada em `docker-compose.prod.yml`/`production.env.example` sem ganho (§9) |
| Filtragem de path por job (build seletivo backend vs frontend) | Complexidade (`dorny/paths-filter` ou diff manual) desproporcional ao ganho de CI minutes neste volume (§8.2) |
| Cache mount do BuildKit (`--mount=type=cache`) além do `type=gha` | Segundo mecanismo de cache sobreposto sem benefício mensurável comprovado agora (§13) |
| Resolver `NEXT_PUBLIC_COMPANY_SLUG` em runtime já nesta sprint | Seria a "grande refatoração" explicitamente fora de escopo; registrada como dívida futura (§12.2, §26) |
