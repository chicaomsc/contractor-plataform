## 1. Contexto

O backend já é multi-tenant no sentido de que cada `User` pertence a uma `Company` (`company_id`) e todo o isolamento de dados é feito filtrando por esse `companyId` — ver `TenantIsolationIntegrationTest`. Mas isso é multi-tenancy **de dados**, não de **produto**: hoje só existe uma forma de criar uma empresa (`POST /auth/register`, autoatendimento), só existe um papel (`OWNER`), e o frontend público resolve o tenant a exibir através de uma variável **de build** (`NEXT_PUBLIC_COMPANY_SLUG=jr-pinturas`, gravada dentro da imagem Docker em `frontend/Dockerfile:31-34` e imposta como obrigatória em `infra/compose/docker-compose.prod.yml:133`).

Isso significa, na prática, que **uma imagem de frontend = um cliente**. Para colocar um segundo cliente em produção hoje seria preciso: gerar uma segunda imagem GHCR com outro `NEXT_PUBLIC_COMPANY_SLUG`, outro `docker-compose.prod.yml`/stack, e criar a conta via API diretamente — não existe nenhuma tela ou papel que permita a nós, operadores da plataforma, provisionar clientes.

## 2. Objetivo desta sprint

Transformar "aplicação multi-tenant nos dados, mono-tenant na entrega" em "plataforma administrável com resolução de tenant em runtime", sem ainda precisar de DNS real, billing, e-mail transacional ou self-service público. Esta sprint entrega o **desenho técnico completo** (DT-only); a implementação será dividida entre Claude Code (backend) e Codex (frontend) numa etapa seguinte.

## 5. SUPER_ADMIN — modelagem (decisão final)

Avaliadas 4 opções:

| Opção | Descrição | Prós | Contras |
|---|---|---|---|
| A | `User.companyId` nullable | Reaproveita 100% da tabela/repositório/login existentes; e-mail continua globalmente único automaticamente | Precisa relaxar um `NOT NULL` existente; exige cuidado em todo código que hoje assume `companyId != null` |
| B | `User` associado a uma Company sentinela "platform" | Não mexe no schema (`company_id` continua `NOT NULL`) | Polui `companies` para sempre — toda listagem/contagem administrativa de empresas precisa filtrar essa linha fantasma; risco de colisão de slug; semanticamente errado (plataforma não é uma "empresa") |
| C | Entidade separada (`platform_admins`) | Separação total de conceitos | Duplica login/JWT/hash de senha; e-mail deixa de ser unicamente verificável entre as duas tabelas sem um check extra; `AuthService.login()` precisaria tentar duas tabelas ou ter endpoint próprio, quebrando a decisão de login único (§7) |
| D | A, refinado com `CHECK` constraint no banco | Mesmos prós de A, mais uma garantia de integridade que a aplicação não pode violar por acidente | Nenhum real, é estritamente melhor que A puro |

**✅ APROVADO — Opção D, final.** `User.companyId` nullable, sem company sentinela, sem entidade separada.

**Invariante final (obrigatória, dupla camada):**

```
SUPER_ADMIN → company_id IS NULL
OWNER       → company_id IS NOT NULL
```

- **Camada 1 — banco (última linha de defesa):** `CHECK` constraint na tabela `users`:
  ```sql
  ALTER TABLE users ADD CONSTRAINT chk_users_role_company_id
    CHECK (
      (role = 'SUPER_ADMIN' AND company_id IS NULL)
      OR
      (role <> 'SUPER_ADMIN' AND company_id IS NOT NULL)
    );
  ```
  Nenhuma inserção/atualização, de qualquer camada da aplicação (ou de um acesso manual ao banco), pode violar essa invariante — é a garantia final, independente de bug de aplicação.
- **Camada 2 — aplicação (validação antecipada, melhor mensagem de erro):** toda criação/atualização de `User` feita pelo `UserService`/`AuthService`/`AdminService` valida a mesma regra em memória **antes** de persistir, para falhar com uma `BusinessRuleException` (422, mensagem clara) em vez de deixar a constraint do banco estourar como um 500 genérico de `DataIntegrityViolationException`. A validação de aplicação é conveniência de DX/mensagem de erro; a garantia real é o `CHECK` do banco.

Justificativa da opção: é a mais simples e mais segura (constraint no banco, não só na aplicação), não introduz uma linha fantasma em `companies`, e mantém a tabela `users` como único ponto de autenticação — login único (§7) continua trivial.

Impacto:
- `role` (VARCHAR via `@Enumerated(STRING)`) ganha o valor `SUPER_ADMIN` — não é enum nativo do Postgres, então adicionar o valor não exige `ALTER TYPE`, só a migration da constraint.
- `status` ganha o valor `PENDING` (ver §13).
- `JwtService.generateAccessToken`: claim `companyId` passa a ser opcional (omitida/`null` quando o usuário for `SUPER_ADMIN`).
- `JwtPrincipal.companyId()` passa a `UUID` nullable.
- `UserRepository`: ganha `findByCompanyIdAndRole`/`existsByCompanyIdAndRole` (necessários para o admin API listar owners de uma empresa) e uma projeção leve de status (§13/§14) — nenhuma outra mudança estrutural.

## 6. Autorização

Regra:
- `SUPER_ADMIN`: acessa `/admin/**` (`@PreAuthorize("hasRole('SUPER_ADMIN')")` em todo `AdminController`), lista/cria/gerencia companies, nunca acessa dados operacionais de uma company (estimates, gallery, etc. — isso é do OWNER).
- `OWNER`: acessa endpoints já existentes (`@PreAuthorize("hasRole('OWNER')")`, inalterado), nunca acessa `/admin/**`.

Enforcement em duas camadas (defesa em profundidade, dado que `/admin/**` é superfície sensível e será implementado por outra pessoa/IA depois deste DT):
1. `SecurityConfig`: adicionar `.requestMatchers("/admin/**").hasRole("SUPER_ADMIN")` explícito na cadeia de filtros — protege mesmo que alguém esqueça a anotação no controller.
2. `@PreAuthorize("hasRole('SUPER_ADMIN')")` em cada método do `AdminController`, seguindo o padrão já usado em `CompanyController`.

A isso soma-se, nesta revisão, o `ActiveAccountFilter` (§13) — que roda para **qualquer** requisição autenticada, incluindo `/admin/**`, garantindo que um SUPER_ADMIN com `status != ACTIVE` também é bloqueado, não só um OWNER.

Nada disso depende do frontend — o frontend replica a regra só por UX (§21), o backend é a autoridade final, como já é hoje.

## 7. Login

Avaliadas: (A) endpoint único, (B) login admin separado no backend, (C) mesma autenticação + autorização por papel.

**Decisão: C.** Um único `POST /auth/login` no backend (sem mudança de contrato) — a distinção é só de **papel no JWT retornado** e de **rota no frontend**. O frontend expõe `/login` e `/admin/login` (duas páginas, mesmo endpoint por trás) — motivo puramente de UX/onboarding (URL dedicada para o time da plataforma), não de segurança.

Pós-login:
- `role == SUPER_ADMIN` → frontend redireciona para `/admin`.
- `role == OWNER` → frontend redireciona para `/dashboard`.

Efeito colateral necessário no backend: `AuthService.me()` hoje sempre carrega `Company` via `user.getCompanyId()` (`CompanyService.findById`) — isso quebra para um `SUPER_ADMIN` (`companyId == null`). `MeResponse` precisa de um ramo: se `role == SUPER_ADMIN`, `company/branding/settings` retornam `null` em vez de tentar carregar. O frontend usa `session.company == null` como o sinal definitivo de "esta sessão não é de um OWNER" (ver §21) — reaproveita um dado que o backend já teria que emitir corretamente, em vez de inventar outro mecanismo.

## 8. Bootstrap do primeiro SUPER_ADMIN (decisão final)

Avaliadas: env vars no startup, migration, script/CLI, endpoint temporário, seed local-only.

**✅ APROVADO — `ApplicationRunner` idempotente lido de env vars**, mesmo padrão de segredo já usado para `JWT_SECRET`/`POSTGRES_PASSWORD`:

```
PLATFORM_ADMIN_BOOTSTRAP_EMAIL=...
PLATFORM_ADMIN_BOOTSTRAP_PASSWORD=...
```

Comportamento exato — tabela de decisão completa (fail-fast em produção diante de configuração inválida, nunca um "meio-bootstrap" silencioso):

| Situação | Comportamento |
|---|---|
| Nenhuma das duas variáveis definida | No-op silencioso (log `INFO`), sobe normalmente. Válido tanto em dev (sem bootstrap) quanto em produção já bootstrapada anteriormente. |
| Somente uma definida (e-mail sem senha, ou senha sem e-mail) | **Configuração inválida → falha o startup.** O `ApplicationRunner` lança exceção (comportamento padrão do Spring Boot: falha ao subir o contexto), log `ERROR` indicando exatamente qual variável está faltando. Evita subir com bootstrap parcial. |
| Ambas definidas, e-mail já existe como `SUPER_ADMIN` | No-op idempotente — não altera a senha existente, não duplica, log `INFO` "SUPER_ADMIN já existe, bootstrap ignorado". Roda em todo restart sem efeito colateral. |
| Ambas definidas, e-mail já existe mas pertence a um usuário com outro papel (`OWNER`) | **Falha o startup.** Colisão de e-mail com uma conta `OWNER` já existente (e-mail é globalmente único, §5/§3) é um erro de configuração humano — nunca resolvido silenciosamente. Log `ERROR` explícito, sem detalhes que ajudem enumeração externa de e-mails (mensagem genérica de configuração inválida no log de aplicação, que só o operador vê). |
| Ambas definidas, e-mail livre, senha não atende à política de senha da aplicação (mesma regra de `RegisterRequest.password`: `@NotBlank @Size(min=8,max=128)`) | **Falha o startup.** Nunca cria um `SUPER_ADMIN` com senha fora da política já usada para `OWNER`. Log `ERROR` sem nunca imprimir a senha (nem em texto puro, nem mascarada — simplesmente não é logada). |
| Ambas definidas, e-mail livre, senha válida | Cria o `SUPER_ADMIN` (`companyId=null`, `status=ACTIVE`, hash BCrypt), log `INFO` confirmando criação (sem senha). |

Regras adicionais obrigatórias (todas atendidas pela tabela acima):
- Nenhuma credencial hardcoded, nenhuma senha default/fallback.
- Nunca imprimir a senha, em nenhum nível de log.
- Nunca sobrescrever a senha de um `SUPER_ADMIN` já existente.
- Não recriar/duplicar admin a cada restart (idempotência garantida por `existsByEmail`).
- Falha segura (fail-fast) diante de qualquer configuração ambígua ou inválida em vez de "ignorar e seguir".
- **Recomendação operacional (a documentar no runbook, não uma trava técnica):** depois do primeiro bootstrap bem-sucedido, `PLATFORM_ADMIN_BOOTSTRAP_EMAIL`/`PLATFORM_ADMIN_BOOTSTRAP_PASSWORD` podem ser removidas de `production.env` — o runner é um no-op inofensivo se permanecerem (idempotente), mas remover reduz a superfície de exposição de uma senha em texto puro num arquivo de configuração depois que ela deixou de ser necessária.

Não expõe endpoint HTTP nenhum para isso (fecha o vetor "criar SUPER_ADMIN via API pública").

Local: `production.env`/`.env` locais recebem as duas vars antes do primeiro `docker compose up`. Produção: mesmo mecanismo de segredo já documentado no runbook (`docs/operations/runbook.md`, tabela de secrets) — este DT deve resultar, na implementação, em uma linha nova nessa tabela (incluindo a recomendação de remoção pós-bootstrap acima).

## 9. Admin API — contrato (congelado para implementação)

Todos sob `/admin`, todos `@PreAuthorize("hasRole('SUPER_ADMIN')")`, todos sujeitos ao `ActiveAccountFilter` (§13).

### `POST /admin/companies`
Cria Company + OWNER (`PENDING`) + convite, numa única transação atômica (ver §10).

Request:
```json
{
  "companyName": "string, obrigatório, 2-100",
  "slug": "string, opcional — se omitido, gera automaticamente (reaproveita CompanyService/AuthService.generateUniqueSlug)",
  "country": "string, ISO alpha-2, obrigatório",
  "tradeName": "string, opcional",
  "ownerName": "string, obrigatório",
  "ownerEmail": "string, e-mail, obrigatório"
}
```
Response `201`:
```json
{
  "company": { "id": "uuid", "name": "...", "slug": "...", "country": "PT", "status": "ACTIVE" },
  "owner": { "id": "uuid", "email": "...", "name": "...", "status": "PENDING" },
  "invite": { "token": "raw-token-mostrado-uma-única-vez", "expiresAt": "2026-08-02T10:00:00Z" }
}
```
Erros: `422` (slug ou e-mail já em uso — `BusinessRuleException`), `400` (validação).

### `GET /admin/companies?status=&search=&page=&size=`
Lista paginada (Spring `Pageable`/`Page<CompanyAdminSummary>` — primeira paginação real do backend, convenção nova a documentar). Item: `{ id, name, slug, status, ownerEmail, createdAt }`.

### `GET /admin/companies/{id}`
```json
{
  "company": { "id","name","slug","email","country","tradeName","status","createdAt" },
  "owners": [ { "id","email","name","role","status","createdAt" } ]
}
```
`404` se não existir.

### `PATCH /admin/companies/{id}/status`
Request: `{ "status": "ACTIVE" | "INACTIVE" }`. Response `200` com a company atualizada. `404` se não existir.

### `POST /admin/companies/{companyId}/owners`
**Convida um OWNER novo** para uma empresa já existente (e-mail ainda não pode existir na plataforma). Request: `{ "ownerName", "ownerEmail" }`. Response `201` igual ao bloco `owner`+`invite` do onboarding. Erros: `404` company inexistente, `422` e-mail já em uso.

### `POST /admin/companies/{companyId}/owners/{ownerId}/invites` — **reemitir convite** (NOVO nesta revisão)
Gera um **novo** convite para um owner que ainda está `PENDING` (ex.: o link anterior expirou ou foi perdido). Revoga implicitamente qualquer convite anterior ainda válido do mesmo owner (`revoked_at = now()` no registro antigo) antes de criar o novo — nunca deixa dois convites simultaneamente válidos para o mesmo owner.

Sem corpo de request. Response `201`:
```json
{ "invite": { "token": "novo-token-mostrado-uma-única-vez", "expiresAt": "..." } }
```
Erros: `404` company/owner inexistente, `409` (`ConflictException`) se o owner **não** estiver `PENDING` (já ativou a conta — não há o que reemitir).

### `DELETE /admin/companies/{companyId}/owners/{ownerId}/invite` — **revogar convite (sem reemitir)** (NOVO nesta revisão)
Invalida o convite pendente do owner **sem** gerar um novo (`revoked_at = now()`). O owner permanece `PENDING`, mas sem nenhum token utilizável até que `POST .../invites` seja chamado depois. Usado quando um convite vazou e o operador quer cortar o acesso imediatamente, sem necessariamente já ter um novo destinatário/canal de entrega pronto.

Response `204`. Erros: `404` company/owner inexistente, `409` se o owner não estiver `PENDING` ou não houver convite ativo para revogar.

**Distinção deliberada, sem ambiguidade:**
- "Convidar um owner novo" = `POST /admin/companies/{companyId}/owners` (e-mail nunca visto antes).
- "Reemitir convite de um owner pendente existente" = `POST /admin/companies/{companyId}/owners/{ownerId}/invites` (revoga + cria).
- "Só revogar, sem reemitir" = `DELETE /admin/companies/{companyId}/owners/{ownerId}/invite`.

### `POST /auth/invites/accept` (permitAll — o convidado ainda não está autenticado)
Request: `{ "token": "...", "password": "mín. 8 chars" }`. Sucesso: `200` com `AuthResponse` (login automático após definir senha) — `status` do usuário passa `PENDING → ACTIVE`. Erros: `404` token inexistente, `422` token expirado, revogado ou já usado, `400` senha fraca.

## 10. Company onboarding — uma etapa, atômica (decisão final)

Avaliado: transação única vs. duas etapas (criar Company, depois convidar Owner separadamente).

**✅ APROVADO — uma única operação transacional.** `POST /admin/companies` cria Company + Branding/Settings default + User `PENDING` + convite dentro de **uma única transação Spring (`@Transactional`)** — tudo ou nada. Se qualquer parte falhar (ex.: violação de unicidade de slug, e-mail já em uso, erro ao gerar o convite), a transação inteira é revertida e **nenhuma** das duas entidades (Company nem User) permanece criada — não existe estado intermediário "Company existe mas sem OWNER" nem "OWNER existe mas Company não". Isso replica exatamente o padrão já existente em `AuthService.register()` (que já faz isso para o fluxo de autoatendimento).

O OWNER nasce em `status = PENDING` — o estado correto para "aguardando definição de senha via convite" (não `ACTIVE`, já que ele não pode logar até aceitar o convite; ver §13).

Convidar um **segundo** owner numa empresa já existente é a operação separada (`POST /admin/companies/{id}/owners`), naturalmente — porque aí a Company já existe e não há nada a criar/reverter em conjunto com ela.

Campos obrigatórios no onboarding: `companyName`, `country`, `ownerName`, `ownerEmail` (`slug` auto-gerado se omitido, como já acontece hoje). Branding/Settings usam os mesmos defaults hardcoded que `AuthService.register()` já usa — **não** exigir configuração de marca no onboarding, como pedido.

## 11. Senha do Owner / convite

Avaliado: (A) senha temporária definida pelo admin, (B) token de convite, (C) reset-password token, (D) outra.

**Decisão: B — convite com token opaque, aceito via `/auth/invites/accept`.** Owner nunca recebe uma senha definida por terceiros (evita "senha temporária compartilhada por canal inseguro" e evita ter que forçar troca no primeiro login). Sem serviço de e-mail: o **mecanismo de token** é entregue nesta sprint; a **entrega por e-mail** é explicitamente fora de escopo — o token é retornado no corpo da resposta do `POST /admin/companies`, `POST .../owners` ou `POST .../owners/{ownerId}/invites` (reemissão) para cópia manual (Slack/WhatsApp/etc. pelo operador humano), nunca reexibido depois. "Reenviar convite" (§9) significa sempre revogar o anterior + gerar um novo — nunca existe reenvio automático por e-mail nesta sprint.

## 12. Invite token — desenho (atualizado: revogação)

Tabela `owner_invites`, seguindo o precedente já existente de `estimate_shares` (`V10`, que já hasheia tokens públicos revogáveis):

```
owner_invites
  id            UUID PK
  user_id       UUID FK -> users(id), NOT NULL
  token_hash    VARCHAR(255) UNIQUE NOT NULL   -- SHA-256 do token bruto, nunca plaintext
  expires_at    TIMESTAMP NOT NULL              -- created_at + 7 dias (default)
  used_at       TIMESTAMP NULL                  -- marca uso único (aceito com sucesso)
  revoked_at    TIMESTAMP NULL                  -- NOVO: marca revogação administrativa (sem uso)
  created_by    UUID FK -> users(id) NULL        -- SUPER_ADMIN que criou o convite
  created_at    TIMESTAMP NOT NULL
```

Regras:
- Token bruto gerado com `SecureRandom` (mesmo nível dos refresh tokens atuais), só o hash é persistido.
- Expiração: 7 dias a partir da criação (constante/configurável, sem endpoint de configuração nesta sprint). Reemitir (§9) sempre gera uma expiração nova de 7 dias a partir do momento da reemissão — não herda o prazo do convite anterior.
- **Validade de um convite** (checada em `accept`, e implicitamente nas novas operações de reemissão/revogação): `used_at IS NULL AND revoked_at IS NULL AND expires_at > now()`. Falhar qualquer uma dessas condições → `422` em `accept`.
- Uso único: `accept` bem-sucedido seta `used_at = now()` na mesma transação que ativa o usuário (`PENDING → ACTIVE`) — impede replay.
- Revogação administrativa (NOVO): `DELETE .../invite` e a etapa implícita de `POST .../invites` (reemissão) setam `revoked_at = now()` no convite anterior ainda válido — nunca mais aceitável após isso, mesmo que ainda não tivesse expirado.
- No máximo um convite **válido** (não usado, não revogado, não expirado) por owner em um dado momento — reemitir sempre revoga o anterior antes de criar o novo, garantindo essa invariante sem precisar de constraint adicional no banco (é imposta na lógica do `InviteService`, dado que a operação é sempre "revogar todos os válidos deste user\_id, depois inserir um novo").
- Sem e-mail em lugar nenhum do token/hash em log.

## 13. Status — Company e User — e enforcement em tempo real (revisado)

**Company**: mantém `ACTIVE, INACTIVE` (nenhum valor novo necessário).

**User**: ganha `PENDING` — `ACTIVE, INACTIVE, PENDING`. `PENDING` = convidado, ainda sem senha definida; não pode logar (mapeado para `DisabledException → 401 "Account Disabled"`, igual a `INACTIVE`).

### Regra de autorização em tempo real (NOVA — substitui a aceitação de risco da versão anterior)

Requisito aprovado: **um access token JWT criptograficamente válido não é suficiente para autorizar uma operação.** A regra de autorização completa passa a ser:

```
OWNER
  + JWT válido
  + User.status == ACTIVE
  + Company.status == ACTIVE
    → operação autorizável

SUPER_ADMIN
  + JWT válido
  + User.status == ACTIVE
  + companyId == null
    → segue para autorização administrativa

Qualquer outro caso (User != ACTIVE, ou OWNER com Company != ACTIVE)
    → negar (401 "Account Disabled")
```

Isto vale para **qualquer requisição autenticada normal** — não somente para emissão (`login`) ou renovação (`refresh`) de token, que é o que a versão anterior deste DT cobria.

**Onde a validação acontece — mecanismo centralizado, proporcional à arquitetura Spring Security existente:**

Um novo filtro de servlet, **`ActiveAccountFilter`**, registrado na cadeia de filtros logo **depois** do `JwtAuthenticationFilter` existente (mesma posição relativa, antes do `UsernamePasswordAuthenticationFilter`). Responsabilidade única: depois que o `JwtAuthenticationFilter` já validou a assinatura do JWT e montou o `JwtPrincipal` no `SecurityContext` (continua fazendo isso sem lookup ao banco, como hoje), o `ActiveAccountFilter`:

1. Se não há `Authentication` no `SecurityContext` (rota pública) → segue sem checar nada.
2. Se há `JwtPrincipal` → executa **uma única consulta leve** (projeção JPA, não hidrata as entidades completas): `UserRepository.findActivityStatus(UUID userId)`, um `LEFT JOIN` indexado entre `users` e `companies` retornando só `{status, companyStatus}` (`companyStatus` vem `null` para `SUPER_ADMIN`, que não tem `companyId`).
3. Se o usuário não existir mais (deletado após o token ter sido emitido) → 401.
4. Se `status != ACTIVE` → 401 `"Account Disabled"`.
5. Se o papel não é `SUPER_ADMIN` e `companyStatus != ACTIVE` → 401 `"Account Disabled"`.
6. Caso contrário → segue a cadeia normalmente até o `@PreAuthorize`/controller.

A exceção lançada (`DisabledException`, já existente e já mapeada) é tratada pelo mesmo mecanismo de entry point de autenticação que a cadeia de filtros já usa hoje para falhas do `JwtAuthenticationFilter` (produzindo o mesmo formato `ProblemDetail` 401 que o restante da API já usa) — a implementação deve reaproveitar esse componente já existente, não inventar um novo formato de resposta.

**Por que um filtro central, e não `if (company.isActive())` espalhado:** um único ponto de enforcement, testável isoladamente, que nenhum controller/service precisa lembrar de chamar — exatamente o pedido explícito de não espalhar a checagem manualmente por todos os controllers. `/auth/login` e `/auth/refresh` continuam com suas próprias checagens explícitas (já desenhadas abaixo), porque ocorrem **antes** de existir um `JwtPrincipal` autenticado na cadeia (login ainda não tem token; refresh usa um token opaco à parte, não um Bearer JWT) — o filtro central cobre exatamente o que essas duas rotas não cobrem: toda chamada subsequente feita com um access token já emitido.

Efeito nos três pontos identificados na inspeção original (agora todos fechados, não só o quarto):
- **Login** (`AuthService.login`): mantém a checagem pós-autenticação existente (`company.status == INACTIVE` → `DisabledException`), redundante com o filtro só porque login não passa pelo filtro (não há token ainda nesse momento).
- **Refresh** (`AuthService.refresh`): mantém a checagem explícita equivalente, pelo mesmo motivo (token opaco, não passa pelo `JwtAuthenticationFilter`/`ActiveAccountFilter`).
- **APIs autenticadas "normais"**: agora cobertas pelo `ActiveAccountFilter` — um access token de 15 minutos emitido antes da desativação **deixa de funcionar imediatamente na próxima requisição** após a empresa/usuário ser desativado, não apenas na expiração natural do token. Isto substitui e fecha o risco antes aceito ("janela de até 15 minutos") — ver §35.
- **Landing pública**: `CompanyService.getPublicSite()` passa a checar `status == ACTIVE`, senão lança `ResourceNotFoundException` (404, igual a slug inexistente — não vazar que a empresa existe mas está desativada). Este caminho não passa pelo `ActiveAccountFilter` (é público, sem JWT) — por isso continua sendo uma checagem própria dentro de `CompanyService`, não do filtro.

## 14. JWT não é estado atual (documentação explícita)

As claims do JWT (`role`, `companyId`) **ajudam na autenticação e no contexto da requisição** (identificam quem está falando e evitam um lookup para montar o principal), mas **não são, e nunca foram tratadas nesta sprint como, a fonte de verdade sobre se o usuário ou a empresa continuam ativos**. Uma `Company` pode ser desativada a qualquer momento depois que um access token já foi emitido para um dos seus usuários — o JWT em si não tem como saber disso, é só uma assinatura sobre um snapshot do passado.

A estratégia escolhida (§13, `ActiveAccountFilter`) garante revogação operacional efetiva durante a validade desse token fazendo **uma consulta leve por requisição autenticada** — não uma consulta por token (o token continua sendo validado por assinatura, sem lookup), mas uma consulta de status por request, que é o ponto onde a decisão de autorização de fato acontece. Isso é uma mudança deliberada em relação ao comentário original do `JwtAuthenticationFilter` ("evita lookup ao banco por request") — aquele comentário permanece verdadeiro para a **autenticação** (montagem do principal), mas deixa de ser verdadeiro para a **autorização de estado** (ACTIVE/INACTIVE), que agora é checada a cada request.

**Não é adicionado Redis, cache distribuído ou sessão distribuída nesta sprint** — a consulta é uma única leitura indexada (`user_id` PK + `company_id` FK, ambos indexados hoje), proporcional ao volume atual do projeto. Se o custo se tornar relevante em escala futura, cache com invalidação ativa (ex.: invalidar no exato momento de `PATCH .../status`) é a evolução natural — não necessária nesta sprint, e explicitamente fora de escopo agora.

## 16. Resolução de tenant — mecanismo técnico

Fonte do tenant no request: **Host header**, resolvido no backend (não no frontend), por um motivo direto: se o frontend tentasse extrair o slug fazendo `host.split('.')[0]`, ele precisaria conhecer o domínio-base da plataforma e, pior, não teria como lidar com domínio customizado (`jrpinturas.pt` não tem um "subdomínio" para extrair) — centralizar a resolução no backend deixa o frontend agnóstico a essa lógica, hoje e quando domínio customizado existir.

Novo endpoint público:
```
GET /public/tenant?host={host}
```
- `{host}` é o valor do header `Host` **tal como o Server Component do Next.js o recebeu** (com porta, se houver — por isso vai como query param, não path param, evitando problemas de escaping do `:`), repassado nesta chamada servidor-a-servidor. Ver §17 para a análise completa de confiança sobre esse valor.
- Lógica no backend (nova propriedade `app.platform.base-domain`, ex.: `localhost` em dev, `plataforma.com` em produção):
  1. Remove a porta de `host`, se presente.
  2. Se `host` termina exatamente em `.{baseDomain}` → extrai o primeiro rótulo como slug candidato, confirma que existe uma Company com esse slug.
  3. Senão (domínio customizado) → **não implementado nesta sprint** (ver §17) → segue para o passo 4.
  4. Se nada resolveu e `PLATFORM_DEFAULT_TENANT_SLUG` estiver configurado → retorna esse slug como fallback (ver §22 — necessário para não quebrar a JR Pinturas em produção antes de existir DNS real).
  5. Senão → `404`.
- Resposta: `200 { "slug": "jr-pinturas" }` ou `404`.
- **Não** verifica `status` aqui (isso é responsabilidade de `getPublicSite`, §13) — uma pequena informação ("este slug existe") pode vazar mesmo para empresa inativa; aceito como risco menor (slug já é público por natureza, é o que aparece na URL).

O `(public)/page.tsx` do frontend passa a: ler `headers().get('host')` (Next 15, `next/headers`, Server Component), chamar `GET /public/tenant?host=...`, obter o slug, e então chamar `fetchPublicSite(slug)` **exatamente como já faz hoje** — nenhuma mudança na camada de dados existente (`public-site-api.ts`, hooks), só a origem do slug muda.

## 17. Host / proxy — segurança da resolução de tenant

Reforço explícito pedido: qual informação é autoridade para a resolução de tenant, e por que `X-Forwarded-Host` nunca deve ser essa autoridade sem uma cadeia de proxy confiável validada.

**O que é autoridade hoje:** o header `Host` **exatamente como recebido pelo processo Next.js** (via `next/headers`), que por sua vez é o que o **Caddy** encaminhou para `frontend:3000`. Confirmado na inspeção (`infra/caddy/Caddyfile`): o `reverse_proxy` do Caddy repassa o `Host` recebido do cliente **sem reescrevê-lo** — comportamento padrão do Caddy (diferente de alguns outros proxies que substituem o `Host` pelo hostname do upstream). Isso significa que, na topologia atual (`Internet → Caddy → Next.js`), o valor que o `(public)/page.tsx` lê em `headers().get('host')` é fielmente o que o cliente HTTP enviou.

**O que explicitamente NÃO é usado como autoridade:** `X-Forwarded-Host` (ou qualquer header `X-Forwarded-*`) não é lido em nenhum lugar deste desenho. Só o `Host` de conexão é usado. Isso é deliberado — `X-Forwarded-Host` é tipicamente definido por quem está do lado do **cliente** de um proxy (ou seja, pode ser forjado por qualquer requisição HTTP direta que não passe por um proxy confiável intermediário), enquanto o `Host` de conexão que o Caddy encaminha é o que efetivamente chegou pela conexão TCP/TLS estabelecida — não pode ser adulterado por um header adicional arbitrário.

**Severidade real do "tenant spoofing" nesta arquitetura:** o `Host` só influencia **qual site público (já público, somente leitura) é renderizado** — nunca influencia autenticação/autorização de `/dashboard` ou `/admin`, que dependem inteiramente do JWT Bearer, independente de qualquer header de host. Ou seja, o pior cenário de um `Host` forjado é "ver a landing pública de outra empresa que também já é pública por natureza" — não há vazamento de dado privado nem escalonamento de privilégio possível por esse vetor. Ainda assim, o desenho evita ampliar essa superfície desnecessariamente (não introduzindo `X-Forwarded-Host` como fonte adicional).

**Lacuna hoje, aceita e documentada:** com o bloco de site atual do Caddy (`{$CADDY_HOST}` = `:80`, "qualquer host nesta porta"), o Caddy **não valida** o `Host` contra uma lista de domínios conhecidos antes de encaminhar — qualquer valor de `Host` chega ao frontend. Isso é aceitável hoje porque (a) o único efeito é mostrar uma landing pública de tenant errado para quem manda um `Host` arbitrário via um cliente HTTP direto (não um navegador normal, que sempre usa o domínio real digitado/clicado), e (b) sem DNS real, a maior parte do tráfego cai no fallback `PLATFORM_DEFAULT_TENANT_SLUG` de qualquer forma (§22). Esta lacuna se fecha **naturalmente** na Sprint 11C: quando existirem blocos de site reais no Caddy por domínio (`jr-pinturas.plataforma.com { ... }` ou um bloco wildcard `*.plataforma.com`), o próprio Caddy passa a rejeitar/não casar requisições cujo `Host` não corresponda a nenhum domínio configurado — fechando a lacuna na borda, antes mesmo de chegar ao Next.js.

**Ambiente de desenvolvimento local:** sem proxy no caminho (`next dev` recebe a conexão diretamente do navegador/Playwright) — mesmo modelo de confiança, sem diferença relevante: o `Host` é o que o cliente HTTP conectado enviou, exatamente como em produção.

**Impacto futuro do Cloudflare (documentado, não implementado):** na topologia futura `Internet → Cloudflare → Caddy → Spring`, duas proteções adicionais chegam "de graça": (1) Cloudflare só encaminha tráfego para hostnames configurados na zona DNS daquele domínio — um `Host` fora dessa lista nem chega ao Caddy; (2) o Caddy deve configurar `trusted_proxies` com os intervalos de IP reais do Cloudflare, para poder confiar em headers como `CF-Connecting-IP` para logging/rate-limiting — mas isso não muda a fonte de verdade para tenant resolution, que continua sendo o `Host` de conexão (agora validado tanto pela zona do Cloudflare quanto pelos blocos de site do Caddy). Nada disso é implementado nesta sprint; fica registrado como escopo da Sprint 11C, junto com o restante do trabalho de domínio/TLS.

## 24. Backward compatibility — JR Pinturas

A empresa e o owner existentes hoje (`role=OWNER`, `companyId` preenchido, `status=ACTIVE`) já satisfazem a nova `CHECK` constraint (`role <> 'SUPER_ADMIN' AND company_id IS NOT NULL`) sem qualquer backfill.

**Ponto crítico identificado nesta inspeção:** a produção real hoje só tem `CADDY_HOST=:80` (sem domínio, sem wildcard — confirmado lendo `infra/caddy/Caddyfile`, um único bloco de site). Isso significa que, **até a Sprint 11C entregar domínio real**, o header `Host` recebido em produção não vai bater com nenhum padrão de subdomínio — a resolução por Host, sozinha, quebraria o acesso à JR Pinturas em produção hoje. É exatamente para isso que existe o fallback `PLATFORM_DEFAULT_TENANT_SLUG` (§16/§22 — mecanismo temporário, ver decisão final abaixo): configurado como `jr-pinturas` em produção, mantém o comportamento atual (mono-tenant efetivo) até que 11C ative subdomínios reais — a funcionalidade fica **pronta mas latente** em produção, plenamente exercitável em local/E2E via `*.localhost`.

**✅ Decisão final sobre `PLATFORM_DEFAULT_TENANT_SLUG`:** aprovado como **mecanismo de transição explícito, não como arquitetura multi-tenant definitiva**. Regra final:

```
Host resolvível (subdomínio bate com app.platform.base-domain)
    → tenant correspondente

Host não resolvível + PLATFORM_DEFAULT_TENANT_SLUG configurado
    → tenant default

Host não resolvível + variável ausente
    → 404
```

Depois que a Sprint 11C entregar domínio/subdomínios reais e o Caddy passar a ter blocos de site por domínio, `PLATFORM_DEFAULT_TENANT_SLUG` deixa de ser necessária e pode ser removida de `production.env` — este DT registra isso como o critério de desativação da variável, não como algo a ser feito nesta sprint.

## 25. Destino de `NEXT_PUBLIC_COMPANY_SLUG` e critério de imagem genérica (reforçado)

Deixa de ser uma dependência funcional de build. Não é removido de imediato de todo lugar por segurança de transição, mas:
- Sai do `frontend/Dockerfile` como `ARG`/`ENV` obrigatório (a imagem publicada deixa de ser rotulada por tenant).
- Sai da exigência (`:?...is required`) em `docker-compose.prod.yml`.
- `production.env.example` remove a linha ou a marca claramente como legado/opcional.
- `.github/workflows/publish-images.yml` remove a validação obrigatória dessa variável e o label OCI `io.chicaodw.tenant`.

**Critério de aceite reforçado — "não basta remover a variável, é preciso provar que o tenant não está baked-in por outro mecanismo":**
1. Build único da imagem frontend (`docker build`, um único digest).
2. `docker inspect` da imagem: confirmar que **nenhuma** `ENV`/label remanescente referencia um slug de tenant específico (nem `NEXT_PUBLIC_COMPANY_SLUG`, nem `io.chicaodw.tenant`).
3. Subir **dois containers a partir do mesmo digest** (ou um container recebendo requisições com dois `Host` diferentes — ambos os modos válidos), sem nenhuma variável de ambiente de tenant diferente entre eles, só `Host` diferente na requisição (`tenant-a.*` vs `tenant-b.*`).
4. Confirmar que cada um renderiza a empresa correta correspondente ao `Host` recebido, sem rebuild, sem restart entre as duas requisições.
5. Confirmar que a rota pública (`dynamic = "force-dynamic"`, já assim hoje — §3) não está cacheando estaticamente o resultado por build, o que esconderia uma dependência residual de tenant fixo atrás de um cache de página.

Este é o critério de aceite formal do §34 ("mesma imagem/digest serve dois tenants") — a prova é o passo 3+4 acima, executável via E2E (`tenant-runtime.spec.ts`, §30) ou manualmente antes do go-live.

## 26. GHCR — critério de aceite

Após esta sprint, a mesma imagem/digest publicado por `publish-images.yml` deve servir qualquer tenant cujo Host resolva corretamente — nenhum novo cliente exige nova imagem. `frontend-ci.yml` (linha 23, hoje `NEXT_PUBLIC_COMPANY_SLUG: jr-pinturas` hardcoded para build/lint/test) deixa de precisar dessa variável.

## 27. Caddy/Cloudflare — impacto futuro (documentado, não implementado)

Wildcard de subdomínio exige um bloco `*.{domínio}` no Caddyfile e certificado TLS wildcard — que só pode ser emitido via desafio DNS-01 (não HTTP-01), ou seja, exige um provedor de DNS programável (ex.: módulo Cloudflare do Caddy) — uma dependência mais pesada que o ACME HTTP-01 simples usado hoje. Domínio customizado por cliente (`jrpinturas.pt`) exigiria TLS "on-demand" do Caddy, com seu próprio endpoint de permissão anti-abuso. Quando o Cloudflare entrar na topologia, o Caddy precisará de `trusted_proxies` configurado para os intervalos de IP do Cloudflare (§17) — sem isso, dados de conexão (IP real do cliente) ficam incorretos para logging/rate-limiting, embora isso não afete a resolução de tenant em si (que depende do `Host`, não de `X-Forwarded-*`). Nada disso é implementado nesta sprint — fica registrado como escopo da Sprint 11C.

## 28. Segurança

- **Escalonamento de privilégio**: nenhum DTO de criação/atualização aceita `role` vindo do cliente para si mesmo — autorregistro sempre gera `OWNER`; criação administrativa de owner sempre gera `OWNER`; `SUPER_ADMIN` só existe via bootstrap por env var (§8). Nenhuma rota de "trocar meu próprio papel" existe ou deve existir.
- **IDOR**: endpoints `/admin/**` operam deliberadamente entre empresas (esse é o objetivo) — não há verificação de `companyId` do principal para eles, por design; `{id}` inexistente → 404 padrão.
- **Cross-tenant**: superfície OWNER existente não muda; `TenantIsolationIntegrationTest` deve continuar verde após a migration.
- **Exposição do admin**: `/admin/**` fora do `permitAll`, gate triplo agora (`SecurityConfig` + `@PreAuthorize` + `ActiveAccountFilter`, §6/§13). Rate limiting em `/auth/login` (usado também por `/admin/login`) permanece item de backlog já conhecido (roadmap), não introduzido nem resolvido aqui.
- **Token de convite**: hash SHA-256 em repouso (nunca plaintext), uso único, expira em 7 dias, revogável administrativamente (`revoked_at`, §12), entregue só uma vez na resposta HTTP — nunca em log. Reemissão sempre revoga o anterior antes de criar o novo, nunca deixando dois convites válidos simultaneamente para o mesmo owner.
- **Empresa/usuário desativado, incluindo tokens já emitidos**: fechado pelo `ActiveAccountFilter` (§13/§14) — não há mais uma janela de até 15 minutos de acesso residual; a próxima requisição autenticada após a desativação já é rejeitada. Site público 404 (`getPublicSite`, checagem própria por ser rota pública sem JWT).
- **JWT**: claim `companyId` nullable tratada explicitamente (sem NPE) — coberto em `JwtServiceTest` (§29). O JWT nunca é tratado como fonte de verdade sobre status (§14).
- **Resolução de tenant / Host spoofing**: análise completa no §17 — só `Host` de conexão é usado (nunca `X-Forwarded-Host`), impacto limitado a conteúdo público já-público (landing page), sem escalonamento de privilégio possível por esse vetor; lacuna de validação de domínio na borda (Caddy) é aceita nesta sprint e fechada naturalmente na 11C.
- **Força bruta**: sem mudança de escopo — mesma superfície e mesma pendência de backlog de antes.

## 34. Critérios de aceite

- `SUPER_ADMIN` existe (via bootstrap) e nunca é confundido com `OWNER` (papéis distintos, `companyId` nulo garante isso estruturalmente, com `CHECK` constraint no banco como última linha de defesa).
- `OWNER` nunca acessa `/admin/**` (403 no backend, redirecionado no frontend).
- `SUPER_ADMIN` cria/lista/ativa/desativa companies via `/admin/**`.
- Onboarding cria Company + OWNER `PENDING` numa transação atômica (tudo ou nada); OWNER define a própria senha via convite (nunca recebe senha definida por terceiros).
- Convite pendente pode ser reemitido (revoga o anterior + gera novo) ou revogado sem reemissão, via os dois endpoints dedicados (§9).
- Company `INACTIVE` ou User não-`ACTIVE` bloqueiam **imediatamente** qualquer operação autenticada do OWNER — inclusive com um access token já emitido e ainda dentro do seu TTL — via `ActiveAccountFilter`; login/refresh também bloqueados; site público 404.
- Tenant A nunca acessa dados de Tenant B (regressão coberta por `TenantIsolationIntegrationTest`).
- Landing pública resolve o tenant em runtime via `Host` (com fallback documentado, `PLATFORM_DEFAULT_TENANT_SLUG`, explicitamente temporário até a Sprint 11C).
- `NEXT_PUBLIC_COMPANY_SLUG` deixa de ser exigido no build da imagem frontend, e nenhum outro mecanismo (label, cache estático, ARG residual) mantém um tenant baked-in — verificado pelo procedimento do §25.
- Uma mesma imagem/digest de frontend serve pelo menos dois tenants diferentes, comprovado por E2E, sem rebuild.
- JR Pinturas continua funcionando (login, dashboard, site público) sem nenhuma migração de dados manual.
- Testes de backend, frontend e E2E listados em §29/§30 passam.

## 35. Riscos

- Resolução de tenant por Host só é plenamente exercitável em produção depois que a Sprint 11C entregar domínio/subdomínio real — até lá, depende do fallback `PLATFORM_DEFAULT_TENANT_SLUG` (mitigação já desenhada, mecanismo de transição explícito, não um risco não-tratado).
- Ausência de e-mail transacional torna a entrega do convite (inicial e reemitido) manual — aceito, fora de escopo por decisão explícita do usuário.
- ~~Token de acesso (JWT) de 15 min continua válido por até 15 min após desativar uma empresa~~ — **fechado nesta revisão** pelo `ActiveAccountFilter` (§13/§14): a próxima requisição autenticada já é rejeitada, não há mais janela de 15 minutos de acesso residual.
- **Novo (aceito, proporcional):** o `ActiveAccountFilter` adiciona uma consulta leve (projeção indexada `user_id`/`company_id`) a **toda** requisição autenticada — um custo de desempenho deliberado, aceito no volume atual do projeto, sem cache/Redis por instrução explícita. Se o volume crescer a ponto de importar, a evolução natural é um cache com invalidação ativa no momento de `PATCH .../status` — não necessário agora.
- `getPublicSite` sem checagem de status era uma correção obrigatória desta sprint — fechada (§13).
- E-mail globalmente único na tabela `users` significa que um SUPER_ADMIN não pode compartilhar e-mail com nenhum OWNER existente — aceitável dado o volume baixo e gerenciado manualmente de contas de plataforma (também é a regra que faz o bootstrap falhar com segurança nesse caso, §8).
- Lacuna de validação de `Host` na borda (Caddy não valida domínio hoje, §17) — severidade baixa (só afeta qual conteúdo público é mostrado), fechada naturalmente pela Sprint 11C.

## 36. Decisões humanas — resolvidas

As 8 decisões abertas na versão anterior deste DT foram todas resolvidas e aprovadas:

1. **Modelagem de SUPER_ADMIN** = Opção D (`companyId` nullable + `CHECK` constraint no banco como última linha de defesa, validação de aplicação como segunda camada) — §5.
2. **Onboarding** = Company+Owner numa única transação atômica (tudo ou nada) — §10.
3. **Convites** = tabela dedicada `owner_invites`, token hasheado, uso único, expiração de 7 dias, entrega manual — **com** reemissão (`POST .../invites`) e revogação (`DELETE .../invite`) dedicadas, semântica sem ambiguidade em relação a "convidar owner novo" — §9/§12.
4. **Tenant resolution** = Host header + `GET /public/tenant`, path-based (`/t/{slug}`) descartado como arquitetura principal — §16.
5. **`PLATFORM_DEFAULT_TENANT_SLUG`** = aprovado como mecanismo de transição explícito, não definitivo, removível quando 11C entregar DNS real — §24.
6. **`company_domains`** = não criado nesta sprint, só documentado como evolução futura — §18.
7. **`/admin/users`** = não incluído nesta sprint; gestão de owners só dentro de `/admin/companies/{id}` — §23.
8. **Bootstrap** = `ApplicationRunner` idempotente + env vars, com tabela de comportamento completa (fail-fast em configuração inválida) — §8.

Além disso, três reforços de segurança/arquitetura pedidos foram incorporados como regras obrigatórias do desenho, não como pendências: enforcement centralizado de `Company`/`User` inativos via `ActiveAccountFilter` mesmo para tokens já emitidos (§13), documentação explícita de que o JWT não é fonte de estado atual (§14), e análise de segurança de `Host`/`X-Forwarded-Host`/proxy (§17).

**Nenhuma decisão humana adicional está pendente para a implementação prosseguir.** Todos os pontos levantados nesta rodada foram resolvidos tecnicamente dentro deste DT. Itens que permanecem como trabalho futuro (Sprint 11B/11C: domínio real, `company_domains`, Cloudflare, TLS) já estavam identificados como tal e não bloqueiam o início da implementação desta sprint.
