## 2. Contexto

Depois da 11A.2, o stack sobe com `docker compose up` e fica assim:

```
host:${BACKEND_PORT:-8080}  ──▶ backend   (Spring Boot, profile prod)
host:${FRONTEND_HOST_PORT:-3000} ──▶ frontend  (Next.js standalone)
                                postgres  (sem porta publicada, só rede interna)
```

`backend` e `frontend` publicam porta diretamente no host — decisão **explicitamente
temporária** desde a 11A.1, mantida propositalmente até agora só para permitir
validação local ponta a ponta sem depender de um proxy que ainda não existia. Isso
nunca foi o desenho final: significa que qualquer processo que alcance a VPS na porta
8080 fala HTTP puro diretamente com o Spring Boot, e na porta 3000/3001 diretamente
com o Next.js — sem TLS, sem um único ponto de auditoria/rate-limit, e com dois
serviços internos (pensados para conversar só entre si e com o Postgres) tratados como
se fossem a borda pública da aplicação.

**Por que isso não deve continuar:** frontend e backend foram construídos assumindo
que algo na frente resolve TLS, agrega logs de acesso, e decide o que é público. Hoje
esse "algo" não existe — a porta 8080 e a porta 3000 *são* a borda pública, por
enquanto. Continuar assim em produção real significaria: sem HTTPS (credenciais e
tokens JWT trafegando em claro), sem certificado, dois domínios/portas diferentes
para o operador lembrar, e o Actuator/Swagger do backend diretamente alcançável de
qualquer lugar que alcance a porta 8080.

**Papel do Caddy nesta sprint:** tornar-se o único processo que aceita conexões
HTTP/HTTPS vindas de fora do host, decidir para qual dos dois serviços internos
(`frontend`/`backend`) cada requisição vai, e — mais adiante, quando um domínio real
existir — provisionar e renovar certificados TLS automaticamente. Nesta sprint o Caddy
**passa a existir e a rotear corretamente**; ele **não** passa a servir HTTPS real
(não há domínio, não há Cloudflare, não há VPS) — isso é validado com HTTP puro em
`:80` localmente, com a mesma configuração pronta para virar HTTPS automático assim
que um domínio real for apontado (Sprint 11B+).

**Relação com VPS/Cloudflare/HTTPS futuro:** a arquitetura alvo do projeto é
`Cloudflare → Hetzner VPS → Caddy → {Next.js, Spring Boot} → PostgreSQL`. Nenhuma
peça de Cloudflare ou da VPS é tocada aqui — o Caddy é desenhado para que, quando
essas peças existirem, a única mudança operacional seja apontar `CADDY_HOST` para o
domínio real (ver §8); nenhuma reestruturação de rotas ou do Compose deve ser
necessária nesse momento.

## 3. Objetivos

1. Introduzir um serviço `caddy` no `docker-compose.prod.yml` como único ponto de
   entrada HTTP(S) do stack.
2. Rotear `/` para o frontend e `/api/*` (com strip do prefixo) para o backend,
   preservando os contratos de rota atuais do Spring sem exigir renomear nenhum
   controller.
3. Rotear `/uploads/*` para o backend (logos/galeria), sem strip de prefixo.
4. Remover a publicação direta de porta do `frontend` e do `backend` no host —
   somente o Caddy publica porta.
5. Manter o PostgreSQL exclusivamente na rede interna (inalterado desde a 11A.1).
6. Definir uma estratégia de endereço/host parametrizável que funcione com HTTP puro
   localmente (sem ACME) e migre para HTTPS automático com um domínio real, sem
   reescrever o Caddyfile.
7. Decidir a fronteira de responsabilidade de headers de segurança e compressão entre
   Next.js, Spring Boot e Caddy, evitando duplicação/conflito.
8. Definir persistência (`/data`, `/config`), healthcheck e logging do Caddy.
9. Revisar `APP_CORS_ALLOWED_ORIGINS` à luz do same-origin, sem enfraquecer a
   configuração existente.
10. Produzir uma matriz de variáveis novas/alteradas e um plano de implementação e
    testes executável.

## 4. Não Objetivos

- Cloudflare, DNS real, compra/configuração de domínio.
- Provisionamento da VPS Hetzner, Terraform.
- GHCR, pipeline de publicação de imagens, deploy remoto.
- Backup, Restic, Storage Box.
- Observabilidade completa (Grafana/Prometheus/Loki) — só logging básico via Docker.
- Autenticação nova, migração do JWT/refresh token para cookie `HttpOnly`.
- Qualquer mudança funcional de produto.
- Implementação de código/config nesta tarefa — Caddyfile, Compose, Dockerfiles,
  frontend, backend e `.env` **não são alterados aqui**, só desenhados.

## 6. Arquitetura Proposta

```
                         internet (ou host local)
                                  │
                                  ▼
                    ┌─────────────────────────┐
                    │          caddy           │  único serviço publicando porta
                    │   :${CADDY_HTTP_PORT}    │  (80 local / 80+443 produção)
                    └────────────┬─────────────┘
                                 │  rede "internal" (Docker bridge)
                 ┌───────────────┼────────────────────┐
                 │               │                     │
                 ▼               ▼                     ▼
     "/"  ──▶ frontend:3000   "/api/*" (strip) ──▶ backend:8080   "/uploads/*" ──▶ backend:8080
                                                         │
                                                         ▼
                                                    postgres:5432
                                              (somente rede interna,
                                               inalterado desde 11A.1)
```

- **Único ponto de entrada:** `caddy`. `frontend` e `backend` deixam de ter qualquer
  `ports:` no Compose — só `expose` (documentação de intenção, sem publicar no host)
  ou nem isso, já que a rede Docker já torna o serviço alcançável por nome para
  qualquer outro container na mesma rede sem precisar de `expose`.
- **PostgreSQL:** inalterado — nunca teve porta publicada, nunca é alcançado pelo
  Caddy (só o backend fala com ele).
- **Portas publicadas no host:** só `${CADDY_HTTP_PORT:-80}` (e, quando HTTPS real
  existir, `${CADDY_HTTPS_PORT:-443}`) — ver §8 e §13.

## 7. Estratégia de Roteamento

| Padrão | Destino | Strip de prefixo? | Justificativa |
|---|---|---|---|
| `/api/*` | `backend:8080` | **Sim** — Caddy remove `/api` antes de repassar | Nenhum controller do Spring tem prefixo `/api` hoje (ver §5.2). Fazer o strip no Caddy é a única forma de expor `https://dominio.tld/api/...` (padrão pré-aprovado) **sem renomear nenhuma rota do backend**. |
| `/uploads/*` | `backend:8080` | **Não** | A rota real do backend já é `/uploads/**` (resource handler + matcher de segurança). `resolveAdminAssetUrl`/`resolvePublicAssetUrl` no frontend já constroem exatamente esse path a partir do valor devolvido pela API — nenhuma mudança de código necessária aqui, só a regra de Caddy. |
| `/` (catch-all) | `frontend:3000` | — | Tudo que não bate nos dois padrões acima — inclui `/dashboard/**`, `/login`, `/share/[token]`, `/_next/*` (servidos pelo próprio processo Next.js standalone), `/api/health` do frontend (ver nota abaixo), e o 404 nativo do Next.js (`not-found.tsx`, já existente) para qualquer rota desconhecida. | Simplicidade: um único `handle` final cobre a app inteira sem listar cada rota do Next.js manualmente. |

**Nota sobre `/api/health` do frontend vs. `/api/*` do backend:** isto é uma colisão
de nomenclatura, não de rota — a rota do frontend é `/api/health` (App Router route
handler, existe dentro do processo Next.js), enquanto o padrão de proxy `/api/*` do
Caddy aponta para o *backend*. **Decisão:** o padrão `/api/*` do Caddy deve ser
avaliado com cuidado para não capturar `/api/health` do frontend sem querer. Duas
opções foram consideradas:

- **(A) Renomear a checagem de saúde do frontend para fora do namespace `/api`**
  (ex.: mover para `/healthz` ou `/_health`) — evita a colisão de raiz, mas altera um
  contrato já implementado na 11A.2 sem necessidade real (o Docker healthcheck do
  frontend, que é o único consumidor hoje, não passa pelo Caddy — continua batendo
  direto em `127.0.0.1:3000/api/health` de dentro do próprio container).
- **(B) Manter `/api/health` como está e simplesmente não expor o healthcheck do
  frontend através do Caddy** — como o Docker healthcheck do frontend já roda
  *dentro* do container (`wget http://127.0.0.1:3000/api/health`, nunca atravessa a
  rede `internal` nem o Caddy), a colisão nunca se manifesta na prática: ninguém
  precisa acessar `/api/health` do frontend *através* do Caddy. Se algum dia isso for
  necessário, o Caddy pode ter uma regra mais específica (`/api/health` exato) com
  prioridade sobre o `/api/*` genérico, resolvendo a ambiguidade sem tocar no
  frontend.

**Decisão: (B).** Nenhuma mudança no contrato da 11A.2, nenhuma rota nova exposta
publicamente sem necessidade. Documentado aqui para não ser "descoberto" como bug
depois.

### Compatibilidade com os controllers atuais do Spring
Zero mudança de contrato no backend. O strip de `/api` acontece inteiramente no
Caddy — o Spring continua recebendo exatamente `/estimates`, `/auth/login`, etc.,
como hoje.

### `/actuator/health/**`
**Decisão: não expor publicamente através do Caddy.** Nenhuma regra de Caddy
encaminha `/actuator/*` — o Actuator continua acessível só de dentro da rede Docker
(usado pelo próprio healthcheck do container backend, que roda `wget` de dentro do
container, sem passar pela rede `internal` nem pelo Caddy). Um cliente externo que
tentar `https://dominio.tld/actuator/health` cairá no catch-all `/` → frontend →
404 do Next.js. Isso é uma **redução de superfície exposta** em relação ao estado
atual (hoje `/actuator/health/**` é alcançável por qualquer um que atinja a porta
8080 publicada) — efeito colateral positivo do same-origin, não um requisito
explícito, mas vale documentar como tal.

### `/api-docs/**`, `/swagger-ui/**`
Mesma decisão: **sem regra de Caddy**, portanto inalcançáveis publicamente uma vez
que o Caddy for o único ponto de entrada (hoje são alcançáveis via porta 8080
publicada). Redução de superfície, efeito colateral do desenho, sem exigir nenhuma
mudança de `SecurityConfig.java` (o matcher `permitAll` ali continua correto — é
sobre autenticação, não sobre alcançabilidade de rede).

### 404
Não há um "404 do Caddy" dedicado — qualquer path que não bata em `/api/*` nem
`/uploads/*` cai no catch-all e chega ao Next.js, que já tem uma página 404 própria
(`not-found.tsx`, existente desde a Sprint 7B). Nenhuma configuração de erro
adicional necessária no Caddy para esse caso.

### Redirects
Nenhum redirect novo é necessário. O único redirect existente
(`/dashboard/**` sem sessão → `/login`) já acontece dentro do Next.js
(`middleware.ts`) e continua funcionando sem alteração — o Caddy só encaminha a
requisição para o frontend, que decide o redirect como já decide hoje.

## 8. HTTP Local versus HTTPS Real

**Decisão: um único Caddyfile, endereço do site parametrizado por variável de
ambiente (`CADDY_HOST`), sem lógica condicional nem arquivo separado por ambiente.**

```caddyfile
{$CADDY_HOST} {
    ...
}
```

- **Local (validação sem domínio):** `CADDY_HOST=:80`. Um endereço de site que é só
  uma porta (sem hostname) faz o Caddy **nunca tentar automatic HTTPS/ACME** — é o
  próprio comportamento documentado do Caddy (confirmado no Caddyfile de exemplo já
  embutido na imagem oficial, que usa exatamente esse padrão). Isso satisfaz
  diretamente "não force ACME durante testes locais" sem precisar de nenhuma flag
  extra ou arquivo alternativo.
- **Produção futura (domínio real):** `CADDY_HOST=dominio.tld` (ou
  `dominio.tld, www.dominio.tld` para aceitar as duas formas). Assim que o endereço
  do site for um hostname de verdade, o Caddy tenta automaticamente provisionar um
  certificado via ACME (Let's Encrypt, por padrão) na primeira requisição, e renová-lo
  sozinho depois — sem nenhuma mudança adicional no Caddyfile.
- **Alternativas consideradas:**
  - *Dois Caddyfiles (`Caddyfile.local` / `Caddyfile.prod`)* — rejeitado: duplica
    lógica de roteamento (que é idêntica nos dois casos) só para variar uma linha;
    risco real de os dois arquivos divergirem silenciosamente ao longo do tempo.
  - *`tls internal` para HTTPS local com CA própria do Caddy* — considerado como
    técnica **disponível, mas não default**: permite testar o *comportamento* de
    HTTPS localmente (redirect HTTP→HTTPS, headers só-HTTPS) sem tocar em ACME real,
    trocando `CADDY_HOST=:80` por algo como `CADDY_HOST=localhost` +
    `tls internal` no bloco. Não é necessário para validar roteamento
    (`/`, `/api/*`, `/uploads/*`), que é o foco desta sprint — fica documentado como
    opção para quem quiser testar HTTPS localmente, não como parte do fluxo padrão.
- **Cuidado a documentar para quando o Cloudflare existir (fora do escopo, mas
  relevante para não ser surpresa depois):** se o Cloudflare estiver com o proxy
  laranja ativo (modo "proxied") na frente do Caddy, o desafio ACME padrão
  (`HTTP-01`) pode falhar, porque o Cloudflare intercepta a conexão antes de chegar
  ao Caddy. As soluções usuais (usar `DNS-01` com um provider do Cloudflare, ou
  desativar o proxy laranja durante a emissão inicial do certificado) ficam para a
  sprint em que o Cloudflare for de fato configurado — só o risco é registrado aqui
  (§22).

## 9. Caddyfile (desenho — não implementado nesta tarefa)

- **Caminho proposto:** `infra/caddy/Caddyfile` (novo diretório `infra/caddy/`,
  paralelo a `infra/compose/` e `infra/env/`, seguindo a mesma convenção de
  organização já usada pelo projeto).
- **Estrutura (esboço, para a implementação seguinte):**

```caddyfile
{$CADDY_HOST} {
	encode zstd gzip

	log {
		output stdout
		format json
	}

	handle_path /api/* {
		reverse_proxy backend:8080 {
			header_up X-Forwarded-Proto {scheme}
		}
	}

	handle /uploads/* {
		reverse_proxy backend:8080
	}

	handle {
		reverse_proxy frontend:3000
	}

	handle_errors {
		respond "{err.status_code} {err.status_text}"
	}
}
```

- **`encode zstd gzip`:** Caddy oferece `zstd` primeiro (melhor razão/CPU), cai para
  `gzip` se o cliente não suportar — ver §11.
- **`log`:** access log estruturado em JSON para stdout (nunca arquivo dentro do
  container — mesma decisão já tomada para backend/frontend na 11A.2). Ver §17 para
  o que entra/não entra no log.
- **`reverse_proxy` sem `to` explícito de scheme:** os upstreams (`backend:8080`,
  `frontend:3000`) são HTTP puro dentro da rede Docker — não há TLS interno entre
  Caddy e os dois serviços (nem precisa: é a mesma rede bridge isolada, sem tráfego
  saindo do host). `header_up X-Forwarded-Proto {scheme}` garante que o backend saiba
  se a requisição original era HTTP ou HTTPS (consumido por
  `server.forward-headers-strategy: framework`, já configurado na 11A.2).
- **`handle_path` vs. `handle`:** `handle_path` remove o prefixo casado (`/api`)
  antes de encaminhar — é o mecanismo exato do strip descrito em §7.
  `handle`/`handle_path` (não `route`+`uri strip_prefix` manual) porque expressa a
  intenção diretamente e é o idiom recomendado pela documentação do Caddy para esse
  caso.
- **Timeouts:** não sobrescritos nesta fase — os defaults do `reverse_proxy` do Caddy
  (dial/read/write generosos, na casa de segundos a poucos minutos conforme a
  operação) já comportam os piores casos conhecidos da aplicação (geração de PDF é em
  memória e rápida; upload é limitado a 5 MB pela política já existente). Se algum
  timeout se mostrar insuficiente na validação, ajustar então — não antecipar.
- **`trusted_proxies`:** **não configurado nesta sprint.** É relevante quando existir
  *outro* proxy na frente do Caddy (Cloudflare) cujo IP precise ser confiado para
  extrair o IP real do cliente de um `X-Forwarded-For` já preenchido. Hoje o Caddy é
  a própria borda (nenhum proxy na frente) — o comportamento default do Caddy já é
  seguro nesse cenário (ver §18). Fica como pendência explícita para quando o
  Cloudflare existir.
- **Tratamento de `X-Forwarded-*`:** o `reverse_proxy` do Caddy já popula
  `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host` automaticamente para os
  upstreams — não precisa de configuração manual além do `header_up` explícito acima
  (redundante com o default, mantido só por clareza/documentação).
- **Política de erro:** `handle_errors` simples (status + texto) — nenhuma página de
  erro customizada nesta sprint (fora de escopo de produto). Erros de upstream (ex.:
  backend fora do ar) resultam em `502`/`504` padrão do Caddy.

## 10. Headers — Fonte de Verdade

| Header | Fonte de verdade | Caddy duplica? |
|---|---|---|
| `Content-Security-Policy` | **Next.js** (backend também define a sua própria, mais simples, para as respostas JSON/Actuator — sem conflito, são response paths diferentes) | Não |
| `X-Content-Type-Options` | Next.js **e** backend (já idênticos nos dois hoje) | Não |
| `X-Frame-Options` / `frame-ancestors` | Next.js (`X-Frame-Options: DENY`) **e** backend (`frame-ancestors 'none'` no seu próprio CSP) | Não |
| `Referrer-Policy` | Next.js e backend (já idênticos) | Não |
| `Permissions-Policy` | Next.js e backend (já idênticos) | Não |
| `Strict-Transport-Security` | **Caddy** — é o único componente que sabe se a conexão é HTTPS de verdade | Sim, mas só quando `CADDY_HOST` for um domínio real (ver abaixo) |

**Por que não duplicar CSP/X-Frame-Options/etc. no Caddy:** frontend e backend já
definem esses headers corretamente **para as suas próprias respostas** (o frontend
inclusive calcula o `connect-src` do CSP dinamicamente a partir de
`NEXT_PUBLIC_API_BASE_URL`). Adicionar uma terceira declaração no Caddy só criaria
risco de divergência entre três lugares em vez de dois, sem nenhum ganho — o Caddy
não sabe (nem precisa saber) o `connect-src` correto de cada app.

**HSTS — por que só o Caddy:** nem o Next.js nem o Spring sabem, de dentro do seu
próprio processo, se a conexão terminou em TLS de verdade ou não (ambos só recebem
HTTP puro do Caddy, mesmo quando o cliente externo usou HTTPS). O Caddy é o único
componente com essa informação. **Decisão de implementação futura:** o header
`Strict-Transport-Security` só deve ser adicionado ao bloco do Caddyfile quando
`CADDY_HOST` for um domínio real (não `:80`) — nesta sprint o desenho já isola isso
(o bloco HSTS não existe/não tem efeito no cenário `:80` local), mas a ativação
efetiva do header fica condicionada a TLS real estar funcionando ponta a ponta
(depende de VPS/Cloudflare, fora do escopo). Nenhuma mudança necessária no Next.js
nem no Spring por causa disso — ambos continuam sem declarar HSTS, como já é hoje.

## 11. Compressão

| Camada | Estado após 11A.2 | Decisão nesta sprint |
|---|---|---|
| Next.js | `compress: true` (default, implícito) | **Mantido inalterado.** Não é código de produto tocado nesta sprint. |
| Spring Boot | `server.compression.enabled: true`, mime-types JSON/texto, sem PDF | **Mantido inalterado**, mesmo motivo. |
| Caddy | Novo — `encode zstd gzip` no bloco do site | **Passa a ser a camada primária/externa de compressão** para todo tráfego que atravessa o Caddy. |

**Dupla compressão?** Não, na prática: se o backend já respondeu com
`Content-Encoding: gzip`, o `encode` do Caddy detecta o header já presente e não
recomprime — comportamento documentado do próprio Caddy (evita corromper o corpo
recomprimindo algo já comprimido). O único custo é CPU gasta duas vezes à toa em
casos onde o backend comprime uma resposta que o Caddy já teria comprimido de
qualquer forma — não é um bug funcional, é uma ineficiência pequena.

**Qual camada deveria ser responsável, olhando para frente:** o Caddy, por já ser o
único ponto de saída para a internet. **Não desligar** a compressão do Spring/Next.js
nesta sprint (seria uma alteração de `application-prod.yml`/`next.config.ts`, fora do
escopo aqui) — registrado como limpeza futura de baixa prioridade em §22/§23, a ser
feita só depois que o roteamento via Caddy estiver validado em produção real.

## 12. CORS

**Decisão: manter `APP_CORS_ALLOWED_ORIGINS` e toda a validação já construída na
11A.2, sem enfraquecer nada.**

- **Com same-origin via Caddy, o CORS deixa de ser exercitado pelo navegador** no
  caminho principal (frontend chamando `/api/*` no mesmo `scheme://host:port` que a
  própria página — não há preflight, não há necessidade de
  `Access-Control-Allow-Origin` para essas chamadas específicas).
- **Mas CORS continua necessário porque:**
  1. **Dev local sem Docker** (`npm run dev` na porta 3000 chamando o backend direto
     na porta 8080 via `./mvnw spring-boot:run`) é cross-origin por definição — esse
     é o fluxo de desenvolvimento do dia a dia, inalterado por esta sprint, e
     depende do CORS atual continuar funcionando exatamente como está.
  2. **Defesa em profundidade:** CORS é reforçado pelo *navegador*, não pelo
     servidor — não impede um cliente não-browser (curl, outro serviço) de chamar a
     API. A proteção real de dados é o JWT. Ainda assim, uma configuração de CORS
     restritiva reduz a superfície de abuso via browser (ex.: um site malicioso
     tentando usar o token de um usuário logado a partir de outra origem) — vale
     manter mesmo sendo redundante no caminho feliz.
  3. Não há garantia de que todo tráfego futuro será same-origin — a arquitetura é
     multi-tenant SaaS; um domínio de marketing separado ou uma futura integração
     poderiam legitimamente precisar de CORS configurado.
- **Comportamento em produção (atrás do Caddy):** `APP_CORS_ALLOWED_ORIGINS` deve ser
  configurada com o **mesmo domínio público** que o Caddy serve (ex.:
  `https://dominio.tld`) — coerente com o same-origin real, funciona como uma rede de
  segurança que nunca deveria disparar no uso normal, mas protege caminhos
  alternativos (porta interna exposta por engano, chamada direta ignorando o Caddy).
- **Comportamento local:** inalterado — continua aceitando os defaults de
  desenvolvimento já existentes (`http://localhost:3000`, etc.) fora do profile
  `prod`.
- **Não desabilitar nada "porque agora tem proxy":** explicitamente contrário à
  instrução da tarefa — mantido.

| Variável | Serviço | Finalidade | Obrigatória? | Segredo? | Momento | Default local | Comportamento em produção | Rebuild ou restart? |
|---|---|---|---|---|---|---|---|---|
| `CADDY_HOST` | caddy | Endereço do site no Caddyfile (`{$CADDY_HOST}`) | Não (tem default) | Não | Runtime | `:80` (HTTP puro, sem ACME) | Domínio real (ex.: `dominio.tld`) — ativa automatic HTTPS | Restart (recarrega o Caddyfile) |
| `CADDY_HTTP_PORT` | compose (interpolação) | Porta do host publicada para HTTP | Não | Não | Orquestração | `80` | `80` (recebido pelo Cloudflare/VPS) | Recriação do container |
| `CADDY_HTTPS_PORT` | compose (interpolação) | Porta do host publicada para HTTPS | Não | Não | Orquestração | Não publicada localmente (sem TLS real ainda) | `443` | Recriação do container |
| `NEXT_PUBLIC_API_BASE_URL` | frontend (build-time) | Origem que o browser chama para a API/uploads | Sim | Não | **Build-time** | `http://localhost:8080` (dev direto) ou a origem do Caddy local | **Passa a ser a mesma origem pública do site** (ex.: `https://dominio.tld`) em vez da origem do backend isoladamente — mudança de *valor*, não de mecanismo | **Rebuild** (já documentado como build-time desde a 11A.2) |
| `NEXT_PUBLIC_SITE_URL` | frontend (build-time) | Canonical/OG, base de links públicos de partilha | Recomendada | Não | Build-time | Sem mudança de mecanismo | Mesma origem pública (`https://dominio.tld`) | Rebuild |
| `APP_CORS_ALLOWED_ORIGINS` | backend | Origens permitidas por CORS | Sim (com profile `prod`) | Não | Runtime | Inalterado (defaults de dev) | Passa a incluir a origem pública servida pelo Caddy (ver §12) | Restart |

**Nota importante sobre `NEXT_PUBLIC_API_BASE_URL`:** hoje essa variável é lida por
**dois** caminhos de código diferentes no frontend — os clientes HTTP JSON
(`http-client.ts`/`admin-http-client.ts`, que fazem `new URL(path, base)` com `path`
já contendo a barra inicial igual à rota do Spring) e a resolução de assets
(`resolveAdminAssetUrl`/`resolvePublicAssetUrl`, mesmo padrão `new URL(url, base)`).
Trocar o **valor** dessa variável para a origem pública do Caddy (ex.:
`https://dominio.tld`) resolve corretamente o caso de `/uploads/*` sem nenhuma
mudança de código (o backend já serve `/uploads/**` na raiz, e o Caddy roteia
`/uploads/*` sem strip — ver §7) — mas **não** resolve sozinho o caso das chamadas de
API, porque essas precisam terminar em `/api/...` para o Caddy rotear ao backend,
e hoje os dois clientes HTTP montam a URL como `origem + path` **sem** o prefixo
`/api`. Isso não é uma mudança de *variável*, é uma mudança de **uma linha em dois
arquivos** (`http-client.ts`, `admin-http-client.ts`) para prefixar `/api` no path
antes de montar a URL — ver §19, Etapa 4. Documentado aqui explicitamente porque é o
único ponto onde "só trocar uma variável de ambiente" não é suficiente, e eu não
quero que isso seja descoberto como bug de implementação depois.

## 14. Docker Compose (desenho)

Novo serviço, a ser adicionado em `infra/compose/docker-compose.prod.yml` na
implementação seguinte:

```yaml
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    environment:
      CADDY_HOST: ${CADDY_HOST:-:80}
    volumes:
      - ../caddy/Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    ports:
      - "${CADDY_HTTP_PORT:-80}:80"
      # - "${CADDY_HTTPS_PORT:-443}:443"   # habilitar quando CADDY_HOST for um domínio real
    networks:
      - internal
    depends_on:
      frontend:
        condition: service_healthy
      backend:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:80/"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 15s
    mem_limit: 256m
    mem_reservation: 128m
    cpus: "0.5"
    logging: *default-logging
```

- **Imagem/tag:** `caddy:2-alpine` — já verificada nesta tarefa (§5.4): tem
  wget/curl, roda como root (necessário para bind em 80/443), Caddyfile de exemplo
  já usa o padrão `:80` recomendado para HTTP puro sem ACME.
- **`restart: unless-stopped`:** mesmo padrão dos outros três serviços — consistente,
  sem motivo para divergir (mesmo raciocínio do DT-011A.2 §6.3.3).
- **Volumes:** `Caddyfile` montado **read-only** (config é gerida pelo repositório,
  não deve ser editável de dentro do container); `caddy_data`/`caddy_config` como
  volumes nomeados — ver §15.
- **Network:** só `internal` — o Caddy alcança `frontend`/`backend` pelo nome do
  serviço, na mesma rede que já existe.
- **`depends_on`:** `frontend` e `backend` com `condition: service_healthy` — o Caddy
  só deve começar a rotear tráfego depois que os dois upstreams já estiverem prontos
  (evita 502 no primeiro request logo após `up`). Diferente da relação
  `backend`→`postgres` da 11A.2 (que é uma dependência de *dado*), esta é uma
  dependência de *disponibilidade do proxy* — mais parecida com um API gateway
  esperando seus backends.
- **Portas publicadas:** só `CADDY_HTTP_PORT` (padrão `80`) nesta sprint — a linha de
  `CADDY_HTTPS_PORT`/443 fica **comentada/condicional** no desenho até existir TLS
  real, para não publicar uma porta que não serve nada localmente.
- **Remoção de `ports:` do frontend/backend:** ambos os serviços deixam de ter o
  bloco `ports:` inteiramente — permanecem alcançáveis dentro da rede `internal` pelo
  nome do serviço (Docker DNS interno), que é tudo que o Caddy precisa. `expose:` é
  opcional/documental (não muda alcançabilidade dentro da mesma rede definida
  pelo usuário) — incluir por clareza não é obrigatório, mas é barato.
- **Recursos provisórios:** `256m`/`128m`/`0.5` vCPU — Caddy é um proxy leve (sem
  estado de aplicação, sem JVM/V8); dimensionado propositalmente pequeno, na mesma
  categoria "provisório, revisar na 11B" dos demais serviços (DT-011A.2 §6.3.2).
- **`read_only`/`security_opt`/capabilities:** avaliados (§18) e propostos como
  **melhoria proporcional a considerar na implementação**, não bloqueantes para esta
  sprint: `read_only: true` no filesystem raiz é viável mantendo `/data`/`/config`
  como volumes graváveis (e possivelmente um `tmpfs` para diretórios temporários que
  o Caddy possa precisar) — decisão final de habilitar ou não fica para a
  implementação, sem impacto na arquitetura de roteamento.

## 15. Persistência do Caddy

| Volume | Caminho no container | Conteúdo | Por que precisa sobreviver a recreate |
|---|---|---|---|
| `caddy_data` | `/data` | Certificados TLS emitidos (ACME), chaves privadas, cache OCSP | Recriar o container **sem** este volume forçaria o Caddy a reemitir um certificado novo do zero a cada `up`/atualização de imagem — na prática esbarraria nos **rate limits do Let's Encrypt** (por domínio/semana) e causaria uma janela sem HTTPS válido a cada deploy. Crítico assim que houver domínio real. |
| `caddy_config` | `/config` | Config JSON autosalva pelo Caddy (estado ativo, usado por `caddy reload`/admin API) | Sem isto, o Caddy perde o "último config ativo conhecido" entre reinícios — não é tão crítico quanto `/data` (o Caddyfile montado como volume `:ro` já é a fonte de verdade declarativa), mas é o padrão recomendado pela própria documentação do Caddy para qualquer uso não-efêmero. |

Nenhum dos dois precisa de backup nesta sprint (fora de escopo — 11A.5), mas ambos
precisam **existir como volumes nomeados** desde já para que a persistência funcione
corretamente quando TLS real for ligado.

## 16. Healthcheck do Caddy

**Decisão: o healthcheck do Caddy verifica só o próprio Caddy, não profundamente
cada upstream.**

```
CMD wget -q -O /dev/null http://127.0.0.1:80/
```

Isso confirma que **o processo Caddy está de pé e aceitando conexões na porta que
importa** — não confirma que o frontend/backend por trás dele estão saudáveis (isso
já é responsabilidade dos healthchecks *deles próprios*, já existentes desde a
11A.1/11A.2, e da condição `depends_on: service_healthy` no `caddy` que garante que
ele só *inicia* depois que os dois já estão saudáveis).

**Diferenciação explícita (pedida pela tarefa):**

| Sinal | O que significa | Quem verifica |
|---|---|---|
| Caddy vivo | O processo Caddy está de pé e a porta 80 aceita conexões | `healthcheck` do próprio `caddy` (este) |
| Frontend vivo | O processo Next.js está de pé | `healthcheck` do `frontend` (`/api/health`, já existente) |
| Backend pronto | JVM viva **e** Postgres alcançável | `healthcheck` do `backend` (`/actuator/health/readiness`, já existente) |

**Por que não acoplar tudo em um único healthcheck "profundo" do Caddy** (ex.: o
Caddy checando `/` que por sua vez bate no frontend, ou `/api/health` do backend
através de si mesmo): um healthcheck do Caddy que dependesse de um upstream
respondendo faria o **próprio Caddy** aparecer `unhealthy` sempre que só o frontend
(ou só o backend) tivesse um problema — mascarando qual dos três serviços realmente
falhou e potencialmente derrubando o único ponto de entrada por um problema que é só
de um dos dois upstreams. Manter os três healthchecks independentes (um por serviço,
cada um checando só a si mesmo) preserva o diagnóstico claro que a 11A.2 já
estabeleceu para frontend/backend.

## 17. Logs

- **stdout/stderr, sempre** — mesma decisão já estabelecida para backend/frontend na
  11A.2 (`log { output stdout }` no Caddyfile, nunca um arquivo dentro do container).
- **Formato:** JSON (`format json` no bloco `log` do Caddyfile) — mais fácil de
  processar depois, se/quando uma stack de observabilidade for adicionada (fora do
  escopo agora).
- **Rotação:** via o driver `json-file` do Docker, reaproveitando a mesma âncora
  `x-logging` (`max-size: 10m`, `max-file: 5`) já usada pelos outros três serviços —
  nenhuma configuração de rotação nova a inventar.
- **Dados sensíveis:** o access log padrão do Caddy inclui método, path, status,
  duração, User-Agent e IP do cliente — **não inclui corpo de request/response nem
  headers de autenticação** por padrão (`Authorization` não é logado a menos que
  explicitamente configurado, o que não está sendo proposto aqui). Nenhuma
  informação de `JWT_SECRET`/senhas passa pelos logs do Caddy (ele não vê o conteúdo
  de tokens, só que existe um header `Authorization`, se decidir logar headers — que
  não está sendo habilitado nesta sprint).
- **IP do cliente:** hoje (sem Cloudflare), o IP que o Caddy vê **é** o IP real do
  cliente — correto por padrão. Quando o Cloudflare existir (fora do escopo), o IP
  que o Caddy verá será o da Cloudflare, e o IP real do visitante viajará num header
  (`CF-Connecting-IP` ou `X-Forwarded-For`) que só deve ser confiado depois de
  configurar `trusted_proxies` com os ranges da Cloudflare — pendência explícita
  registrada em §9/§22, não resolvida aqui.
- **Sem stack de observabilidade:** nenhum Loki/Prometheus/Grafana introduzido —
  fora de escopo, como já estava explícito na tarefa.

## 18. Segurança

| Item | Avaliação |
|---|---|
| Frontend/backend sem porta pública | Depois desta sprint, `ports:` sai dos dois — só alcançáveis pela rede `internal`. Esta é a mudança de segurança central da sprint. |
| PostgreSQL interno | Inalterado desde a 11A.1 — nunca teve porta publicada. |
| `forward-headers-strategy: framework` | Já ativo desde a 11A.2 no backend — passa a ser efetivamente usado agora que existe um proxy real na frente enviando `X-Forwarded-*`. |
| Spoofing de `X-Forwarded-For` | Mitigado principalmente por **topologia de rede**: com `frontend`/`backend` sem porta publicada, só o `caddy` (mesma rede Docker) consegue alcançá-los — um cliente externo não pode enviar headers `X-Forwarded-*` diretamente a eles. O comportamento default do `reverse_proxy` do Caddy (que é a própria borda pública hoje, sem proxy na frente) já trata corretamente um `X-Forwarded-For` vindo do cliente sem confiar cegamente nele. |
| `trusted_proxies` | Não configurado — correto para o cenário atual (Caddy é a borda). Vira necessário quando o Cloudflare existir (fora de escopo, pendência registrada). |
| Headers de segurança | Sem duplicação (§10) — mantidos na app, HSTS reservado ao Caddy quando TLS real existir. |
| Endpoints Actuator | `/actuator/**` deixa de ser alcançável publicamente (nenhuma regra de Caddy o expõe) — redução de superfície, efeito colateral positivo do desenho (§7). |
| Acesso direto por rede Docker | Qualquer container **na mesma rede `internal`** ainda alcança `frontend:3000`/`backend:8080` diretamente pelo nome — isso é esperado e necessário (é como o próprio Caddy os alcança); não é um vetor de ataque novo, já que só containers definidos neste mesmo `docker-compose.prod.yml` participam dessa rede. |
| Caddy admin API | A imagem oficial expõe a admin API só em `localhost:2019` **dentro do container** por padrão — nenhuma porta é publicada para ela neste desenho (só `CADDY_HTTP_PORT`/`CADDY_HTTPS_PORT` são publicadas), então a admin API não fica acessível nem pela rede `internal`, nem pelo host. Nenhuma ação adicional necessária. |
| Filesystem read-only | Viável (`read_only: true` + volumes graváveis para `/data`/`/config`) — proposto como melhoria a considerar na implementação (§14), não bloqueante. |
| Capabilities | Caddy roda como root (padrão da imagem oficial, necessário para bind em portas <1024). Trocar para usuário não-root + `cap_add: [NET_BIND_SERVICE]` é uma opção de hardening mais forte, deixada como possível item futuro (11A.6) para não aumentar o escopo desta sprint além do roteamento. |
| Secrets | Nenhum segredo novo introduzido — o Caddyfile não contém credenciais; `CADDY_HOST` não é sensível. |

## 22. Riscos e Trade-offs

| Risco/trade-off | Descrição | Mitigação/decisão |
|---|---|---|
| Same-origin com prefixo `/api` | Exige uma mudança pontual de código no frontend (2 arquivos) — não é "zero código", como uma solução por subdomínios teria sido | Aceito: é exatamente o padrão pré-aprovado na tarefa; a mudança é pequena, centralizada, e testável isoladamente (Etapa 4, §19) |
| Prefixo `/api` e possíveis colisões futuras | Uma futura rota do frontend chamada `/api/*` colidiria com o proxy para o backend | Documentado em §7 (caso concreto: `/api/health`); resolvido preferindo regras mais específicas no Caddy quando necessário, sem exigir renomear rotas do frontend preventivamente |
| Variáveis build-time do Next | `NEXT_PUBLIC_API_BASE_URL` muda de valor (origem do backend → origem pública via Caddy) — exige rebuild da imagem do frontend, não só restart | Já era uma limitação estrutural conhecida desde a 11A.2 (matriz de variáveis); nada novo, só um valor diferente |
| ACME local | Se alguém setar `CADDY_HOST` para um hostname real acidentalmente durante teste local (sem DNS apontando de fato), o Caddy tentará e falhará a emissão do certificado, sem quebrar o roteamento HTTP em si | Documentado: usar `:80` para validação local é a orientação padrão (§8); falha de ACME não é catastrófica, só gera log de erro e Caddy segue sem HTTPS |
| Dupla compressão | Backend/frontend podem comprimir uma resposta que o Caddy comprimiria de qualquer forma | Sem risco funcional (Caddy não recomprime o que já vem comprimido) — só ineficiência de CPU pequena, documentada como limpeza futura (§11) |
| Headers duplicados | Risco evitado por desenho — Caddy não duplica CSP/X-Frame-Options/etc. (§10) | N/A — mitigado na própria arquitetura, não um risco residual |
| Cloudflare futuro | `trusted_proxies` não configurado ainda; ACME HTTP-01 pode conflitar com o modo "proxied" da Cloudflare | Ambos documentados como pendência explícita (§9, §17) para a sprint em que o Cloudflare for de fato introduzido |
| Persistência dos certificados | Sem os volumes `caddy_data`/`caddy_config`, cada recreate re-emitiria certificado, esbarrando em rate limit do Let's Encrypt | Volumes nomeados definidos desde já (§15), mesmo sem uso real de TLS ainda |
| Perda do IP real do cliente | Não acontece hoje (Caddy é a borda) — aconteceria se o Cloudflare fosse introduzido sem configurar `trusted_proxies`/`CF-Connecting-IP` | Fora do escopo desta sprint; risco registrado para quando o Cloudflare existir |
| Dependência do proxy | Se o Caddy cair, a aplicação inteira fica inacessível (mesmo com frontend/backend saudáveis) — é a natureza de um único ponto de entrada | Aceito como trade-off inerente ao desenho pedido (single entry point); `restart: unless-stopped` + healthcheck raso (§16) minimizam o tempo de indisponibilidade em caso de falha do próprio Caddy |
