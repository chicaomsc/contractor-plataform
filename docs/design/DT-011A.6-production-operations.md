# DT-011A.6 — Production Operations Documentation

## 1. Status

Implemented

## 2. Contexto

As Sprints 11A.1–11A.5 construíram, nesta ordem: containers de produção (11A.1),
configuração `prod` (11A.2), Caddy como entrypoint único (11A.3), publicação de
imagens no GHCR (11A.4 + estabilização em `fix/ghcr-pipeline-stabilization`) e
backup/restore via Restic (11A.5). Cada uma produziu seu próprio Design Técnico
(`docs/design/DT-011A.{2,3,4,5}.md`) e sua própria seção em `infra/README.md`, que
cresceu para **883 linhas** cobrindo cinco sprints diferentes no mesmo arquivo.

O que falta não é mais decisão técnica — é **consolidação**: hoje, entender "como
operar isto" exige ler cinco DTs, um README de 883 linhas e um README de backup
separado, e ainda assim não existe um único lugar que descreva o ciclo operacional
completo (deploy → validação → rollback ou restore → troubleshooting) do ponto de
vista de quem vai operar o sistema, não de quem o construiu.

## 3. Objetivo

Produzir **somente o Design Técnico** desta sprint: inspecionar o repositório real,
mapear o que existe, identificar inconsistências/duplicações/lacunas, decidir a
estrutura documental final (fontes de verdade + estrutura de diretórios) e definir
o conteúdo esperado de um runbook de produção — sem criar ainda nenhum arquivo de
`docs/operations/`, sem alterar `infra/README.md`, sem alterar `docs/roadmap.md`,
sem tocar em código, Compose, Caddy ou workflows.

### 4.11 `infra/backup/` — implementação real (lida script a script, não só o DT)

- `lib.sh`: helpers compartilhados — `log`/`die`, `require_var`/`require_cmd`/`require_file`, `load_backup_env` (resolve `BACKUP_COMPOSE_FILE`/`BACKUP_PRODUCTION_ENV` relativos ao diretório do `backup.env`, não ao CWD), `compose_container_id` (resolve container por serviço via `docker compose ps -q`, nunca adivinha nome de volume prefixado), `restic_run` (monta repositório/senha/cache/SFTP de forma centralizada; monta `RESTIC_REPOSITORY` como bind mount só quando é um path absoluto, não quando tem prefixo de esquema como `sftp:`), um **registro único de cleanup** (`_CLEANUP_PATHS`/`_CLEANUP_VOLUMES` + `trap _run_registered_cleanup EXIT`, para não sobrescrever `trap ... EXIT` entre múltiplos registros), e `send_staging_to_restic` (copia o staging para um **volume Docker nomeado efêmero** antes de entregar ao Restic — refinamento real descoberto durante validação, não um workaround só de Mac: evita depender de bind mount na única travessia Docker↔Restic que lê arquivo de origem).
- `backup-postgres.sh`: `pg_dump --format=custom --compress=6` via `docker exec` na porta do container `postgres` já rodando; valida com `pg_restore --list` (container `postgres:17-alpine` efêmero); copia `production.env` para o mesmo staging (protegido pela criptografia do Restic); nunca considera sucesso se `pg_dump` falhar.
- `backup-files.sh`: `--target backend-storage|caddy-data|all`; lê os volumes via `--volumes-from <container>:ro`; nunca escreve.
- `backup-all.sh`: orquestra os três; `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --group-by tags --prune` **só** se os backups anteriores tiverem sucesso; `--skip-retention`/`--with-check` como flags opcionais.
- `restore-postgres.sh`: dry-run por padrão (resolve/valida, sai com código 2); `--confirm` para de fato parar `backend`, rodar `pg_restore --clean --if-exists --no-owner` via stdin, e avisar explicitamente sobre o descompasso Flyway/`APP_VERSION`.
- `restore-files.sh`: dry-run por padrão; `--confirm` copia o conteúdo validado via `--volumes-from` (gravável) e corrige `chown` (uid/gid **1000:1000**, inspecionado no `backend/Dockerfile`) — não precisa parar o serviço.
- `systemd/contractor-platform-backup.{service,timer}`: templates versionados, **não instalados**; timer diário `03:15 UTC`, `Persistent=true`.
- **Tudo isso foi validado de ponta a ponta com dados reais** (empresa + logo criados via API, corrompidos/apagados, restaurados com hash idêntico; `caddy_data` idem; `restic check`/retenção/3 modos de falha testados) — não é apenas o desenho do DT, é a implementação testada.

## 9. Estrutura Documental Proposta

**Rejeitada a estrutura de 5 arquivos sugerida no pedido**
(`production-runbook.md`, `deployment.md`, `rollback.md`, `disaster-recovery.md`,
`troubleshooting.md`). Motivo: deploy, rollback, disaster recovery e
troubleshooting são momentos do **mesmo ciclo operacional** e compartilham
contexto (os mesmos health checks, o mesmo `APP_VERSION`, a mesma distinção
rollback-vs-restore) — separá-los em 5 arquivos criaria exatamente a duplicação
e o risco de deriva que a Sprint 11A.6 existe para eliminar. Disaster recovery em
particular já tem `infra/backup/README.md` como especialista; um arquivo
`disaster-recovery.md` à parte duplicaria isso ou ficaria vazio.

**Proposta (a menor estrutura que é clara, profissional e fácil de manter):**

```
docs/operations/
  runbook.md      # único documento novo desta sprint (implementação futura)
```

Um arquivo. Ele cobre deploy, rollback, health checks, logs, inspeção,
troubleshooting e os dois checklists — com **links**, não cópias, para
`infra/backup/README.md` (backup/restore/disaster recovery), `docs/design/DT-*`
(decisões) e `infra/env/production.env.example` (variáveis). Se, depois da
Sprint 11B/11C, o runbook crescer a ponto de um segundo arquivo se justificar
por conteúdo real (não por antecipação), ele nasce então — não agora.

### Recomendação explícita sobre `infra/README.md`

**Deve ser reduzido, não continuar crescendo.** Hoje mistura referência técnica
de infraestrutura (o que cada serviço do Compose faz e por quê — deve
permanecer aqui) com procedimento operacional (como fazer deploy, como validar,
como fazer rollback — deve mudar para o runbook). Recomendação concreta:
manter as seções de arquitetura/decisão (`Arquitetura dos containers`, `Dados
persistentes`, `Portas`, `Roteamento`, `Configuração de Produção`, `Caddy`,
seções de nomenclatura/tags do GHCR, resumo de backup) e **mover** as seções de
procedimento (`Comandos de validação` do Caddy, o passo a passo de
deploy/rollback do GHCR) para `docs/operations/runbook.md`, deixando um
resumo+link no lugar — exatamente o padrão que a seção "Backup / Restore" já
usa corretamente com `infra/backup/README.md` hoje. Isso não é executado nesta
tarefa (§30).

### Recomendação explícita sobre `infra/backup/README.md`

**Continua especializado, sem mudança.** Já é exatamente o padrão certo: raiz
técnica completa vive lá, `infra/README.md` só resume+linka. O runbook novo deve
tratar backup/restore/disaster-recovery do mesmo jeito — resumo curto + link,
nunca reescrever os comandos.

## 12. Deploy — Confirmado no Código/Config Real

Fluxo (confirmado, não inventado):

```
git push origin main
  → publish-images.yml dispara (paths: backend/**, frontend/**)
  → dois jobs independentes publicam:
       ghcr.io/chicaomsc/contractor-platform-backend:<full-sha>
       ghcr.io/chicaomsc/contractor-platform-frontend:<full-sha>
  → operador define APP_VERSION=<full-sha> em production.env
  → docker compose --env-file infra/env/production.env \
      -f infra/compose/docker-compose.prod.yml pull
  → docker compose --env-file infra/env/production.env \
      -f infra/compose/docker-compose.prod.yml up -d
  → health checks (§21)
  → smoke test (login, listar dado conhecido)
```

**Nunca `--build`** neste fluxo — confirmado em `infra/README.md`: `up -d` sem
`--build` nunca invoca o bloco `build:` quando a imagem referenciada já existe.
**Deploy de imagem ≠ migration rollback** — Flyway é forward-only (§16).

## 13. Rollback de Aplicação vs. Restore de Banco

Definição explícita que o runbook deve repetir sempre que o assunto aparecer:

- **Rollback de aplicação** = `APP_VERSION=<sha-anterior>` + `pull` + `up -d`. Reverte **código**. Não toca no banco. Mecanismo: `docker-compose.prod.yml` (`image: ...:${APP_VERSION}`).
- **Restore de banco** = `infra/backup/scripts/restore-postgres.sh <snapshot> --confirm`. Reverte **dado**. Mecanismo: Sprint 11A.5.
- **Nunca tratar `APP_VERSION=<sha-antigo>` como "desfez a migration"** quando uma migration incompatível já rodou — o código antigo pode quebrar contra o schema novo (já documentado em `docs/design/DT-011A.4-ghcr-image-pipeline.md` §18 e reforçado em `docs/design/DT-011A.5-backup-restore.md` §28). O runbook deve apresentar isso como **dois procedimentos distintos**, nunca como "duas formas de fazer a mesma coisa".

## 14. Flyway / Migrations

Forward-only, confirmado em `docker-compose.prod.yml` (`spring.flyway.clean-disabled: true` em `application-prod.yml`) e nos testes reais da Sprint 11A.5 (`DbValidate: Successfully validated 10 migrations` após um restore real). **Nenhum downgrade automático existe ou é planejado.** Migration destrutiva → só resolve com restore de um snapshot anterior (aceitando a janela de RPO).
