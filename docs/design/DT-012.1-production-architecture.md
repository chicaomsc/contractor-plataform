# DT-012.1 — Production Architecture (Design Only)

**Sprint:** 12.1
**Tipo:** Documento técnico (DT) — apenas design, nenhum código/Dockerfile/compose/workflow foi criado ou alterado nesta tarefa.
**Status:** Proposed
**Revisão:** corrigida inconsistência de ACME/TLS wildcard — ver §9 e `ADR-005`
(§25). A versão original recomendava HTTP-01 como ponto de partida; corrigido
para DNS-01/Cloudflare, único mecanismo compatível com o certificado wildcard
que a multi-tenancy por subdomínio dinâmico exige. Nenhuma outra decisão
arquitetural foi alterada nesta revisão.

## 1. Objetivo

Consolidar, num único documento de arquitetura, a topologia de produção completa do
Contractor Platform — o que já foi decidido e implementado nas Sprints 11A/11B, e o
que ainda precisa ser decidido antes do go-live real (VPS, domínio, TLS,
observabilidade, escalabilidade). Este documento não reabre decisões já tomadas sem
justificativa explícita — ele as cita, confirma, e preenche as lacunas que ainda não
tinham uma decisão registrada (Redis, custo Hetzner, ADRs formais, plano das
subsprints seguintes).

## 2. Escopo e não-escopo

**Escopo:** os 20 itens listados na tarefa (arquitetura lógica → custo Hetzner),
cada um como uma seção numerada abaixo.

**Não-escopo (explícito, por instrução desta sprint):**
- Nenhum código, Dockerfile, `docker-compose.yml`/`.prod.yml`, ou workflow GitHub
  Actions é criado ou alterado por este documento — implementação é
  responsabilidade das subsprints 12.2–12.7 (§27).
- Não reabre auditoria de segurança (`DT-011B.1`–`.5`) nem os scanners automáticos
  (`DT-011B.7`/`docs/security/security-baseline.md`) — são citados como já
  resolvidos onde relevante.
- Não decide o provedor de DNS/CDN definitivo além de reafirmar Cloudflare como
  already-targeted (`DT-011A.3 §2`) — só formaliza o custo e o papel dele.

## 3. Fontes já decididas (não reabertas por este documento)

Este documento parte de decisões já tomadas e implementadas nas Sprints 11A/11B,
citadas ao longo do texto. Resumo das mais estruturais, para não repetir a citação
completa em toda seção:

- **Topologia-alvo já declarada** (`DT-011A.3 §2`): `Cloudflare → VPS Hetzner →
  Caddy → {Next.js, Spring Boot} → PostgreSQL`. Este documento adota essa topologia
  como definitiva e a detalha.
- **`docker-compose.prod.yml`** já implementa: rede única `internal`, só `caddy`
  publica porta, 4 volumes nomeados, healthchecks em todos os serviços,
  `restart: unless-stopped`, limites de CPU/memória marcados como provisórios.
- **Migrations Flyway forward-only**, sem downgrade automático — restore de backup
  é o único caminho de reversão de dado (`DT-011A.5 §28`).
- **Backup via Restic** (Postgres `pg_dump` + `backend_storage` + `caddy_data`),
  retenção 7 diárias / 4 semanais / 6 mensais, RPO ≤ 24h, RTO ≈ horas — já
  desenhado e testado localmente (`DT-011A.5`), pendente só de VPS/Storage Box
  reais.
- **Pipeline de imagem via GHCR** (`DT-011A.4`): tags SHA imutáveis, nunca
  `:latest`, `linux/amd64`.
- **Multi-tenancy em runtime**, não build-time — resolução de tenant por `Host`
  real (`DT-011A.7`/`DT-011A.8`, reafirmado em `runbook.md §21.1`).
- **Nenhuma observabilidade, nenhum Redis, nenhum TLS real** hoje — todos
  deliberadamente adiados nos DTs anteriores, não esquecidos. Este documento decide
  o que fazer com cada um.

## 4. Arquitetura lógica da aplicação

```
                         ┌─────────────────────────────┐
                         │   Cliente (browser/API)     │
                         └──────────────┬───────────────┘
                                        │ HTTPS (após 12.x)
                         ┌──────────────▼───────────────┐
                         │   Cloudflare (DNS + proxy)    │  ← §22, custo
                         └──────────────┬───────────────┘
                                        │
                         ┌──────────────▼───────────────┐
                         │   Hetzner VPS (único host)    │
                         │  ┌─────────────────────────┐  │
                         │  │  Caddy (único :80/:443) │  │  ← §7/§8
                         │  └────┬──────────────┬─────┘  │
                         │       │              │        │
                         │  ┌────▼─────┐   ┌────▼─────┐  │
                         │  │ frontend │   │ backend  │  │  ← §4.1/§4.2
                         │  │ Next.js  │   │ Spring   │  │
                         │  └──────────┘   └────┬─────┘  │
                         │                       │        │
                         │                  ┌────▼─────┐  │
                         │                  │ postgres │  │  ← §9
                         │                  └──────────┘  │
                         └────────────────────────────────┘
                                        │
                         ┌──────────────▼───────────────┐
                         │  Hetzner Storage Box (backup) │  ← §12
                         └───────────────────────────────┘
```

### 4.1 Backend (Spring Boot)

Um único deployável (JAR), multi-tenant desde o desenho inicial (`company_id` em
toda tabela de negócio — `ADR-000`, citado em `DT-011A.4 §12.1`, rejeitando
retrofit posterior por ser mais caro). Stateless
(`SessionCreationPolicy.STATELESS`) — nenhuma sessão de servidor, nenhum cookie
emitido pelo backend. Autenticação via JWT de curta duração + refresh token opaco
persistido (não é um JWT, não é cacheado — `DT-011B.6D`).

Módulos de domínio (pacotes): `auth`, `admin` (SUPER_ADMIN/plataforma), `company`,
`gallery`, `servicecatalog`, `customer`, `estimate` (+ `pdf`), `common` (storage,
segurança, exceções). Nenhuma mudança de arquitetura modular é proposta aqui — a
estrutura atual já suporta o crescimento esperado no horizonte desta DT (§19).

### 4.2 Frontend (Next.js)

Uma única imagem (`output: "standalone"`), serve **múltiplos tenants em runtime** —
resolve o tenant pelo `Host` real da requisição contra `GET /public/tenant`, não
por variável de build (`NEXT_PUBLIC_COMPANY_SLUG` foi removido, `DT-011A.7`/`.8`).
Isso significa: **uma imagem publicada serve toda a base de clientes**, sem rebuild
por tenant — uma decisão que já paga dividendos na arquitetura de deploy (§19) e na
de escalabilidade (§21).

### 4.3 Por que não microsserviços

Rejeitado explicitamente para este estágio: dois processos (backend, frontend) já
são a granularidade certa para uma equipe pequena e uma base de clientes ainda em
validação de mercado. Microsserviços introduziriam: rede entre serviços (latência,
falhas parciais), múltiplos deploys coordenados, observabilidade obrigatória
(tracing distribuído) antes mesmo de ter uma agora — tudo custo, sem benefício de
escala que o produto ainda não precisa. Ver `ADR-001` (§25).

## 5. Topologia dos containers

Confirma e detalha a topologia já implementada em `docker-compose.prod.yml`:

| Container | Rede | Porta publicada no host | Depende de (`condition`) |
|---|---|---|---|
| `caddy` | `internal` | `${CADDY_HTTP_PORT:-80}` (e `:443` quando TLS ativar, §8) | `frontend`/`backend` `service_healthy` (só ordenação de start) |
| `frontend` | `internal` | Nenhuma | Nenhuma (deliberado — frontend sobe mesmo com API fora) |
| `backend` | `internal` | Nenhuma | `postgres` `service_healthy` |
| `postgres` | `internal` | Nenhuma | — |

Nenhum container além do `caddy` é alcançável fora da rede Docker — essa é a
garantia real de isolamento (não um firewall externo adicional, embora um
firewall de borda no VPS — §5.1 — continue recomendado como camada extra).

### 5.1 Firewall do host (novo nesta DT — não implementado antes)

Ainda não há uma decisão registrada sobre firewall de SO/nuvem no VPS. Proposta:
**Hetzner Cloud Firewall** (recurso nativo, gratuito, aplicado antes do pacote
chegar à VM) com uma única regra de entrada: TCP 80/443 de qualquer origem (ou,
se o Cloudflare Proxy estiver ativo, restrito aos ranges de IP do Cloudflare) +
TCP 22 (SSH) restrito ao IP do operador/bastion. Nenhuma outra porta exposta —
Postgres/backend/frontend já não publicam porta nenhuma no Compose, então isso é
defesa em profundidade, não a garantia primária.

## 7. Estratégia de rede

- Uma única rede bridge Docker (`internal`) para todos os 4 containers — já
  implementada, sem mudança proposta.
- **Nenhum overlay/Swarm/Kubernetes** — desproporcional para um único host
  (`ADR-002`, §25).
- **Borda pública:** Cloudflare (DNS + proxy, modo laranja) na frente do VPS —
  esconde o IP real do VPS, absorve mitigação básica de DDoS/L7 no plano
  gratuito, e é o único ponto que precisa de TLS "de verdade" do ponto de vista do
  cliente (Cloudflare→Caddy pode usar um certificado "Full (strict)" com o
  certificado real do Caddy/Let's Encrypt — não "Flexible", que deixaria o trecho
  Cloudflare→VPS em texto plano). Também é o provedor DNS usado pelo desafio
  ACME DNS-01 do Caddy (§9) — com DNS-01, o proxy pode **permanecer sempre em
  modo laranja**, inclusive durante emissão/renovação de certificado (diferença
  em relação à revisão anterior deste documento, que ainda cogitava HTTP-01 e
  exigiria desligar o proxy temporariamente).
- **Host header trust:** confirmado (`runbook.md §21.1`) que o backend nunca lê
  `X-Forwarded-Host`, resolve tenant só pelo `Host` real da requisição que chega
  ao Caddy. Isso só é confiável de ponta a ponta quando o Caddy tiver um domínio
  real configurado (§8) — hoje (`CADDY_HOST=:80`) qualquer `Host` é aceito. Este é
  o item que fecha `SEC-TENANT-04`, tratado como bloqueador de go-live, não desta
  DT isoladamente.

## 8. Caddy Reverse Proxy

Sem mudança de desenho: reafirma `DT-011A.3` como a fonte de verdade
(`/api/*` → backend com prefixo removido; `/uploads/*` → backend com prefixo
mantido; catch-all → frontend). Este documento acrescenta:

- **Papel do Caddy no HTTPS** é tratado separadamente em §9, já que é
  literalmente o próximo item da lista da tarefa e o motivo mais concreto para a
  VPS real ser provisionada.
- **Trusted proxies do Caddy:** quando o Cloudflare Proxy estiver ativo, o Caddy
  deve ser configurado com a diretiva `trusted_proxies` apontando para os ranges
  de IP publicados pela Cloudflare (`https://www.cloudflare.com/ips/`) — isso é o
  que permite ao Caddy (e por extensão ao backend, se algum dia precisar) confiar
  em `X-Forwarded-For` vindo da Cloudflare sem aceitar spoofing de qualquer
  origem. **Não implementado antes desta DT porque não havia Cloudflare real** —
  agora que a topologia-alvo inclui Cloudflare, esta é uma decisão nova,
  registrada para a Sprint 12.3 (§27) implementar.

## 9. HTTPS automático

**Correção de inconsistência arquitetural (revisão desta DT):** o produto é
multi-tenant por subdomínio (`{tenant}.{PLATFORM_BASE_DOMAIN}`, `DT-011A.7`/
`.8`, hosts dinâmicos, um por empresa). Isso exige um certificado **wildcard**
(`*.{PLATFORM_BASE_DOMAIN}`) para cobrir qualquer subdomínio de tenant sem emitir
um certificado por empresa cadastrada. **O desafio ACME HTTP-01 não é capaz de
emitir certificado wildcard** — é uma limitação do próprio protocolo ACME, não
uma escolha de configuração: só o desafio **DNS-01** pode provar controle sobre
`*.dominio.tld`. A versão anterior deste documento recomendava HTTP-01 como
ponto de partida, o que teria bloqueado o próprio requisito de multi-tenancy por
subdomínio assim que a primeira empresa fosse cadastrada em produção. Corrigido
abaixo.

**Decisão final:** Caddy com ACME automático (Let's Encrypt), desafio **DNS-01
via Cloudflare** (provedor DNS já adotado para a zona, §7) — único mecanismo
compatível com certificado wildcard. Continua sendo zero-configuração manual de
renovação (o motivo original de escolher Caddy, `DT-011A.3`, não reaberto) —
muda apenas o modo de desafio.

**O que muda:** hoje `CADDY_HOST=:80` (endereço sem hostname) — Caddy nunca tenta
ACME para um endereço assim. Assim que `CADDY_HOST=*.dominio.tld` (wildcard,
domínio real com a zona gerenciada no Cloudflare, §7), o Caddy solicita e renova
o certificado wildcard automaticamente via DNS-01, sem exigir que a porta 80
esteja envolvida na validação.

**Implementação implica um Caddy customizado (registrado para a Sprint 12.3, não
feito aqui):** o desafio DNS-01 contra Cloudflare exige o módulo
`caddy-dns/cloudflare`, que não vem na imagem oficial `caddy:2-alpine` — precisa
de uma imagem Caddy construída com `xcaddy` incluindo esse módulo. Isso é
trabalho de implementação (Dockerfile novo para o Caddy), não decidido nem
criado nesta DT ("não implementar nada ainda") — apenas registrado como
pré-requisito concreto da Sprint 12.3.

**Credencial Cloudflare — permissão mínima, nunca no Caddyfile/repositório:**
- O Caddy autentica no DNS-01 via um **API Token** do Cloudflare (não a Global
  API Key, que teria acesso a toda a conta) escopado a **uma única permissão:
  `Zone:DNS:Edit`, restrita à zona `{PLATFORM_BASE_DOMAIN}` especificamente** —
  suficiente para criar/remover o registro `TXT _acme-challenge.*` que o DNS-01
  usa para provar controle da zona, nada além disso (sem acesso a outras zonas,
  sem acesso a Cloudflare Access/WAF/billing/outras contas).
- **Nunca commitado, nunca hardcoded no `Caddyfile`** — o `Caddyfile` referencia
  o token por variável de ambiente (`{env.CLOUDFLARE_API_TOKEN}`, sintaxe do
  Caddy), nunca o valor literal.
- **Tratado como secret de produção**, mesmo tratamento já dado a
  `JWT_SECRET`/`POSTGRES_PASSWORD`/`RESTIC_PASSWORD` (§16) — vive em
  `infra/env/production.env` (gitignored, `DT-011A.2`) e, a prazo, no mesmo
  gerenciador de segredos externo ainda não escolhido (§16, pendência já
  registrada, não nova).

**Tráfego HTTP→HTTPS da aplicação — sem mudança de papel:** o redirecionamento
HTTP→HTTPS que o Caddy já faz automaticamente para todo tráfego de aplicação
(browser do cliente, chamadas de API) **continua existindo normalmente** — isso
é ortogonal ao mecanismo de validação ACME. A mudança desta revisão é
exclusivamente sobre *como o Caddy prova ao Let's Encrypt que controla o
domínio* (DNS-01, não HTTP-01/porta 80) — não sobre como o Caddy trata requisições
HTTP reais de usuários, que seguem redirecionadas para HTTPS como já esperado.

**HTTP-01 — registrado como alternativa rejeitada para o wildcard** (não apenas
adiada, como a versão anterior deste documento colocava — genuinamente
inadequada para este requisito): ver `ADR-005` revisado (§25) e §26.

**HSTS:** ativado somente quando `CADDY_HOST` for um domínio real — nunca em
`:80`/localhost (`DT-011A.3 §10`, reafirmado, sem mudança nesta revisão).

## 10. PostgreSQL

Sem mudança de desenho: `postgres:17-alpine`, Flyway forward-only,
`clean-disabled: true`, pool HikariCP dimensionado (provisoriamente) para
~2 vCPU/4GB. Este documento acrescenta duas decisões novas:

### 10.1 Point-in-Time Recovery (PITR) — avaliado, não adotado agora

`DT-011A.5` já lista PITR como item futuro. Decisão desta DT: **não adotar PITR
nesta fase**. Motivo: PITR exige WAL archiving contínuo (armazenamento adicional,
maior superfície de configuração) para reduzir o RPO de 24h para minutos — um
ganho que não se justifica no estágio atual (cliente único/poucos clientes,
volume de escrita baixo, RPO de 24h já documentado e aceito como não-SLA
contratual). Revisitar quando o RPO de 24h deixar de ser aceitável para o
negócio, não por tuning arquitetural especulativo.

### 10.2 Réplica de leitura — avaliado, não adotado agora

Mesma lógica: nenhuma carga de leitura hoje justifica uma réplica dedicada. Fica
registrado como opção natural de escalabilidade vertical→horizontal (§21), não
como item desta fase.

## 11. Redis

**Este é o item genuinamente em aberto** que os DTs anteriores nunca resolveram
explicitamente (nem propuseram, nem rejeitaram com justificativa registrada) —
tratado aqui pela primeira vez.

### 11.1 Onde Redis apareceria, se introduzido

- **Rate limiting distribuído:** hoje `InMemoryRateLimiter` (`DT-011B.6A`) —
  correto e suficiente enquanto houver **um único processo backend**. Deixaria de
  funcionar corretamente (cada réplica teria seu próprio contador) no momento em
  que o backend escalar horizontalmente (§21) — esse é o gatilho concreto para
  Redis, não um limite de tempo arbitrário.
- **Cache de leitura** (ex.: `GET /public/sites/{slug}` — hoje resolvido a cada
  request contra Postgres): candidato natural se a carga de leitura pública
  crescer, mas não há sinal de que isso seja necessário hoje.
- **Fila de jobs assíncronos:** nenhum job assíncrono existe hoje (PDF é gerado
  em memória, síncrono, por request) — sem consumidor concreto, não há motivo
  para introduzir uma fila.

### 11.2 Decisão

**Não introduzir Redis nesta fase.** Justificativa:
1. O backend continua **stateless e single-instance** — nada hoje precisa de
   estado compartilhado entre processos.
2. Introduzir Redis agora seria exatamente o padrão que o projeto já rejeitou
   conscientemente em outros pontos (`DT-011A.2 §6.1.7`, sobre correlação de
   logs: *"a complexidade não se paga ainda"*) — mesma lógica se aplica aqui.
3. O gatilho para reconsiderar é claro e mensurável: **o dia em que o backend
   escalar para mais de uma réplica** (§21), o rate limiter em memória deixa de
   ser correto e Redis (ou um mecanismo equivalente) se torna necessário, não
   opcional.

Registrado como `ADR-003` (§25) — decisão consciente, não omissão.

## 16. Secrets

Sem mudança de mecanismo — `ProductionReadinessValidator` (backend) já falha o
boot se `JWT_SECRET`/`JWT_ISSUER`/`JWT_AUDIENCE`/CORS estiverem ausentes, em
placeholder, ou fracos (`DT-011A.2`, `DT-011B.6D`). Gap já registrado e não
fechado por esta DT (decisão consciente de não introduzir um gerenciador de
segredos dedicado — Vault etc. — desproporcional a um único VPS/cliente único,
`DT-011A.5 §34`): `RESTIC_PASSWORD`, a chave SSH da Storage Box, e (novo nesta
revisão) `CLOUDFLARE_API_TOKEN` precisam viver em um gerenciador de senhas
externo, produto ainda não escolhido — fica como item explícito da Sprint 12.2
(§27), não resolvido aqui.

**`CLOUDFLARE_API_TOKEN` — regras específicas (novo nesta revisão, §9):**
- **Permissão mínima:** escopo `Zone:DNS:Edit`, restrito à zona
  `{PLATFORM_BASE_DOMAIN}` especificamente — nunca um token de conta inteira,
  nunca a Global API Key legada do Cloudflare (essa não tem como ser escopada a
  uma única zona/permissão).
- **Nunca no `Caddyfile` nem em qualquer arquivo versionado** — só como variável
  de ambiente (`infra/env/production.env`, gitignored, mesmo mecanismo de
  `JWT_SECRET`/`POSTGRES_PASSWORD`), referenciada no `Caddyfile` por
  `{env.CLOUDFLARE_API_TOKEN}`.
- **Rotação:** se o token vazar ou precisar ser trocado, é revogável
  diretamente no painel Cloudflare (My Profile → API Tokens) sem impacto em
  nenhum outro secret do sistema — não compartilha material criptográfico com
  `JWT_SECRET`/`RESTIC_PASSWORD`.

## 18. Observabilidade

**Decisão desta DT: continuar deliberadamente sem uma stack de observabilidade
completa (Prometheus/Grafana/Loki/Sentry) nesta fase** — mesma justificativa de
proporcionalidade usada em todos os DTs anteriores. O que muda com este
documento é tornar explícito **o que já existe e cobre parte da necessidade**,
para não ser confundido com "zero observabilidade":

- **Segurança:** CodeQL + gitleaks + Dependabot + scans de dependência
  (`docs/security/security-baseline.md`, `DT-011B.7`) — já é observabilidade de
  postura de segurança, mesmo não sendo observabilidade de runtime.
- **Saúde operacional:** os health checks (§19) já dão um sinal binário
  up/down por serviço, consumido pelo próprio Docker (`restart: unless-stopped`
  + `condition: service_healthy`).
- **O que continua genuinamente ausente:** métricas de latência/throughput,
  tracing distribuído, alertas proativos (algo além de "o container reiniciou"),
  dashboards.

**Recomendação mínima e proporcional para 12.x (não implementada aqui):** Spring
Boot Actuator já expõe `/actuator/health` — habilitar `/actuator/metrics` e
`/actuator/prometheus` (dependência `micrometer-registry-prometheus`, já
compatível com o Actuator existente) é a menor mudança que abre a porta para uma
stack de métricas futura, **sem** exigir Prometheus/Grafana rodando agora — os
endpoints existiriam, mas nada os raspa até que valha a pena. Registrado como
opção de baixo custo para a Sprint 12.5 avaliar, não uma decisão tomada aqui.

## 22. Escalabilidade futura

**Hoje:** um único VPS, um único Postgres, um único backend, um único frontend —
sem alta disponibilidade, sem failover automático (`DT-011A.5 §17`, não
revisado). Este documento registra o caminho de crescimento, em ordem de menor
para maior custo/complexidade — nenhum destes passos é implementado agora:

1. **Escala vertical primeiro** (trocar CPX21 por CPX31/CPX41 — §22-custo) — menor
   esforço, resolve a maioria dos cenários de crescimento moderado, zero mudança
   de arquitetura.
2. **Múltiplas réplicas de backend** atrás do Caddy (ainda um único VPS ou VPS
   adicional) — **gatilho direto para adotar Redis** (§11): rate limiting em
   memória deixa de ser correto com mais de uma réplica.
3. **Postgres gerenciado ou réplica de leitura** — só depois do passo 2, quando
   o banco (não o backend) for o gargalo medido, não assumido.
4. **Múltiplos hosts/regiões** — fora do horizonte razoável para esta fase do
   produto; não detalhado além de "Cloudflare já abstrai a origem, então trocar
   de host/região é possível sem mudar DNS para o cliente final."

**Princípio geral adotado (`ADR-004`, §25):** nenhum passo de escala é adotado
preventivamente — cada um é uma resposta a um gargalo medido, não a uma
previsão. Isso é uma continuação deliberada do padrão já usado em todos os DTs
anteriores (rate limiting em memória em vez de Redis desde o início, sem
observabilidade até que faça falta, etc.), não uma decisão nova de filosofia.

## 24. Riscos

| Risco | Impacto | Mitigação já existente | Mitigação pendente |
|---|---|---|---|
| VPS único, sem HA — indisponibilidade do host derruba tudo | Alto (mas aceito, `DT-011A.5 §17`) | Backup diário (RPO≤24h), restart automático de containers | Nenhuma HA real prevista nesta fase (§22) |
| `Host` header não validado na borda até domínio real existir (`SEC-TENANT-04`) | Médio, só até §8/§9 fecharem | Nenhuma hoje | Fechado automaticamente quando `CADDY_HOST` for domínio real |
| Restore nunca testado contra VPS/Storage Box reais | Alto (RTO real desconhecido) | Testado localmente com sucesso | Executar 1 restore completo real antes do go-live (§14, bloqueador já registrado) |

| Nenhuma observabilidade de latência/erro em produção — problemas de performance só aparecem via reclamação de cliente | Médio | Health checks binários (§19) | Avaliar `/actuator/prometheus` de baixo custo (§18) numa subsprint futura |

## 25. Decisões arquiteturais (ADRs)

Registradas aqui pela primeira vez de forma consolidada — decisões já implícitas
em DTs anteriores ganham um identificador formal; decisões novas desta DT também.

### ADR-001 — Monólito modular (backend + frontend), não microsserviços
**Contexto:** equipe pequena, produto em validação de mercado, um cliente/poucos
clientes.
**Decisão:** dois processos (Spring Boot, Next.js), módulos internos por domínio.
**Alternativas rejeitadas:** microsserviços por domínio (custo de rede/deploy/
observabilidade sem benefício de escala ainda necessário).
**Reversível:** sim — os módulos internos já são um primeiro corte de fronteiras,
se algum dia justificar extração.

### ADR-002 — Docker Compose de host único, não Kubernetes/Swarm
**Contexto:** um VPS, sem necessidade de orquestração multi-host hoje.
**Decisão:** `docker-compose.prod.yml` como a unidade de implantação inteira.
**Alternativas rejeitadas:** Kubernetes (complexidade operacional desproporcional
para 4 containers em 1 host), Swarm (feature parity pior que Compose para este
caso de uso, sem ganho real).
**Reversível:** sim, com esforço — migrar para Kubernetes é um projeto à parte,
não uma mudança incremental, se algum dia necessário.

### ADR-003 — Sem Redis até haver mais de uma réplica de backend
**Contexto:** §11.
**Decisão:** manter rate limiting em memória, sem cache distribuído, sem fila.
**Alternativas rejeitadas:** introduzir Redis preventivamente "para o futuro".
**Reversível:** sim — gatilho de reversão explícito e mensurável (§21 passo 2).

### ADR-004 — Escalar reativamente, não preventivamente
**Contexto:** §22.
**Decisão:** cada passo de escala (vertical → réplicas → Postgres gerenciado →
multi-host) só é adotado em resposta a um gargalo medido.
**Alternativas rejeitadas:** provisionar para uma carga hipotética futura.
**Reversível:** N/A — é um princípio de processo, não uma peça de infraestrutura.

### ADR-005 — Caddy com ACME automático via DNS-01/Cloudflare (revisado nesta DT), não HTTP-01, não certbot/manual
**Contexto:** §9 — herda a escolha original de `DT-011A.3` de usar Caddy com ACME
automático; **revisa** a versão anterior deste documento, que recomendava
HTTP-01 como ponto de partida. Correção: o produto é multi-tenant por
subdomínio dinâmico (`{tenant}.{PLATFORM_BASE_DOMAIN}`), exige certificado
**wildcard**, e HTTP-01 estruturalmente não emite wildcard — não é uma
preferência de simplicidade, é uma incompatibilidade de protocolo.
**Decisão:** DNS-01 via API do Cloudflare (`caddy-dns/cloudflare`, exige imagem
Caddy customizada via `xcaddy` — implementação da Sprint 12.3, não feita aqui),
token com permissão mínima `Zone:DNS:Edit` escopada à zona, nunca commitado
(§16). Cloudflare Proxy permanece sempre em modo laranja — DNS-01 não exige
desligá-lo.
**Alternativas rejeitadas:**
- **HTTP-01** — rejeitado especificamente para este caso de uso: incapaz de
  emitir certificado wildcard, o que bloquearia a própria arquitetura
  multi-tenant por subdomínio assim que o primeiro tenant fosse provisionado em
  produção. Continuaria válido apenas se o produto abandonasse subdomínios
  dinâmicos por tenant — não é o caso.
- **Certificado manual** (Certbot fora do Caddy, gestão de renovação própria) —
  trabalho redundante com o que o Caddy com DNS-01 já faz automaticamente.
- **Um certificado por subdomínio** (em vez de wildcard), emitido sob demanda a
  cada novo tenant — tecnicamente possível com HTTP-01 + "on-demand TLS" do
  Caddy, mas descartado por ser operacionalmente mais frágil (depende de tráfego
  real chegar para disparar a emissão, rate limits do Let's Encrypt por
  certificado individual em vez de um único wildcard) e por já existir uma
  decisão de produto por subdomínios dinâmicos que o wildcard atende de forma
  mais direta.
**Reversível:** sim, com esforço — trocar de modo de desafio exige reconstruir a
imagem Caddy (módulo DNS-01) e reconfigurar `CADDY_HOST`; não é uma mudança de
uma linha, mas também não é um redesenho de arquitetura.

### ADR-006 — Sem observabilidade completa; Actuator/Prometheus como opção de baixo custo, não decisão tomada
**Contexto:** §18.
**Decisão:** não adotar Grafana/Prometheus/Loki/Sentry agora; registrar
`/actuator/prometheus` como extensão de custo quase zero para quando fizer
sentido raspar métricas.
**Alternativas rejeitadas:** adotar uma stack completa preventivamente.
**Reversível:** sim.

## 26. Alternativas rejeitadas (fora das já cobertas nos ADRs)

- **Vercel/Railway/PaaS gerenciado** para o frontend/backend: mencionados como
  desatualizados/incorretos em `docs/roadmap.md`, já corrigido em `DT-011A.6`.
  Rejeitados porque a arquitetura multi-tenant self-hosted já está construída em
  torno de um VPS único com Caddy — migrar para PaaS gerenciado seria um
  redesenho, não uma opção incremental neste ponto.
- **AWS/GCP/Azure completos:** custo e complexidade desproporcionais para a escala
  atual — Hetzner já é a escolha registrada desde `DT-011A.3`, reafirmada aqui
  com números concretos (§23).
- **Nginx/Traefik em vez de Caddy:** Caddy já escolhido (`DT-011A.3`) por ACME
  automático nativo sem plugin — não reaberto.
- **ACME HTTP-01 para o certificado wildcard** (revisão desta DT, §9/`ADR-005`):
  rejeitado — incapaz de emitir wildcard, incompatível com a exigência de
  subdomínio dinâmico por tenant. Diferente dos demais itens desta lista, não é
  uma questão de proporcionalidade/custo — é uma incompatibilidade técnica direta
  com um requisito já decidido do produto.
- **PITR/réplica de leitura Postgres agora:** avaliados e adiados (§10.1/§10.2).
- **Gerenciador de segredos dedicado (Vault etc.) agora:** avaliado e adiado
  (`DT-011A.5 §34`, reafirmado §16).
