## 1. Modelo de dados

Avaliadas as 5 opções do enunciado original:

| Opção | Veredito | Motivo |
|---|---|---|
| A — tabela dedicada `password_reset_tokens` | **Escolhida** | Reaproveita 100% do padrão já validado por `owner_invites`; sem sobrecarregar semântica alheia |
| B — reaproveitar `owner_invites` | Rejeitada | `owner_invites` está semanticamente amarrado a "usuário `PENDING` definindo a primeira senha"; um usuário que esqueceu a senha já está `ACTIVE`. Misturar os dois ciclos de vida complicaria os testes/invariantes já existentes de `InviteService` |
| C — reaproveitar `refresh_tokens` | Rejeitada | Modelo de confiança diferente: refresh token pertence a uma sessão já autenticada; token de reset é emitido para um requisitante **não autenticado** |
| D — token stateless assinado | Rejeitada | Não dá para revogar sem uma blocklist server-side — nesse ponto já se precisa de uma tabela mesmo |
| E — outra | N/A | Nenhuma alternativa proporcional identificada |

**Decisão: tabela dedicada `password_reset_tokens`**, colunas espelhando `owner_invites`:

```
password_reset_tokens
  id          UUID PK
  user_id     UUID NOT NULL REFERENCES users(id)
  token_hash  VARCHAR(64) UNIQUE NOT NULL   -- SHA-256 hex (TokenHasher), nunca plaintext
  expires_at  TIMESTAMP WITH TIME ZONE NOT NULL
  used_at     TIMESTAMP WITH TIME ZONE NULL
  revoked_at  TIMESTAMP WITH TIME ZONE NULL
  created_by  UUID NULL REFERENCES users(id)  -- NULL = autosserviço; SUPER_ADMIN id = gerado via admin (§15)
  created_at  TIMESTAMP WITH TIME ZONE NOT NULL
  updated_at  TIMESTAMP WITH TIME ZONE NOT NULL

  INDEX idx_password_reset_tokens_user_id (user_id)
```

**Política de múltiplos tokens**: no máximo um token **válido** (não usado, não revogado, não expirado) por usuário a qualquer momento — toda nova emissão revoga (`revoked_at = now()`) qualquer token ainda válido do mesmo usuário antes de criar o novo, exatamente como `InviteService.createInvite`/`reissueInvite` já fazem. Isso vale tanto para emissão via `forgot` quanto via endpoint administrativo (§15) — é o mesmo `PasswordResetTokenService` por trás dos dois.

Adicionalmente, `users` ganha uma coluna nova para a estratégia de invalidação de sessões (decisão revisada, §5): `auth_version BIGINT NOT NULL DEFAULT 0`. Não é uma tabela nova — é uma coluna na tabela `users` já existente, consolidada na mesma migration da tabela acima (§14).

## 2. Solicitação de reset

`POST /auth/password/forgot`, `permitAll`.

Request: `{ "email": "string, obrigatório, formato de e-mail" }` — validação de formato via Bean Validation (`400` se inválido), mas **nenhuma outra validação de negócio jamais é exposta**.

**Resposta pública sempre idêntica, sempre `200`, independente de o e-mail existir, do estado da conta, ou de a solicitação estar em cooldown:**
```json
{ "message": "Se existir uma conta para este email, as instruções foram geradas." }
```

Busca por e-mail: **case-insensitive** (novo método `UserRepository.findByEmailIgnoreCase`), diferente de `register`/`login`, que continuam case-sensitive hoje (comportamento pré-existente, fora de escopo mudar aqui — registrado como inconsistência conhecida, não corrigida nesta sprint). O mesmo e-mail normalizado (lowercase) é a chave usada pelo cooldown (§7).

Comportamento interno (nunca observável externamente — resposta é sempre a mesma):

| Estado | Cria token? |
|---|---|
| E-mail não existe | Não |
| `OWNER` `ACTIVE` + Company `ACTIVE` | Sim (se fora do cooldown — §7) |
| `OWNER` `ACTIVE` + Company `INACTIVE` | Não — mesmo que criasse, o reset nunca completaria (§4/§6) |
| `OWNER` `PENDING` | Não — fluxo correto para quem nunca definiu senha é reemissão de convite (mecanismo já existente), não recovery |
| `OWNER`/`SUPER_ADMIN` `INACTIVE` (desabilitado) | Não |
| `SUPER_ADMIN` `ACTIVE` | Sim (sem checagem de Company — não tem; sujeito ao mesmo cooldown) |

Não criar o token quando o estado já é inelegível evita linhas mortas na tabela; como a resposta pública é idêntica em todos os casos, isso não é observável de fora. **`reset` (§4) sempre revalida o estado atual no momento da conclusão**, então uma mudança de estado entre a solicitação e a tentativa de conclusão continua bloqueada mesmo que o token tenha sido criado antes.

## 3. Entrega manual do link

Separação explícita entre **criação do token** (`PasswordResetTokenService`, um único ponto no backend, compartilhado pelos dois canais abaixo) e **entrega**:

| Ambiente | Canal |
|---|---|
| Fora de `prod` (local/dev/test) | `POST /auth/password/forgot` inclui `debugToken`/`debugResetLink` na resposta — **somente quando um token novo foi de fato criado nesta chamada** (conta existe, elegível, fora de cooldown). Se qualquer uma dessas condições falhar, os campos ficam **ausentes** (não `null` — omitidos do JSON), exatamente como em produção — ver §13 |
| `prod` | `debugToken`/`debugResetLink` **nunca** aparecem no corpo da resposta, nem como `null`. Único canal: SUPER_ADMIN gera o link pela tela `/admin/companies/{id}` (§15/§15), copia, entrega manualmente (Slack/WhatsApp/etc.) — mesmo modelo já usado para convites de OWNER |

Rejeitadas explicitamente: opção C (logar o token) — nunca, em nenhum ambiente; opção D (CLI/script) — infraestrutura desproporcional para o que A/B já resolvem reaproveitando padrões existentes.

## 4. Reset da senha

`POST /auth/password/reset`, `permitAll`.

Request: `{ "token": "string, obrigatório", "newPassword": "string, obrigatório, 8–128 chars" }` (mesma política de `RegisterRequest`/`AcceptInviteRequest`).

**Resposta uniforme aprovada — nenhuma distinção pública entre os motivos de falha do token/conta:**
- Token inexistente, expirado, usado, revogado, `User` não `ACTIVE`, ou (para `OWNER`) `Company` não `ACTIVE`, ou `OWNER` `PENDING` — **todos** resultam em:
  - Status `422 Unprocessable Entity`
  - `ProblemDetail` com o mesmo título/mensagem de sempre para `BusinessRuleException` (nenhuma classe de exceção nova, nenhuma mudança em `GlobalExceptionHandler`), detalhe exatamente:
    ```
    "O link de recuperação é inválido ou não está mais disponível."
    ```
  - **Não há mais `404` para token inexistente** — decisão revisada em relação à versão anterior deste DT (que usava `404` nesse caso, espelhando `InviteService`). Aqui a uniformidade venceu explicitamente sobre a consistência com o padrão de convite, por instrução direta.

**Única exceção deliberada à resposta uniforme**: nova senha igual à senha atual (`passwordEncoder.matches`) → também `422`, mas com mensagem **específica**: "A nova senha deve ser diferente da atual." Isso não viola o princípio anti-enumeração — o requisitante já conhece as duas senhas sendo comparadas (a atual, que ele está tentando definir de novo, e a nova), então a distinção não revela nada sobre o estado da conta que ele não controle.

Ordem de validação (transacional, tudo ou nada):
1. Hash do token → busca; se ausente, **ou** encontrado mas não utilizável por qualquer motivo do parágrafo acima → `422` genérico.
2. Nova senha == senha atual → `422` específico.
3. Política de senha (`@Size`) → `400` (Bean Validation, convenção padrão — roda antes ou depois da consulta ao token, tanto faz, já que não há distinção externa a proteger entre os dois).
4. Sucesso: atualiza `passwordHash`, marca `used_at`, incrementa `auth_version`, revoga todos os refresh tokens do usuário (§5) — tudo na mesma transação Spring.

**Concorrência**: duas conclusões simultâneas com o mesmo token não podem ambas suceder. Mitigação concreta (sem `@Version`, sem lock explícito — nenhum precedente no projeto usa isso): consumo do token via `UPDATE` condicional que só afeta uma linha se `used_at IS NULL AND revoked_at IS NULL AND expires_at > now()`, checando o número de linhas afetadas antes de prosseguir — se `0` linhas, mesma resposta `422` genérica do passo 1. Fecha a corrida de forma atômica no banco, sem infraestrutura nova. *(Nota: `InviteService.acceptInvite` tem a mesma classe de risco, não tratada hoje — fora de escopo corrigir retroativamente aqui.)*

Resposta de sucesso `200`: `{ "message": "Senha atualizada. Inicie sessão novamente." }` — **sem login automático, sem tokens retornados**.

## 5. Invalidação de sessões (estratégia revisada: `auth_version`)

Estratégia anterior deste DT (`password_changed_at` comparado com `iat` do JWT) foi **substituída** por instrução explícita por `auth_version` — comparação de igualdade de um contador, não de timestamps.

| Opção | Veredito |
|---|---|
| `token_version`/`auth_version` (contador incremental, comparado por igualdade) | **Escolhida** (decisão revisada) |
| `password_changed_at` comparado com `iat` do JWT | Descartada nesta revisão — funcionalmente próxima, mas comparação por igualdade de inteiro é mais simples de raciocinar do que comparação temporal (sem depender de que os relógios de emissão/verificação nunca se desalinhem) |
| Só revogar refresh tokens, aceitar access token até expirar | Rejeitada — mesma razão da versão anterior: janela de até 15 min evitável a baixo custo |
| Redis/cache distribuído | Explicitamente descartado pelo enunciado |

**Modelo final:**
- `users.auth_version BIGINT NOT NULL DEFAULT 0` — nova coluna. `DEFAULT 0` garante que nenhuma sessão existente é invalidada só por aplicar a migration (todo usuário já existente começa em `0`, e qualquer JWT emitido a partir daí também carrega `authVersion=0` até o primeiro reset).
- **JWT ganha uma claim nova**: `authVersion` (diferente da estratégia anterior, que reaproveitava `iat` sem precisar de claim nova — aqui uma claim nova é necessária e aceita, por instrução explícita). `JwtService.generateAccessToken(User user)` passa a incluir `.claim("authVersion", user.getAuthVersion())`.
- `JwtPrincipal` ganha um campo `long authVersion`, populado por `JwtAuthenticationFilter` a partir de `claims.get("authVersion", Long.class)`.
- `ActiveAccountFilter`: a mesma projeção escalar de `User` já usada para `status` (consulta de uma única entidade, sem `JOIN` ad-hoc — lição da sprint anterior, mantida) ganha uma segunda coluna: `SELECT u.status AS status, u.authVersion AS authVersion FROM User u WHERE u.id = :userId`. A checagem de `Company.status` para `OWNER` continua como uma consulta separada, exatamente como hoje.
- Regra de decisão: nega (mesma resposta 401 "Account Disabled" já usada para `Company`/`User` inativos, nenhum formato novo) se `principal.authVersion() != view.getAuthVersion()` — **desigualdade em qualquer direção**, não só "mais antigo que" — mais simples de raciocinar e cobre qualquer cenário futuro de invalidação em massa, não só reset de senha.
- `login()`/`refresh()` (`AuthService`) já recebem o `User` completo antes de chamar `jwtService.generateAccessToken(user)` — nenhuma mudança de fluxo, só o `JwtService` passa a ler mais um campo do mesmo objeto que já tinha em mãos. Todo token novo emitido (login, refresh, ou o login automático que `InviteService.acceptInvite` já faz) carrega o `auth_version` **atual** do usuário no momento da emissão.
- Reset bem-sucedido (§4, passo 4), na mesma transação: `passwordHash` atualizado, `auth_version` incrementado (`+1`), todos os refresh tokens do usuário revogados, `password_reset_tokens.used_at` marcado. O incremento por si só já torna **qualquer** access token emitido antes do reset inválido na próxima requisição — nenhuma outra ação é necessária para "esquecer" tokens antigos.

**Impacto em DTOs internos/JWT**: `authVersion` é uma claim interna do JWT — **não é exposta em nenhum DTO de resposta pública** (`AuthResponse`, `MeResponse`, `UserResponse` continuam exatamente como são hoje). O contrato público de `/auth/login`/`/auth/refresh`/`/auth/me` não muda em nada observável pelo frontend — só o conteúdo *interno* do token JWT (que o frontend já trata como opaco) ganha mais uma claim.

Refresh tokens: novo método `@Modifying @Query("UPDATE RefreshToken r SET r.revoked = true WHERE r.userId = :userId AND r.revoked = false")` em `RefreshTokenRepository`, chamado dentro da mesma transação do reset — inalterado em relação à versão anterior deste DT.

## 6. OWNER / Company status

| Estado | Pode solicitar (`forgot`)? | Pode concluir (`reset`)? |
|---|---|---|
| OWNER `ACTIVE` + Company `ACTIVE` | Sim | Sim |
| OWNER `ACTIVE` + Company `INACTIVE` | Resposta `200` genérica; sem `debugResetLink`; token não é criado | Não — `422` genérico (mesmo que um token antigo ainda exista de antes da desativação, revalidado na conclusão) |
| OWNER `PENDING` | Resposta `200` genérica; token não é criado | N/A — usar reemissão de convite; se tentado mesmo assim, `422` genérico |
| OWNER `INACTIVE` (desabilitado) | Resposta `200` genérica; token não é criado | `422` genérico |
| SUPER_ADMIN `ACTIVE` | Sim | Sim |
| SUPER_ADMIN `INACTIVE` (desabilitado) | Resposta `200` genérica; token não é criado | `422` genérico |
| E-mail inexistente | Resposta `200` genérica idêntica, com tempo de resposta razoavelmente uniforme em relação aos demais casos (§9) | N/A |

A resposta pública de `forgot` é **sempre** a mesma string, em todos os casos. "Admin deve reativar antes?" — **sim**: gerar link de recuperação (§15) para um OWNER cujo status não é `ACTIVE` retorna `409` — o SUPER_ADMIN precisa reativar a conta primeiro.

## 7. Token lifetime e cooldown

**TTL: 30 minutos** (aprovado). Justificativa: curto o suficiente para limitar a janela de exposição caso o link vaze; longo o suficiente para a realidade atual de entrega manual (Slack/WhatsApp) sem pressa artificial. Comparação deliberada com `owner_invites` (7 dias): modelo de ameaça bem diferente — convite não tem relação temporal com uma tentativa de login ativa; reset de senha tem.

**Cooldown: 3 minutos por usuário, aprovado, entra nesta sprint.** Reaproveita a própria tabela `password_reset_tokens` — nenhuma tabela/coluna nova, nenhum Redis. Antes de criar um novo token, o serviço verifica se já existe um token **válido** (não expirado/usado/revogado) criado há menos de 3 minutos para aquele `userId` (resolvido a partir do e-mail já normalizado — case-insensitive, §2); se sim, a solicitação **não cria nem revoga nada**, mas a resposta pública continua sendo exatamente o mesmo `200` genérico — o cooldown nunca é observável de fora, nem em dev (§3: sem token novo criado ⇒ sem `debugResetLink`, mesmo fora de `prod`).

- Uso único: `used_at`, mesma semântica de `owner_invites`.
- Nova solicitação (fora do cooldown) revoga a anterior: sim (§1).
- Limpeza de tokens expirados: nenhum job nesta sprint — mesmo padrão de `owner_invites`/`estimate_shares`. Backlog futuro, não bloqueante.
- Timezone: UTC em todo lugar (`Instant`/`TIMESTAMP WITH TIME ZONE`).
- Clock em testes: sem `Clock` injetável — testes manipulam `expiresAt`/`createdAt` diretamente via repositório após criação, mesmo padrão de `InviteAcceptanceTest.expiredToken_isRejected`.

## 8. Rate limiting / abuso

Confirmado por inspeção: **não existe rate limiting em nenhum lugar do backend hoje** (nem para `/auth/login`).

- **Cooldown de 3 minutos por conta**: requisito **desta sprint** (§7), única camada de proteção implementada agora.
- **Rate limiting por IP na borda**: **continua recomendado para a Sprint 11C** (Caddy `rate_limit` ou Cloudflare) — não implementado agora.
- **Classificação**: ausência de rate limiting por IP **não bloqueia o desenvolvimento local** nem a conclusão desta sprint, mas **deve constar explicitamente no checklist de go-live** (mesma terminologia "BLOCKER FOR GO-LIVE" já usada no runbook para TLS) — antes de expor `/auth/password/forgot` publicamente em produção real com domínio/DNS reais (Sprint 11C+), essa camada deveria existir.

## 9. Segurança

- **Account enumeration**: fechado por design em ambas as pontas — `forgot` sempre `200` idêntico; `reset` sempre `422` idêntico (exceto a única exceção justificada do §4).
- **Token brute force**: token de 160 bits (`SecureTokenGenerator`) — espaço de busca inviável; TTL de 30 min limita ainda mais a janela.
- **Replay**: `used_at` de uso único + `UPDATE` condicional atômico (§4) fecham replay e corrida de conclusão simultânea.
- **Token leakage / em logs**: nunca logado em plaintext, em nenhum ambiente (§3/§20).
- **Token em URL vs Referer/histórico/CSP**: ver §10 — fragmento, nunca enviado ao servidor; leitura única, removido da barra de endereço imediatamente após leitura; nunca persistido em `localStorage`/`sessionStorage`; nenhum recurso de terceiros na página de reset.
- **CSP/CSRF**: nenhuma mudança necessária — páginas públicas simples com `POST` via `fetch`; CSRF não se aplica (o token no corpo da requisição já é a prova de posse, não cookies de sessão).
- **Troca de senha por usuário desativado**: impossível — revalidado na conclusão (§4/§6).
- **Sessões antigas**: fechadas por `auth_version` (access tokens) + revogação em massa (refresh tokens), §5.
- **Timing differences**: `forgot` deve fazer trabalho computacional equivalente independentemente de o e-mail existir (evitar que a ausência de um hash bcrypt "real" torne a resposta para e-mail inexistente mensuravelmente mais rápida) — recomendação de implementação, a validar em code review.
- **Race conditions**: cobertas em §4.
- **Múltiplas solicitações**: cobertas pelo cooldown (§7) e pela revogação do token anterior (§1).
- **Rollback transacional**: toda a operação de `reset` (senha + `used_at` + `auth_version` + revogação de refresh tokens) é uma única transação Spring.

## 10. Link de reset

**Formato aprovado**: `/reset-password#token=<token-em-texto-puro>` — fragmento, não query string. Deliberadamente diferente de `/invite?token=...` (Sprint 11A.7, query string) — ver justificativa abaixo; a divergência é intencional e não retroage sobre o convite existente.

**Comportamento obrigatório no frontend** (proposto para o Codex, não implementado aqui):
1. Ler o token de `window.location.hash` (nunca de `useSearchParams()`, que não enxerga fragmentos).
2. Manter o token **somente em memória** (estado do componente React) durante o preenchimento do formulário — nunca gravado em `localStorage`/`sessionStorage`/cookie.
3. Imediatamente após a leitura, remover o fragmento da barra de endereço com `history.replaceState(null, "", window.location.pathname + window.location.search)` — a URL visível deixa de conter o token assim que a página termina de montar, antes de qualquer interação do usuário.
4. Nunca enviar o token para analytics/telemetria (não há nenhum provedor no projeto hoje, mas a regra vale para qualquer futuro).
5. A página `/reset-password` não deve carregar nenhum recurso de terceiros (sem scripts/fontes/imagens externas) — evita qualquer superfície de correlação/observação da página que contém o token.

Justificativa da divergência com `/invite?token=`: um fragmento nunca é enviado ao servidor em nenhuma requisição HTTP — não aparece em logs de acesso do Caddy (que hoje registra `request.uri` completo, incluindo query string), não é enviado como `Referer`, não passa por proxy/CDN futuro. Implementação em Next.js é igualmente simples (`"use client"`, ler `window.location.hash` num `useEffect`). Nenhuma mudança de backend é necessária para suportar isso — o backend só constrói a string do link; o fragmento é 100% interpretado no browser.

Isso **não** corrige a exposição já existente de `/invite?token=...` nos logs do Caddy — fora de escopo retroagir nesta sprint. Browser history: mesmo removendo o fragmento da barra visível via `history.replaceState`, a entrada original com o fragmento pode já estar no histórico do browser (comportamento depende do browser) — risco residual aceito, mitigado pelo TTL curto (30 min) e uso único. Analytics: não aplicável, nenhum provedor existe no projeto.

## 11. Frontend (proposto para o Codex — não implementado aqui)

Rotas novas:
- `/forgot-password` (pública) — formulário de e-mail, resposta sempre genérica, link "Voltar ao login".
- `/reset-password` (pública) — comportamento de leitura/descarte do token conforme §10; formulário de nova senha + confirmação; estados: carregando, token ausente na URL, inválido/expirado/usado (todos a mesma mensagem genérica, refletindo o `422` uniforme do backend), sucesso; em sucesso, **não** faz login automático — redireciona para o login correto (§12).

- `/admin/login` → `/forgot-password?variant=admin`.

## 12. OWNER e SUPER_ADMIN — mesmo fluxo

Confirmado: backend usa **exatamente o mesmo** par de endpoints públicos para os dois papéis — `AuthService`/`PlatformUserDetails` já tratam OWNER e SUPER_ADMIN de forma uniforme. Nenhuma tabela, token ou endpoint público duplicado.

O "retorno para o login certo" é resolvido **inteiramente no frontend**:
- `/forgot-password?variant=admin` (vindo de `/admin/login`) propaga `variant=admin` como query param comum até `/reset-password?variant=admin#token=...`.
- Em sucesso, `/reset-password` lê `variant` (via `useSearchParams()`, sem tocar no fragmento) e redireciona para `/admin/login` se `variant === "admin"`, senão `/login`.
- O link gerado pelo SUPER_ADMIN (§15) é sempre para um OWNER — nunca precisa de `variant=admin`.

## 13. Contratos congelados (backend ↔ frontend)

### `POST /auth/password/forgot` — `permitAll`
Request: `{ "email": "string" }`
Response `200` (sempre, em todos os cenários):
```json
{ "message": "Se existir uma conta para este email, as instruções foram geradas." }
```
Fora de `prod`, **e somente quando um token novo foi de fato criado nesta chamada**, dois campos adicionais aparecem no corpo (ausentes — não `null` — em qualquer outro caso, incluindo em `prod`):
```json
{
  "message": "Se existir uma conta para este email, as instruções foram geradas.",
  "debugToken": "raw-token",
  "debugResetLink": "https://.../reset-password#token=raw-token"
}
```
Erros: `400` e-mail malformado. Nunca `404`/`422` por qualquer motivo de negócio.

### `POST /auth/password/reset` — `permitAll`
Request: `{ "token": "string", "newPassword": "string (8–128)" }`
Response `200`: `{ "message": "Senha atualizada. Acesse sua conta novamente." }`
Erros:
- `422` — token inexistente, expirado, usado, revogado, ou conta/empresa não elegível — **sempre a mesma mensagem**: `"O link de recuperação é inválido ou não está mais disponível."`
- `422` — nova senha igual à atual — mensagem específica: `"A nova senha deve ser diferente da atual."`
- `400` — política de senha (Bean Validation).

### `POST /admin/companies/{companyId}/owners/{ownerId}/password-reset` — `hasRole('SUPER_ADMIN')`
Sem corpo de request (nenhum campo de senha — este endpoint nunca define a senha diretamente, só emite um token).
Response `201`:
```json
{ "resetLink": "https://.../reset-password#token=...", "expiresAt": "2026-08-01T12:30:00Z" }
```
Erros: `404` company/owner inexistente ou owner não pertence à company (mesmo padrão já usado por `reissueInvite`/`revokeInvite`) · `409` owner não está `ACTIVE`.

Não é necessário nenhum tratamento especial para "não pode ser usado para outro SUPER_ADMIN": estruturalmente impossível — um `SUPER_ADMIN` tem `companyId = null` (Sprint 11A.7), portanto nunca aparece na lista de owners de nenhuma `companyId` real; o lookup `requireOwnerInCompany` (mesmo padrão de `AdminCompanyService`) já garante isso sem checagem extra.

Enums/estados envolvidos: `UserStatus` (`ACTIVE, INACTIVE, PENDING` — inalterado), `CompanyStatus` (`ACTIVE, INACTIVE` — inalterado). Nenhum enum novo. Nenhuma claim nova exposta em DTO público (§5).

## 15. Bootstrap / Admin

**Entra nesta sprint**: `POST /admin/companies/{companyId}/owners/{ownerId}/password-reset` (§13) — ação "Gerar link de recuperação" na tela `/admin/companies/{id}` já existente, ao lado de "reemitir convite"/"revogar convite". Reaproveita o mesmíssimo `PasswordResetTokenService` do fluxo público.

Regras aprovadas, todas já refletidas no contrato do §13:
- Apenas `SUPER_ADMIN` (`@PreAuthorize("hasRole('SUPER_ADMIN')")`, mesmo padrão do resto de `AdminController`).
- Owner deve pertencer à company do path (`404` caso contrário).
- Owner deve estar `ACTIVE` (`409` caso contrário) — força reativação explícita antes.
- Revoga qualquer token de reset anterior ainda válido do mesmo usuário antes de criar o novo (mesma política de único-token-válido do §1).
- Retorna o link novo **uma única vez**, na resposta — nunca reexibido depois (mesmo modelo de convite).
- Nunca loga o token.
- **Não** cria um endpoint global `/admin/users` — a ação vive dentro do detalhe da company, como todo o resto da gestão de owners.
- **Não** redefine a senha diretamente — o SUPER_ADMIN nunca recebe/envia `newPassword` em nome de outro usuário; só emite um token que o próprio OWNER usa em `/auth/password/reset`.
- **Não pode ser usado para outro SUPER_ADMIN** — estruturalmente impossível (§13), não precisa de checagem de código adicional.

**Gap aceito, não resolvido nesta sprint**: um `SUPER_ADMIN` que esquece a própria senha em produção, sem outro `SUPER_ADMIN` disponível, não tem canal de entrega (sem e-mail, sem outro admin para gerar o link por ele). Aceito como limitação conhecida do MVP; não resolvido por CLI/script para não introduzir infraestrutura desproporcional.

## 17. Testes backend (planejados)

**Forgot**: e-mail existente cria token · e-mail inexistente não cria nada, mesma resposta · case-insensitive · resposta idêntica em todos os casos (assert literal de igualdade de corpo, incluindo durante cooldown) · nova solicitação (fora do cooldown) revoga a anterior · cooldown impede criação de um segundo token dentro de 3 minutos, sem mudar a resposta pública · token nunca persistido em plaintext.

**Reset**: válido ativa nova senha e permite login imediatamente com um `authVersion` novo · token inexistente/expirado/usado/revogado retornam **o mesmo** `422` genérico · concorrência (duas conclusões simultâneas do mesmo token, só uma sucede, a outra recebe o mesmo `422`) · senha fraca → `400` · nova senha igual à atual → `422` específico · refresh tokens antigos revogados após reset (múltiplos refresh tokens do mesmo usuário, todos revogados) · **claim `authVersion` presente e correta no JWT emitido por login/refresh** · **access token emitido antes do reset é rejeitado na requisição seguinte** (não só após expirar) · **refresh token antigo (pré-reset) rejeitado em `/auth/refresh`**.

**Status**: OWNER + Company inativa → `forgot` não cria token, `reset` (com token pré-existente) → `422` · OWNER `PENDING` → `forgot` não cria token · SUPER_ADMIN ativo → fluxo completo funciona · SUPER_ADMIN desabilitado → `forgot` não cria token.

**Segurança**: enumeração (resposta idêntica, tempo de resposta razoavelmente uniforme) · replay do mesmo token → segunda tentativa `422` · nenhum log contém o token bruto · endpoint admin retorna `403` para um `OWNER` autenticado (sem acesso).

**Admin**: gerar link para OWNER `ACTIVE` → `201` com link, revoga token anterior se existia · para OWNER `PENDING`/`INACTIVE` → `409` · para owner de outra company → `404`.

## 23. Critérios de aceite

- Link "Esqueci a password" presente em `/login` e `/admin/login`.
- `POST /auth/password/forgot` nunca revela se a conta existe (resposta idêntica, sempre `200`, inclusive durante cooldown).
- `POST /auth/password/reset` responde sempre `422` com a mesma mensagem genérica para qualquer motivo de token/conta inválidos — nunca `404`.
- Token de reset: 160 bits, hasheado (SHA-256), expira em 30 min, uso único.
- Nova solicitação (fora do cooldown de 3 min) invalida qualquer token anterior do mesmo usuário.
- Nova senha respeita a mesma política de 8–128 caracteres já usada no resto do projeto.
- Refresh tokens antigos são revogados após reset bem-sucedido.
- Access token emitido antes do reset é rejeitado na requisição seguinte, via `auth_version`.
- OWNER e SUPER_ADMIN usam o mesmo par de endpoints públicos, sem duplicação.
- Company/User inativos: comportamento definido e testado em ambas as pontas, nunca vazando estado.
- `debugToken`/`debugResetLink` só aparecem fora de `prod` e só quando um token novo foi de fato criado; nunca aparecem (nem como `null`) em `prod`.
- Endpoint administrativo de geração de link funciona só para `SUPER_ADMIN`, só para owner `ACTIVE` da company correta.
- Token de reset nunca persiste em `localStorage`/`sessionStorage`; URL é limpa do fragmento após leitura.
- Nenhum token ou senha aparece em log, em nenhum ambiente.
- Testes de backend, frontend e E2E do §17/§18 verdes.

## Riscos

## Decisões humanas — resolvidas

As 3 decisões abertas na versão anterior deste DT foram todas resolvidas e aprovadas, e uma quarta decisão (estratégia de invalidação de access tokens) foi revisada por instrução explícita:

1. **Formato do link** = fragmento (`/reset-password#token=...`), não query string — com o comportamento completo de leitura única, remoção via `history.replaceState`, nunca persistido em storage, nenhum recurso de terceiros na página (§10).
2. **Endpoint administrativo** = `POST /admin/companies/{companyId}/owners/{ownerId}/password-reset` entra nesta sprint, com as regras completas do §15.
3. **TTL e cooldown** = 30 minutos e 3 minutos, respectivamente, ambos confirmados; cooldown reaproveita `password_reset_tokens`, sem Redis, sem alterar a resposta pública.
4. **Invalidação de access tokens** (revisão, não estava nas 3 pendências originais mas foi alterada nesta rodada) = `auth_version` (contador `BIGINT`, comparado por igualdade) substitui a estratégia `password_changed_at`/`iat` da versão anterior — detalhes completos no §5.

Além disso, a resposta de erro de `POST /auth/password/reset` deixou de distinguir `404` (token inexistente) de `422` (token inválido/expirado/usado/revogado) — agora é sempre `422` com a mesma mensagem, exceto a única exceção justificada (nova senha igual à atual).

**Nenhuma decisão humana adicional está pendente.** Todos os pontos levantados nesta rodada foram resolvidos tecnicamente dentro deste DT.
