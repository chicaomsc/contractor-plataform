## 2. Contexto

A Sprint 11A.1 entregou a **fundação de containers**: `backend/Dockerfile` e `frontend/Dockerfile` multi-stage, non-root, com health checks básicos; `infra/compose/docker-compose.prod.yml` subindo backend + frontend + PostgreSQL; `infra/env/production.env.example` mapeando variáveis reais da aplicação. Isso foi validado localmente: os três serviços ficam `healthy`, `/actuator/health` responde `UP`, o frontend responde `200`.

**Containers saudáveis não significam configuração de produção concluída.** O que a Sprint 11A.1 conscientemente não tocou — porque estava fora do escopo dela — é o *comportamento interno* da aplicação quando `docker compose up` é o único sinal de "produção" que ela recebe:

- O backend **não tem profile ativo nenhum** hoje quando sobe via `docker-compose.prod.yml` (`SPRING_PROFILES_ACTIVE` não é definida em lugar nenhum do compose). Ele roda com `application.yml` puro — o que, por acidente e não por decisão, já é razoavelmente seguro, mas não é *verificável* nem *intencional*: nada falha alto e claro se alguém apontar `SPRING_PROFILES_ACTIVE=local` em produção por engano.
- **Não há shutdown gracioso configurado** (`server.shutdown` não está definido — o padrão do Spring Boot é `immediate`). Um `docker stop`/`SIGTERM` pode interromper uma requisição em voo (ex.: geração de PDF, gravação de upload) sem drenagem.
- O **segredo JWT só é validado em tempo de uso** (`Keys.hmacShaKeyFor` roda dentro de `JwtService.signingKey()`, chamado no primeiro login) — não em startup. Um `JWT_SECRET` ausente, fraco ou igual ao placeholder de desenvolvimento sobe o container como `healthy` e só quebra quando o primeiro usuário tentar entrar.
- **Não há probes de liveness/readiness** — só o endpoint agregado `/actuator/health`, sem diferenciar "processo vivo" de "pronto para tráfego real" (isto é, com PostgreSQL acessível).
- **Não há compressão HTTP no backend, nem timezone/encoding explícitos, nem `forward-headers-strategy`** — os três relevantes assim que um proxy reverso (Caddy) existir.

Nenhum desses pontos é bug — são *ausências de decisão explícita*, que hoje só não causam incidente porque o ambiente de validação é benigno (um único operador, uma VPS ainda nem escolhida, sem tráfego real). Rodar a aplicação com esses defaults implícitos em produção é o risco central que esta sprint elimina: cada lacuna acima vira, nesta sprint, uma decisão documentada e (na implementação subsequente) codificada.

**Relação com Caddy, GHCR e a VPS:** nada aqui pressupõe a existência deles. As portas do backend/frontend continuam publicadas diretamente no host (herdado da 11A.1) até a Sprint 11A.3 introduzir o Caddy como único ponto de entrada. Esta sprint, no entanto, *prepara* a aplicação para essa transição (`forward-headers-strategy`, sem duplicar responsabilidades de HSTS/CSP que o Caddy assumirá) sem implementar o proxy em si. GHCR/VPS permanecem inteiramente fora do escopo — nenhuma decisão aqui depende de onde a imagem roda ou de como ela chega lá.

## 3. Objetivos

1. Definir e planejar um profile de produção Spring Boot (`prod`) explícito, com `SPRING_PROFILES_ACTIVE` obrigatória e comportamento documentado quando ausente.
2. Planejar shutdown gracioso do backend, alinhado com o tempo de parada do Docker/Compose.
3. Planejar logging estruturado em stdout/stderr, sem SQL logging nem stack traces em produção.
4. Planejar exposição segura e útil do Actuator, incluindo separação liveness/readiness.
5. Planejar compressão HTTP, CORS estrito por variável, e limites de upload já existentes revalidados operacionalmente (não recriados).
6. Planejar tuning de JVM proporcional a uma VPS pequena, sem flags obsoletas.
7. Planejar validação fail-fast de segredos obrigatórios (JWT, CORS) no profile `prod`.
8. Mapear exaustivamente variáveis build-time vs. runtime do Next.js e decidir a configuração de produção do `next.config.ts`.
9. Decidir o destino dos headers de segurança do frontend hoje vs. quando o Caddy existir.
10. Decidir o health check definitivo do frontend (manter `/` ou criar rota dedicada).
11. Propor limites de recursos, `stop_grace_period` e políticas de restart por serviço no Compose, com premissas de VPS declaradas explicitamente.
12. Produzir uma matriz completa de variáveis de ambiente (existentes e propostas).
13. Produzir um plano de implementação faseado e um plano de testes/validação executável via Docker Compose + curl.

## 6. Decisões Técnicas

### 6.1 Backend

#### 6.1.1 Profile de produção

- **Decisão:** criar `backend/src/main/resources/application-prod.yml` (na implementação, não nesta tarefa) contendo *apenas* os overrides que precisam diferir do `application.yml` base para produção: `server.shutdown: graceful`, `spring.lifecycle.timeout-per-shutdown-phase`, `server.compression.*`, `server.forward-headers-strategy: framework`, `management.endpoint.health.probes.enabled: true`, `management.endpoint.health.group.readiness.include: readinessState,db`, níveis de log explícitos (`INFO` para `io.chicaodw.platform`, `WARN` para `org.hibernate.SQL`), e o registro do validador fail-fast (§6.1.10). **Nenhum segredo entra nesse arquivo** — `JWT_SECRET`, `DB_PASSWORD` etc. continuam vindo exclusivamente de variáveis de ambiente, como já é hoje.
- **O que fica em `application.yml` (inalterado):** tudo que já está lá hoje e já é seguro por padrão em qualquer ambiente — datasource via env vars, `ddl-auto: validate`, `error.include-message/stacktrace: never`, `health.show-details: when-authorized`, Flyway `validate-on-migrate`.
- **Como `SPRING_PROFILES_ACTIVE` será definida:** variável de ambiente obrigatória no `docker-compose.prod.yml` (`environment: SPRING_PROFILES_ACTIVE: prod`), documentada em `production.env.example` como fixa (não uma variável que o operador precisa escolher — é sempre `prod` nesse compose; só existe como env var, e não hardcoded no `application.yml`, para permitir sobrescrever em cenários de debug pontual sem editar o compose).
- **Comportamento quando o profile não for informado:** a aplicação continua subindo (não é fail-fast por *ausência* do profile — isso quebraria `./mvnw test`/execução local sem Docker), mas roda com os defaults do `application.yml` puro, que já são seguros. O validador fail-fast (§6.1.10) roda em qualquer profile e falha por *segredo inválido*, não pela ausência do profile `prod` em si — evita acoplar demais "produção" a uma flag que pode ser esquecida, e ataca a causa raiz real (segredo fraco), não o sintoma.
- **Como evitar defaults inseguros:** o próprio `application.yml` base já não tem defaults inseguros ativados por padrão (a única exceção é o `JWT_SECRET` de fallback, que existe para permitir `./mvnw test`/dev sem configurar nada — mitigado pelo validador fail-fast do §6.1.10, que roda independente de profile).
- **Alternativas consideradas:** (a) colocar tudo em `application.yml` com `@Profile`/condicionais no Java — rejeitado, foge do padrão declarativo já usado (`application-local.yml` existe exatamente para isso); (b) usar `SPRING_CONFIG_ADDITIONAL_LOCATION` para um arquivo de config fora do classpath — rejeitado, adiciona uma camada de indireção sem benefício, já que `application-prod.yml` no classpath já resolve.
- **Consequências:** ativar `prod` sem ativar `local` (o padrão em qualquer VPS) passa a ser uma escolha explícita e testável, não um acidente de omissão.
- **Arquivos afetados (implementação futura):** `backend/src/main/resources/application-prod.yml` (novo), `infra/compose/docker-compose.prod.yml`, `infra/env/production.env.example`.

#### 6.1.2 Datasource e HikariCP

- **Premissa declarada** (nenhuma VPS foi escolhida ainda): dimensionamento pensado para uma VPS inicial pequena, na ordem de **2 vCPU / 4 GB RAM** — compatível com os limites de memória já fixados na 11A.1 (`backend` 1400m/900m + `postgres` 900m/500m + `frontend` 700m/350m soma ~3 GB de limite superior, deixando margem para o SO num host de 4 GB). Se a VPS real escolhida for diferente, estes números devem ser revisitados — não são uma decisão de infraestrutura, são uma decisão de tuning proporcional a uma premissa.
- **Decisão:** manter `maximum-pool-size: 10` e `minimum-idle: 2` (já adequados para a premissa acima — a fórmula usual do HikariCP, `conexões ≈ núcleos × 2 + spindle`, sugeria algo ainda menor para 2 vCPUs compartilhadas com o próprio Postgres, mas 10 já é um teto, não um piso: o pool só cresce até esse valor sob demanda real). Adicionar explicitamente: `idle-timeout: 600000` (10 min, já é o default do Hikari — torná-lo explícito documenta a intenção), `max-lifetime: 1800000` (30 min, idem), `validation-timeout: 5000`.
- **Justificativa:** um pool de 10 já é conservador para o volume de tráfego esperado (cliente beta único); explicitar os timeouts em vez de depender do default do Hikari documenta a intenção e evita que uma futura atualização de dependência mude o comportamento silenciosamente.
- **Alternativas consideradas:** pool maior (20+) — rejeitado, superdimensiona para uma VPS pequena e aumenta a pressão de memória do lado do Postgres (cada conexão Postgres consome memória própria no processo do servidor).
- **Consequências:** sob pico de tráfego incomum, requisições esperam por uma conexão em vez de estourar o Postgres de conexões — comportamento aceitável e reversível (é só configuração).
- **Arquivos afetados:** `backend/src/main/resources/application.yml` (bloco `spring.datasource.hikari`).

#### 6.1.3 Flyway

- **Decisão:** manter migração automática no boot (`spring.flyway.enabled: true`, já é o caso) — é o comportamento já usado em todas as sprints anteriores e não há indicação de que produção deva divergir (não há um segundo processo/job de migração no design da VPS). Manter `validate-on-migrate: true` (já ativo). Adicionar explicitamente `clean-disabled: true` no `application.yml` (não só confiar no default do Spring Boot) — é uma linha, e documentar a intenção supera depender de um comportamento implícito de uma dependência de terceiros. `baseline-on-migrate` permanece `false` — não há necessidade de baseline (o schema sempre nasce vazio via as migrations V1+ existentes, nunca há um banco legado pré-existente para "adotar").
- **Estratégia em caso de erro de migration:** nenhuma automação de rollback — Flyway não suporta rollback automático de migrations já aplicadas (por design da ferramenta). Decisão: se uma migration falhar no boot, o container falha (`FlywayException` propaga e o contexto Spring não sobe) — isso é o comportamento correto e já existente; o `healthcheck` do backend nunca reporta `healthy` nesse cenário, então `docker compose up` fica visivelmente travado em vez de mascarar o problema. Não introduzir retry automático de migration (mascararia um erro real).
- **Alternativas consideradas:** desabilitar Flyway em produção e rodar migrations manualmente antes do deploy — rejeitado, adiciona um passo manual sujeito a esquecimento, sem ganho real dado que o schema desta aplicação sempre foi gerenciado por Flyway automático desde a Sprint 2.
- **Arquivos afetados:** `backend/src/main/resources/application.yml` (uma linha, `clean-disabled: true`).

#### 6.1.4 Shutdown gracioso

- **Decisão:** `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 25s` no `application-prod.yml`. No Compose, adicionar `stop_grace_period: 30s` ao serviço `backend` (5s de margem acima do timeout do Spring, para o processo Java terminar sozinho depois que a fase graciosa do Spring já encerrou — se ele não terminar dentro dos 30s, o Docker manda `SIGKILL`).
- **Comportamento esperado do `docker stop`:** Docker manda `SIGTERM` ao PID 1 (o processo `java`, já garantido pelo `ENTRYPOINT` em exec form da 11A.1) → Spring Boot para de aceitar novas requisições, aguarda até 25s as requisições em voo terminarem (ex.: uma geração de PDF ou um upload em andamento) → processo termina sozinho → Docker nunca precisa do `SIGKILL` no caminho feliz.
- **Alternativas consideradas:** `server.shutdown: immediate` (default atual) — rejeitado, é exatamente o comportamento que queremos eliminar (requisição cortada no meio). `stop_grace_period` maior (60s+) — rejeitado, não há operação nesta aplicação que legitimamente demore mais que alguns segundos (geração de PDF é em memória, não há streaming longo).
- **Consequências:** um `docker compose down`/restart de rotina passa a levar até ~5-25s a mais no pior caso (quando há requisições em voo) — aceitável para uma aplicação sem SLA de zero-downtime nesta fase.
- **Arquivos afetados:** `application-prod.yml` (novo), `docker-compose.prod.yml` (`backend.stop_grace_period`).

#### 6.1.5 Actuator

- **Endpoints expostos:** manter só `health` e `info` (`management.endpoints.web.exposure.include: health, info`, já é o caso) — nenhum novo endpoint (`env`, `beans`, `metrics`, `mappings`, etc.) é necessário sem uma ferramenta de observabilidade consumindo-os, e cada endpoint exposto é superfície de ataque adicional.
- **Detalhes do health:** manter `show-details: when-authorized` — já documentado como seguro por coincidência (§5.1); tornar essa coincidência **decisão explícita**: como `/actuator/health` (e os novos sub-paths de probe) são `permitAll`, nunca há um principal Spring Security autenticado nessas chamadas, então `when-authorized` já nunca revela detalhes a chamadas anônimas. Isso é preferível a `never` porque, se no futuro o endpoint precisar ser acessado autenticado internamente (ex.: um script operacional com credenciais), os detalhes ficam disponíveis sem mudar configuração.
- **Acesso público ou restrito:** `/actuator/health` (e sub-paths `/actuator/health/liveness`, `/actuator/health/readiness`) continuam `permitAll` — são o que o Docker healthcheck usa, e não expõem nada sensível (só `UP`/`DOWN`, sem `show-details` para chamadas anônimas). **Todo o resto do namespace `/actuator/**`** (ex.: `/actuator/info`, caso alguém tente) permanece exigindo autenticação — hoje isso já é implícito por `.anyRequest().authenticated()`, nenhuma mudança necessária aí.
- **Correção necessária no matcher de segurança:** o matcher atual em `SecurityConfig.java` é o path exato `"/actuator/health"` — **não cobre** `/actuator/health/liveness` nem `/actuator/health/readiness` (sub-paths). Decisão: trocar para `"/actuator/health/**"` (wildcard), preservando o mesmo espírito (só o health/probes são públicos) mas cobrindo os sub-recursos que este design introduz.
- **Informações sensíveis:** nenhuma — `info.env.enabled: true` já existente só expõe propriedades sob o prefixo `info.*` (nome/versão da aplicação), não variáveis de ambiente arbitrárias.
- **Consideração sobre o Caddy:** como o Caddy ainda não existe, `/actuator/health/**` fica acessível publicamente na porta 8080 publicada — aceitável (só expõe status, não detalhe) e temporário, na mesma categoria das portas publicadas documentadas na 11A.1.
- **Arquivos afetados:** `SecurityConfig.java` (matcher), `application-prod.yml` (probes).

#### 6.1.6 Health, readiness e liveness

- **Decisão:** habilitar `management.endpoint.health.probes.enabled: true` no `application-prod.yml`, o que registra `/actuator/health/liveness` e `/actuator/health/readiness` como sub-recursos de `/actuator/health` (não precisam de nova entrada em `exposure.include` — são sub-paths do endpoint `health` já exposto).
  - **Liveness** (`readinessState` fora, só `livenessState`) — reflete exclusivamente "o processo Java está de pé e o contexto Spring subiu". **Nunca** inclui o Postgres — de propósito: se o Postgres cair momentaneamente, a JVM continua perfeitamente viva e não deve ser reiniciada por causa disso (reiniciar o backend não conserta um Postgres fora do ar, só causa uma janela de indisponibilidade adicional).
  - **Readiness** — decisão explícita: `management.endpoint.health.group.readiness.include: readinessState,db` — **inclui** o indicador `db` (auto-registrado pelo Spring Boot a partir do `DataSource`), porque nenhuma rota real desta aplicação funciona sem PostgreSQL. "Pronto para tráfego" aqui significa literalmente "consegue atender uma requisição de verdade".
- **Qual endpoint o Docker healthcheck usa e por quê:** **`/actuator/health/readiness`**, não o `/actuator/health` agregado nem `/liveness`. Justificativa: o Docker Compose (fora de Swarm) só tem **um** sinal de saúde por container — não existe o conceito de "liveness vs. readiness" para quem consome `docker compose ps`/`depends_on: condition: service_healthy`. Entre os três, `readiness` é o mais útil aqui: reflete se o backend está de fato utilizável (JVM viva **e** Postgres acessível), que é exatamente o que se quer saber antes de considerar o serviço "up" para fins operacionais.
- **Trade-off aceito:** com essa escolha, uma instabilidade transitória do Postgres pode fazer o container do backend aparecer como `unhealthy` mesmo com a JVM perfeitamente saudável — o Docker não reinicia o container sozinho por causa disso (não há `--restart-on-unhealthy` automático fora de ferramentas externas), mas ferramentas de orquestração futuras que decidam agir sobre "unhealthy" precisam estar cientes dessa semântica. Documentado aqui para não ser descoberto por acidente depois.
- **Diferenciação (resumo):**
  - Processo vivo → `/actuator/health/liveness` (só JVM/contexto).
  - Aplicação pronta → `/actuator/health/readiness` (JVM + Postgres).
  - Dependências externas → hoje só existe uma (Postgres), incluída em readiness, nunca em liveness.
- **Alternativas consideradas:** usar o `/actuator/health` agregado (que também reflete o `db` indicator por padrão) no healthcheck — funcionalmente quase idêntico a usar `readiness` neste caso específico (já que `readiness` foi configurado para incluir `db`), mas usar o path `/readiness` explicitamente documenta a intenção e já deixa o container pronto para um consumidor futuro (ex.: um orquestrador) que queira liveness e readiness com semânticas diferentes de verdade.
- **Arquivos afetados:** `application-prod.yml`, `SecurityConfig.java`, `backend/Dockerfile` (`HEALTHCHECK` muda de `/actuator/health` para `/actuator/health/readiness`), `docker-compose.prod.yml` (healthcheck do serviço `backend`).

#### 6.1.7 Logging

- **Decisão:** manter 100% stdout/stderr (já é o comportamento padrão do Spring Boot e do `docker compose logs`, sem `logging.file.*` configurado — decisão de **não introduzir** log em arquivo dentro do container, pois duplicaria o que o driver `json-file` do Docker já faz com rotação (`max-size:10m`/`max-file:5`, já configurado na 11A.1), sem trazer benefício e ainda arriscando encher o volume do container).
- **Formato:** manter o padrão do Spring Boot (`CONSOLE_LOG_PATTERN`) — já inclui timestamp, nível, PID, thread, logger e mensagem; já desativa ANSI automaticamente quando a saída não é um terminal interativo (caso do Docker), então não há necessidade de `spring.output.ansi.enabled=never` explícito, mas será adicionado mesmo assim no `application-prod.yml` por robustez (não depender de auto-detecção em todo ambiente de execução possível).
- **Timestamp/timezone:** decisão — `TZ=UTC` como variável de ambiente do container (backend e frontend), garantindo timestamps de log em UTC independente de onde a VPS estiver fisicamente. UTC funciona mesmo em uma imagem Alpine sem o pacote `tzdata` instalado, porque o próprio JDK (Java 25) já embute sua base de fusos horários independente do SO — `UTC` não depende de nenhuma consulta externa.
- **Níveis por pacote (produção):** `root: INFO`, `io.chicaodw.platform: INFO` (não `DEBUG` — `DEBUG` é exclusivo do profile `local`), `org.hibernate.SQL: WARN` (nunca logar SQL em produção — dados de clientes podem aparecer em parâmetros de bind), `org.flywaydb: INFO` (útil ver quais migrations rodaram no boot, sem ruído).
- **SQL logging:** **desabilitado** — `spring.jpa.show-sql` nunca é setado como `true` fora de `application-local.yml` (confirmado); manter assim.
- **Stack traces:** nunca em resposta HTTP (`server.error.include-stacktrace: never`, já ativo); sempre no log do servidor via `log.error(..., ex)` (já é o padrão do `GlobalExceptionHandler`, mantido).
- **Dados sensíveis:** nenhum log intencional de senha/token/segredo já existe no código (confirmado por leitura do `GlobalExceptionHandler`/`JwtService`/`AuthController` ao longo das sprints anteriores) — nenhuma mudança de código necessária aqui, só validação (plano de testes, §9).
- **Correlação por request:** decisão — **não implementar nesta sprint**. Um request-id/MDC de correlação é proporcional quando há múltiplas instâncias/logs agregados centralmente — hoje é um único container de backend com log local; a complexidade (filtro novo, propagação de header, mudança de padrão de log) não se paga ainda. Revisitar quando houver agregação de logs centralizada (fora do escopo, ver §11).
- **Arquivos afetados:** `application-prod.yml`.

#### 6.1.8 Compressão HTTP

- **Decisão:** habilitar `server.compression.enabled: true` no `application-prod.yml`, com `server.compression.mime-types: application/json,application/problem+json,text/plain,text/css,application/javascript` e `server.compression.min-response-size: 1024` (1 KB — respostas menores não valem a CPU de comprimir).
- **Por que não incluir `application/pdf`:** o PDF gerado (`EstimatePdfService`) já é um binário razoavelmente denso (texto + eventualmente uma imagem de logo já comprimida); comprimir de novo gasta CPU sem ganho relevante de banda. Simplesmente **não** listar esse mime-type no allowlist já resolve — Spring só comprime o que está na lista.
- **Possíveis conflitos futuros com Caddy:** quando o Caddy existir (11A.3), ele também pode comprimir (`encode gzip zstd`). Isso não é um conflito real — um corpo já comprimido pelo backend (com `Content-Encoding` já setado) normalmente não é recomprimido por um proxy bem-comportado; mesmo assim, a decisão de qual camada comprime pode ser revisitada na 11A.3 para evitar duas passagens de compressão. Habilitar agora no backend tem valor imediato (as portas hoje são publicadas diretamente, sem proxy).
- **Arquivos afetados:** `application-prod.yml`.

#### 6.1.9 CORS

- **Origem permitida via variável:** já implementado (`app.cors.allowed-origins` via `APP_CORS_ALLOWED_ORIGINS`) — mantido.
- **Múltiplas origens:** já suportado (`List<String>` via binding relaxado, string separada por vírgula) — mantido, documentar exemplo com duas origens no `production.env.example` (ex.: apex + `www.`).
- **Wildcard:** decisão — **rejeitar explicitamente** `*` (e qualquer entrada em branco) via o validador fail-fast do §6.1.10, no profile `prod`. O modelo de ameaça desta aplicação (SaaS single-tenant nesta fase, mas multi-tenant na arquitetura) nunca precisa de "qualquer origem" — um CORS aberto anularia a proteção que a autenticação JWT via header (não cookie) já dá contra CSRF.
- **Credentials:** `CorsConfiguration.setAllowCredentials` **nunca é chamado** hoje (permanece no default, que o Spring trata como não permitir credentials automáticas em requisições CORS) — correto e mantido, já que a autenticação é via header `Authorization`, não cookie enviado automaticamente pelo browser.
- **Métodos/headers:** já restritos (`GET,HEAD,POST,PUT,PATCH,DELETE,OPTIONS` / `Authorization,Content-Type,Accept`) — mantidos, sem mudança.
- **Ambiente local vs. produção:** o default do `@Value` (`http://localhost:3000,http://127.0.0.1:3000`) só é usado quando `APP_CORS_ALLOWED_ORIGINS` está ausente — decisão: no profile `prod`, o validador fail-fast (§6.1.10) exige que a variável esteja **explicitamente definida**, então o default de localhost nunca é alcançável em produção real (só em dev/teste local, onde ele já funciona hoje).
- **Fail-fast para configuração inválida:** sim — ver §6.1.10.
- **Arquivos afetados:** `application-prod.yml` (nenhuma mudança de valor, só a validação abaixo), `SecurityConfig.java` (não muda a lógica de CORS em si).

#### 6.1.10 Fail-fast para segredos e configuração inválida (decisão transversal)

- **Decisão:** introduzir um componente `@Component` + `ApplicationRunner` (ex.: `ProductionReadinessValidator`), registrado **sempre** (não gated por `@Profile("prod")` — rejeitado abaixo), que roda logo após o contexto subir e lança `IllegalStateException` (interrompendo o boot, container nunca fica `healthy`) se:
  - `JWT_SECRET` estiver ausente, igual ao valor de fallback de dev (`dev-only-secret-at-least-32-chars-change-in-prod!`), ou tiver menos de 32 bytes em UTF-8 (mínimo do HS256) — mas **só quando `SPRING_PROFILES_ACTIVE` incluir `prod`**; em qualquer outro profile (incl. ausência de profile, usado por testes), o fallback de dev continua permitido, preservando `./mvnw test` funcionando sem configuração.
  - `APP_CORS_ALLOWED_ORIGINS` estiver ausente, vazia, ou contiver `*` — mesma condição de profile.
  - `STORAGE_PATH` (resolvido) não existir e não puder ser criado, ou existir e não for gravável pelo usuário do processo — validado em **qualquer** profile (não é um problema exclusivo de produção; um `STORAGE_PATH` quebrado quebra igualmente em dev).
- **Por que não usar `@Profile("prod")` na classe inteira:** a checagem de `STORAGE_PATH` gravável é útil em qualquer ambiente; só as checagens de JWT/CORS precisam ser condicionais ao profile. Um único componente com lógica condicional interna é mais simples de manter do que duas classes.
- **Alternativas consideradas:** validar via `@ConfigurationProperties` + `@Validated`/Bean Validation (`@NotBlank`, etc.) — parcialmente atraente, mas Bean Validation não expressa bem "diferente por profile" nem "comparar com um valor sentinela conhecido" sem código customizado de qualquer forma; o `ApplicationRunner` explícito é mais direto e mais fácil de testar isoladamente.
- **Consequências:** um deploy com `JWT_SECRET` esquecido/placeholder **nunca** fica `healthy` — em vez de subir "com sucesso" e falhar silenciosamente no primeiro login de um cliente real, falha imediatamente e ruidosamente no boot, exatamente onde um operador olharia primeiro (`docker compose logs backend`).
- **Arquivos afetados (novos, implementação futura):** `backend/src/main/java/io/chicaodw/platform/common/config/ProductionReadinessValidator.java` (nome sujeito a ajuste na implementação) + um teste unitário dedicado.

#### 6.1.11 Upload e armazenamento

- **`STORAGE_PATH`:** mantido como está (`app.storage.base-path`, já configurável, já usado no volume `backend_storage:/app/storage` da 11A.1) — nenhuma mudança de valor.
- **Volume persistente:** já implementado (`backend_storage`) — confirmado que é o único diretório de escrita da aplicação (PDFs nunca tocam disco, gerados em memória por `EstimatePdfService` — já confirmado em tarefa anterior).
- **Permissões do usuário non-root:** já corretas na 11A.1 — `RUN mkdir -p /app/storage && chown -R platform:platform /app/storage` no `backend/Dockerfile`, container roda como `platform` (uid 1000). Quando o volume nomeado `backend_storage` é montado por cima desse diretório, o Docker herda a propriedade do diretório de destino na primeira criação do volume (uid 1000) — sem ação adicional necessária, mas **vale validar operacionalmente** (plano de testes, §9) porque é um dos pontos onde "funciona no Dockerfile" e "funciona com o volume montado" podem divergir na prática.
- **Validação de diretório no startup:** nova, coberta pelo validador fail-fast do §6.1.10 (checagem de gravabilidade).
- **Limites de upload:** já implementados e não tocados por esta sprint (`ImageUploadPolicy`, 5 MB, tipos PNG/JPEG/WebP, validação de assinatura binária — ver §5.1). `spring.servlet.multipart.max-file-size: 5MB`/`max-request-size: 10MB` já alinhados.
- **Comportamento se o volume não estiver disponível:** se `STORAGE_PATH` não existir e não puder ser criado (ex.: erro de montagem do volume), o validador fail-fast (§6.1.10) impede o boot — decisão deliberada de falhar cedo em vez de subir e falhar upload-a-upload.
- **Relação futura com object storage:** nenhuma mudança agora — `StorageService` já é uma interface (Strategy Pattern, `LocalStorageService` é a única implementação hoje); trocar por S3/R2 no futuro (mencionado como risco mitigado no `docs/roadmap.md`) não exige mudança de contrato, só uma nova implementação — fora do escopo desta sprint.
- **Arquivos afetados:** nenhum além do validador já listado em §6.1.10.

#### 6.1.12 JVM

- **`MaxRAMPercentage`/`InitialRAMPercentage`/`UseG1GC`/`ExitOnOutOfMemoryError`:** já implementados na 11A.1 (70/20/G1GC/exit-on-OOM) — **mantidos sem alteração**, já proporcionais ao limite de 1400m definido no Compose.
- **Heap dump:** decisão — **não habilitar** `-XX:+HeapDumpOnOutOfMemoryError` nesta sprint. Justificativa: um heap dump de um processo com até ~1 GB de heap pode ocupar espaço considerável numa VPS pequena com disco limitado; sem uma estratégia de coleta/rotação desses dumps (ferramenta de observabilidade, fora do escopo — ver §12), um OOM repetido encheria o disco com dumps não utilizados. Com `ExitOnOutOfMemoryError` já ativo, a resposta operacional a um OOM hoje é "o container reinicia limpo" (via `restart: unless-stopped`), o que é aceitável para esta fase. Revisitar quando houver um destino (volume dedicado + rotação, ou upload para storage externo) para os dumps.
- **Timezone:** `TZ=UTC` (ver §6.1.7) — não requer flag de JVM adicional, é lido automaticamente via variável de ambiente do container.
- **Encoding:** nenhuma flag necessária — Java 25 já usa UTF-8 por padrão (JEP 400, em vigor desde o Java 18).
- **Container awareness:** nenhuma flag necessária — JVMs modernas (desde o Java 10, e certamente o Java 25) detectam automaticamente os limites de cgroup do container para que `MaxRAMPercentage` funcione corretamente; é um pré-requisito já satisfeito, não uma configuração a adicionar.
- **`JAVA_TOOL_OPTIONS`:** mantido como está, sem novas flags além do já existente. Nenhuma flag obsoleta estava presente (não há `-XX:+UseParallelGC` nem `-Xmx` fixo conflitando com `MaxRAMPercentage`, por exemplo) — nada a remover.
- **Arquivos afetados:** nenhum (decisão de **não alterar** o que já existe, só documentar por que cada opção não-adicionada foi conscientemente deixada de fora).

#### 6.1.13 Segurança de produção

- **Exposição de mensagens de erro/stack traces:** já corretas (`server.error.include-message/include-stacktrace: never`, `GlobalExceptionHandler` sempre devolve `ProblemDetail` sanitizado) — nenhuma mudança.
- **Sessão/cookies:** o backend é 100% stateless (`SessionCreationPolicy.STATELESS`, já ativo) — não emite nenhum cookie. O único cookie do sistema (`contractor_session`) é criado pelo **frontend**, sem token, só para o `middleware.ts` decidir redirecionar — não é uma responsabilidade do backend e não muda nesta sprint.
- **Proxy/forward headers:** decisão — adicionar `server.forward-headers-strategy: framework` ao `application-prod.yml`. Isso faz o Spring usar automaticamente `X-Forwarded-Proto`/`X-Forwarded-Host`/`X-Forwarded-Port` (quando presentes) para reconstruir URLs corretamente — **inofensivo hoje** (não há proxy, os headers simplesmente não chegam, então o comportamento não muda), mas evita uma segunda tarefa de configuração exclusivamente para isso quando o Caddy for introduzido na 11A.3. É essa a "preparação para proxy reverso futuro" pedida, sem implementar o proxy em si.
- **Secrets obrigatórios / JWT secret mínimo / fail-fast:** ver §6.1.10 (decisão consolidada ali para não duplicar).
- **Arquivos afetados:** `application-prod.yml`.

### 6.2 Frontend

#### 6.2.1 Build-time vs. runtime — matriz de variáveis

| Variável | Onde é lida | Momento | Sensível? | Default permitido? | Obrigatória em produção? | Impacto de alterar | Precisa rebuild ou só restart? |
|---|---|---|---|---|---|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | `frontend/src/lib/env/public-env.ts` (client + server), `next.config.ts` (CSP `connect-src`) | **Build-time** (inlined no bundle do cliente pelo webpack) **e** runtime (o processo `server.js` também lê `process.env` diretamente, mas o valor já embutido no JS do cliente é o que domina para chamadas `fetch` feitas no browser) | Não (é uma URL pública, não um segredo) | Não — schema Zod (`z.string().url()`) exige presença | Sim | Muda o backend que o app inteiro chama | **Rebuild** (é `NEXT_PUBLIC_*`) |
| `NEXT_PUBLIC_COMPANY_SLUG` | `public-env.ts` | **Build-time** (inlined) | Não | Não — schema exige `min(1)`, sem default | Sim | Muda qual tenant a landing pública representa | **Rebuild** |
| `NEXT_PUBLIC_SITE_URL` | `public-env.ts`, `layout.tsx` (canonical/OG) | **Build-time** (inlined) | Não | Sim — `.optional()` no schema | Recomendada, não estritamente obrigatória | Afeta canonical URL/Open Graph | **Rebuild** |
| `NODE_ENV` | Next.js internamente | Build-time (já fixado `production` na imagem) e runtime | Não | Não se aplica — fixo na imagem | Sim (sempre `production` na imagem final) | Alterar exigiria rebuild da imagem (não é exposto como variável do Compose) | **Rebuild** (hardcoded no Dockerfile, decisão da 11A.1 mantida) |
| `PORT` | Next.js standalone `server.js` | Runtime | Não | Sim, `3000` | Não | Muda a porta interna do processo Node | Restart |
| `HOSTNAME` | Next.js standalone `server.js` | Runtime | Não | Sim, `0.0.0.0` (já fixado no Dockerfile) | Não | Interface de bind | Restart |
| `NODE_OPTIONS` | Node runtime | Runtime | Não | Sim, `--max-old-space-size=512` (já no Compose) | Não | Ajusta heap do V8 | Restart |
| `FRONTEND_HOST_PORT` | Só o `docker compose` (interpolação do `ports:`) | Nem build nem runtime da aplicação — só orquestração | Não | Sim, `3000` | Não | Porta publicada no host | Restart (nem isso, é só recriação do container) |
| `BACKEND_IMAGE`/`FRONTEND_IMAGE`/`APP_VERSION`/`COMPOSE_PROJECT_NAME` | Só o `docker compose` | Orquestração | Não | Sim (têm defaults no compose) | Não | Qual imagem/tag é usada | Recriação do container |

**Reforço explícito pedido pela tarefa:** toda variável `NEXT_PUBLIC_*` é lida pelo *webpack* durante `next build` e literalmente substituída por seu valor como string constante em cada lugar do código-fonte onde `process.env.NEXT_PUBLIC_X` aparece, dentro do JavaScript que é enviado ao browser. Isso significa que (a) esses valores são **públicos por definição** — qualquer pessoa pode abrir o DevTools e lê-los; nunca colocar um segredo atrás de `NEXT_PUBLIC_*`; e (b) mudar qualquer um deles depois que a imagem já foi construída **não tem efeito nenhum** até a imagem ser reconstruída — reiniciar o container com um valor de ambiente diferente não muda o bundle já compilado.

- **`compress`:** já `true` por default (nenhum override presente) — decisão: manter o default (não setar `compress: false`), sem necessidade de tornar explícito no arquivo (é o comportamento padrão documentado do Next.js; explicitar traria zero mudança de comportamento).
- **`poweredByHeader`/`reactStrictMode`:** já configurados (`false`/`true`) — mantidos.
- **Tratamento de imagens:** `images.remotePatterns` já aceita qualquer host `http`/`https` — decisão: **manter como está**. É necessário porque cada tenant tem seu próprio logo/imagens de galeria, servidos por um host de backend que varia por ambiente (`localhost` em dev, o domínio real em produção) — restringir a um host fixo quebraria o modelo multi-tenant. Não há alternativa mais restritiva sem reintroduzir acoplamento a um host específico.
- **Logs:** nenhuma configuração de logging customizada é necessária — o runtime standalone do Next.js já escreve para stdout/stderr por padrão, capturado pelo driver `json-file` do Docker (mesma decisão do backend, §6.1.7).
- **Comportamento de erros:** já existente e adequado — as páginas já tratam estados de erro/loading (confirmado nas Sprints 7B–10D, ex. `PublicSiteIntegrationShell`, `ShareUnavailableState`) sem lançar exceção não tratada; nenhuma mudança de código de produto nesta sprint (fora do escopo, §4).

#### 6.2.3 Headers de segurança — o que fica agora vs. o que vira do Caddy

| Header | Decisão | Onde fica |
|---|---|---|
| `X-Content-Type-Options: nosniff` | **Manter no Next.js** — já implementado, correto, independe de TLS | `next.config.ts` |
| `Referrer-Policy: strict-origin-when-cross-origin` | **Manter no Next.js** — já implementado | `next.config.ts` |
| `Permissions-Policy` | **Manter no Next.js** — já implementado | `next.config.ts` |
| `X-Frame-Options: DENY` | **Manter no Next.js** — já implementado (equivalente funcional ao `frame-ancestors 'none'` do CSP, que também já está presente — redundância intencional para navegadores antigos que não suportam CSP `frame-ancestors`) | `next.config.ts` |
| `Content-Security-Policy` | **Manter no Next.js** — já implementado, correto e específico da aplicação (inclui `connect-src` derivado do backend real) | `next.config.ts` |
| `Strict-Transport-Security` | **Não adicionar agora** — decisão explícita. HSTS instrui o browser a *recusar* qualquer conexão HTTP futura àquele host por um período — anunciar isso sobre HTTP puro (sem `Secure` de fato garantido) é, na melhor das hipóteses, ignorado pelo browser (a especificação HSTS exige que o header só tenha efeito quando entregue sobre HTTPS) e, na pior, um risco se o ambiente mudar de domínio antes do TLS estar pronto. **Vira responsabilidade do Caddy na Sprint 11A.3**, que só deve emitir HSTS depois que o TLS via Cloudflare estiver validado ponta a ponta. | Caddy, 11A.3 |

**Evitar duplicar responsabilidades futuras:** quando o Caddy existir, ele **não deve** re-declarar `Content-Security-Policy`/`X-Frame-Options`/etc. — a aplicação (Next.js) já é a fonte da verdade para esses headers porque só ela sabe seu próprio `connect-src` real. O Caddy deve se limitar a HSTS + qualquer header exclusivamente de camada de transporte (nada disso é implementado agora — só a fronteira de responsabilidade é decidida).

#### 6.2.4 Healthcheck do frontend

- **Decisão:** substituir o healthcheck de `/` por uma rota dedicada `frontend/src/app/api/health/route.ts` (App Router Route Handler), retornando `200` com um corpo mínimo (`{ status: "ok" }`), sem nenhuma dependência de backend, banco, ou variável de ambiente além das já necessárias para o processo subir.
- **Justificativa:** `/` hoje já funciona como healthcheck (confirmado na 11A.1, documentado como decisão temporária), mas ele acopla duas preocupações: "o servidor Node está de pé" e "a página pública renderiza corretamente" (que envolve `generateMetadata`, potencialmente uma tentativa de fetch ao backend público, e toda a árvore de componentes da landing). Um healthcheck deve ser o mais simples e independente possível — uma rota dedicada sem lógica de negócio é mais barata de computar a cada 30s e não gera um falso "unhealthy" se a landing pública tiver algum problema de renderização não relacionado à saúde do processo em si.
- **Dependências que o healthcheck deve/não deve verificar:** não deve verificar o backend (mesmo raciocínio do `depends_on` ausente, §5.3 — o frontend deve reportar saudável mesmo com a API fora do ar) nem nenhum dado externo. Deve verificar apenas que o processo Node/Next.js está respondendo — é exatamente o que uma rota estática sem I/O garante.
- **Impacto sobre o build standalone:** nenhum — Route Handlers do App Router são incluídos automaticamente no output `standalone` (tratados como qualquer outra rota), sem configuração adicional.
- **Simplicidade:** a rota é deliberadamente trivial — sem verificação de variáveis de ambiente, sem chamada de rede, sem lógica condicional — evitando "over-engineering" de um healthcheck (coerente com o pedido explícito de simplicidade).
- **Arquivos afetados (implementação futura):** `frontend/src/app/api/health/route.ts` (novo), `frontend/Dockerfile` (`HEALTHCHECK` muda de `http://127.0.0.1:3000/` para `http://127.0.0.1:3000/api/health`), `docker-compose.prod.yml` (healthcheck do serviço `frontend`), `infra/README.md` (remover a nota de "healthcheck temporário via `/`").

#### 6.2.5 Graceful shutdown do Node

- **Decisão:** **nenhuma alteração de código é necessária.** O `server.js` do output standalone roda como PID 1 (exec form já garantido no `frontend/Dockerfile` desde a 11A.1) e, sem um handler de `SIGTERM` customizado, a disposição padrão do Node é encerrar o processo imediatamente ao receber o sinal.
- **Justificativa da suficiência:** esta aplicação não mantém conexões de longa duração no frontend (sem WebSockets, sem streaming, sem SSE) — todo request é uma renderização/API call curta. Não há "trabalho em voo" que justifique uma fase de drenagem graciosa como a que o backend precisa (§6.1.4, onde geração de PDF/upload são operações que legitimamente levam tempo). Adicionar um handler de `SIGTERM` customizado sem um caso de uso real seria complexidade sem benefício.
- **Consequência aceita:** requisições HTTP em voo no exato momento do `SIGTERM` podem receber uma conexão resetada em vez de uma resposta completa — para um app sem SLA de zero-downtime nesta fase, e dado que toda operação é idempotente/segura de repetir (GET de página, chamadas de API que o TanStack Query já re-tenta), esse é um risco aceito, não ignorado.
- **`stop_grace_period` proposto para o Compose:** manter o default do Docker (10s) para o serviço `frontend` — não há necessidade de um valor maior, já que não há drenagem a esperar.
- **Arquivos afetados:** nenhum.

#### 6.3.1 Profiles e variáveis

Isso é consistente: o Compose valida o que ele mesmo interpola (nomes de imagem, credenciais do Postgres usadas em múltiplos lugares do YAML); a aplicação valida o que só ela consome.
- **Arquivos afetados:** `docker-compose.prod.yml`, `production.env.example` (documentar `SPRING_PROFILES_ACTIVE` como fixo, não editável).

#### 6.3.2 Recursos

**Premissa declarada (repetida de §6.1.2 para visibilidade):** VPS inicial hipotética de ~2 vCPU / 4 GB RAM — não escolhida ainda, só uma referência de dimensionamento. Se a VPS real for maior/menor, os números abaixo devem ser recalculados proporcionalmente.

| Serviço | `mem_limit` (já implementado) | `mem_reservation` (já implementado) | `cpus` (proposto, ausente hoje) | Risco de OOM |
|---|---|---|---|---|
| `postgres` | 900m | 500m | `1.0` (proposto) | Baixo — Postgres degrada com pouca memória (menos cache de buffer) antes de ser morto por OOM; o limite de 900m já é generoso para o volume de dados de um cliente beta |
| `backend` | 1400m | 900m | `1.0` (proposto) | Médio — `MaxRAMPercentage=70` de 1400m ≈ 980 MB de heap máximo; `ExitOnOutOfMemoryError` já garante que um esgotamento vira reinício limpo em vez de um processo travado consumindo CPU em GC contínuo |
| `frontend` | 700m | 350m | `0.5` (proposto) | Baixo — `--max-old-space-size=512` já limita o heap do V8 abaixo do `mem_limit` do container, deixando margem para memória não-heap do Node |

- **Limits vs. reservations, fora do Swarm:** decisão registrada explicitamente porque é frequentemente mal entendida — sob `docker compose up` (sem `docker stack deploy`), `mem_limit`/`mem_reservation` (a sintaxe legada, já em uso desde a 11A.1) funcionam via cgroups do Docker Engine diretamente: `mem_limit` é um teto rígido (o kernel mata o processo com OOM killer se ultrapassado); `mem_reservation` é um "soft limit" (só entra em ação sob pressão de memória do host, sem garantia forte). Isso é diferente de `deploy.resources.limits/reservations`, que **só tem efeito sob `docker stack deploy` (Swarm)** — sob `docker compose up` puro, um bloco `deploy:` é silenciosamente ignorado. Por isso a 11A.1 já usou corretamente a sintaxe legada, e esta sprint mantém a mesma escolha para `cpus` (`cpus:` no nível do serviço, não `deploy.resources.limits.cpus`).
- **CPU:** decisão — propor `cpus: "1.0"` para `postgres` e `backend`, `cpus: "0.5"` para `frontend`, somando 2.5 vCPU nominais — **acima** da premissa de 2 vCPU declarada. Isso é intencional: limites de CPU no Docker não são reservas exclusivas (múltiplos serviços podem competir pelas mesmas CPUs até seus limites individuais, o scheduler do kernel faz a divisão de fato sob contenção) — a soma pode exceder o total físico sem problema, é só um teto individual por serviço para impedir que um processo descontrolado (ex.: um loop de GC constante) monopolize 100% da VPS e derrube os outros dois serviços junto.
- **Alternativas consideradas:** não definir `cpus` nenhum (deixar tudo competir livremente) — considerado, mas rejeitado porque um dos três processos travando em uso de CPU alto (ex.: geração de PDF com um documento pato lógico gigante) hoje poderia af etar os outros dois sem limite; um teto individual contém o dano.
- **Arquivos afetados:** `docker-compose.prod.yml` (`cpus:` em cada serviço).

#### 6.3.3 Restart policy

| Serviço | Política (já implementada) | Mantida? | Justificativa |
|---|---|---|---|
| `postgres` | `unless-stopped` | Sim | Precisa voltar sozinho após reboot da VPS ou crash, mas não deve reiniciar em loop se o operador explicitamente parou o stack (`docker compose stop`) |
| `backend` | `unless-stopped` | Sim | Mesmo raciocínio — inclusive é o que faz o `ExitOnOutOfMemoryError` (§6.1.12/6.3.2) ser uma estratégia operacional válida: o processo sai limpo, o Compose sobe de novo |
| `frontend` | `unless-stopped` | Sim | Mesmo raciocínio, sem motivo para divergir |

- **Por que não `always`:** `always` reinicia mesmo depois de um `docker stop` manual explícito (na próxima vez que o Docker daemon subir) — comportamento surpreendente para operação manual nesta fase (sem orquestrador gerenciando o ciclo de vida). `unless-stopped` é estritamente mais previsível para um operador humano.
- **Por que não `on-failure`:** não reinicia em caso de reboot do host/restart do Docker daemon a menos que combinado com outras flags — `unless-stopped` já cobre o caso de falha (`on-failure` seria um subconjunto mais restrito, sem ganho aqui) e também cobre reboot do host, que `on-failure` sozinho não cobre.
- **Arquivos afetados:** nenhum (decisão de manter o que já existe).

## 8. Plano de Implementação

Cada etapa é pequena, ordenada, e pode ser validada isoladamente antes de avançar para a próxima. Nenhuma etapa desta seção é executada nesta tarefa — é o roteiro da(s) tarefa(s) seguinte(s).

### Etapa 1 — Backend: profile de produção
- **Arquivos alterados:** `backend/src/main/resources/application-prod.yml` (novo).
- **Comportamento esperado:** subir o backend com `SPRING_PROFILES_ACTIVE=prod` ativa shutdown gracioso, compressão, `forward-headers-strategy`, probes e níveis de log de produção, sem quebrar nenhum teste existente (que não usam esse profile).
- **Como validar:** `./mvnw test` continua verde; `./mvnw spring-boot:run -Dspring-boot.run.profiles=prod` local (com env vars mínimas) sobe sem erro.
- **Risco:** baixo — é um arquivo novo, aditivo; risco principal é um valor de propriedade YAML mal formatado (detectável no boot).

### Etapa 2 — Backend: Actuator, probes e matcher de segurança
- **Arquivos alterados:** `application-prod.yml` (probes), `SecurityConfig.java` (matcher `/actuator/health/**`).
- **Comportamento esperado:** `/actuator/health/liveness` e `/actuator/health/readiness` respondem sem autenticação; `readiness` reflete o Postgres, `liveness` não.
- **Como validar:** `curl http://localhost:8080/actuator/health/liveness` e `/readiness` com o Postgres up e depois com o Postgres parado (`docker compose stop postgres`) — `liveness` deve continuar `UP`, `readiness` deve virar `DOWN`.
- **Risco:** médio — é o ponto onde um erro de matcher pode acidentalmente tornar público algo que não devia, ou (o oposto) quebrar o healthcheck do Docker. Testar os dois cenários explicitamente antes de prosseguir.

### Etapa 3 — Backend: logging, shutdown gracioso, fail-fast de segredos
- **Arquivos alterados:** `application-prod.yml` (logging, `server.shutdown`), `ProductionReadinessValidator.java` (novo) + teste unitário.
- **Comportamento esperado:** boot com `JWT_SECRET` placeholder e `prod` ativo falha explicitamente; `docker stop` num container em requisição longa aguarda até o timeout configurado.
- **Como validar:** subir com `JWT_SECRET` de exemplo (placeholder) e `SPRING_PROFILES_ACTIVE=prod` — boot deve falhar com mensagem clara nos logs. Depois, com secret válido, subir normalmente e rodar `docker stop -t 30 <container>` durante uma requisição deliberadamente lenta (ex.: script que faz upload grande) e confirmar que ela completa antes do container morrer.
- **Risco:** médio — é o ponto mais fácil de causar um falso-positivo (validador rejeitando uma configuração válida) ou falso-negativo (não pegar um placeholder real). Cobrir com teste unitário dedicado antes de validar manualmente.

### Etapa 4 — Backend: JVM e Compose (profile + recursos)
- **Arquivos alterados:** `docker-compose.prod.yml` (`SPRING_PROFILES_ACTIVE`, `TZ`, `cpus`, `stop_grace_period`, healthcheck do backend apontando para `/readiness`).
- **Comportamento esperado:** `docker compose up` sobe o backend já em profile `prod`, respeitando os novos limites de CPU e o novo healthcheck.
- **Como validar:** `docker compose config` (sem segredos reais, só placeholders válidos) resolve sem erro; `docker compose up -d` e `docker compose ps` mostram `backend` `healthy` usando o novo endpoint (confirmável via `docker inspect` do healthcheck configurado).

## 11. Riscos e Trade-offs

| Risco/trade-off | Descrição | Mitigação/decisão |
|---|---|---|
| VPS pequena e limites de memória | A soma dos `mem_limit` (900+1400+700 = 3000m) mais o SO deixa pouca folga numa VPS de 4 GB | Premissa declarada explicitamente (§6.3.2); valores devem ser recalculados quando a VPS real for escolhida (fora do escopo desta sprint) |
| OOM do backend | `MaxRAMPercentage=70` de um `mem_limit` de 1400m ainda pode ser insuficiente sob carga real não testada | `ExitOnOutOfMemoryError` + `restart: unless-stopped` transformam um OOM em uma reinicialização limpa, não em travamento silencioso; sem heap dump por ora (§6.1.12) — diagnóstico fino fica para quando houver observabilidade |
| Readiness depender do banco | Um blip do Postgres marca o backend inteiro como `unhealthy`, mesmo que a JVM esteja saudável | Decisão consciente (§6.1.6) — é o sinal mais honesto disponível no modelo de saúde único do Docker Compose; liveness continua isolado do Postgres para não causar reinício desnecessário do processo |
| Variáveis build-time do Next.js | Qualquer mudança de `NEXT_PUBLIC_*` exige rebuild completo da imagem, não um simples restart | Documentado explicitamente na matriz (§7/§6.2.1) — é uma limitação estrutural do Next.js, não algo que este design resolve (resolver exigiria um mecanismo de rewrite em runtime, avaliado e descartado como over-engineering para um único tenant nesta fase) |
| Duplicação futura de headers com o Caddy | Se o Caddy (11A.3) também declarar CSP/X-Frame-Options, os dois podem divergir e um navegador aplica regras conflitantes de forma imprevisível | Fronteira de responsabilidade decidida agora (§6.2.3): Next.js é a fonte da verdade para headers de aplicação, Caddy fica só com HSTS/TLS. Revisitar explicitamente na 11A.3 |
| Migrations automáticas no boot | Uma migration com erro impede o backend de subir, sem rollback automático | Comportamento intencional (§6.1.3) — falhar visivelmente é preferível a mascarar; requer disciplina de revisão de migration antes de qualquer deploy futuro (fora do escopo de automação aqui) |
| Armazenamento local (não object storage) | `backend_storage` é um volume Docker local — não há redundância nem backup automático ainda | Já era uma limitação conhecida da 11A.1; nenhuma mudança de arquitetura de storage nesta sprint (fora do escopo — backup é 11A.5) |
| Publicação temporária de portas | `BACKEND_PORT`/`FRONTEND_HOST_PORT` continuam expostas diretamente ao host/rede até o Caddy existir | Já documentado como temporário desde a 11A.1; sem TLS, tráfego nessas portas é HTTP puro — aceitável apenas para o cenário de VPS ainda não provisionada/sem tráfego real de produção |
| Healthcheck raso vs. profundo | `/actuator/health/readiness` é mais profundo que `/` do frontend (que não verifica nada além do processo Node) | Assimetria intencional — o backend tem uma dependência externa real (Postgres) que vale a pena verificar; o frontend não tem nenhuma dependência que devesse bloquear sua própria saúde (§6.2.4) |
