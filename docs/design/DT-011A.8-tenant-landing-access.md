# DT-011A.8 — Tenant Landing Access

- **Status:** Implemented
- **Sprint:** 11A.8
- **Depende de:** 11A.7 (Platform Admin & Multi-tenancy) — concluída e validada

---

## 1. Estado atual

Inspecionado o código real pós-11A.7 (backend e frontend, já implementados e validados):

**Backend:**
- `GET /admin/companies/{id}` (`AdminController`/`AdminCompanyService`) retorna `CompanyAdminDetailResponse { company: CompanyAdminDetail, owners: [...] }`, e `CompanyAdminDetail` **já inclui `slug`** (`id,name,slug,email,country,tradeName,status,createdAt`).
- `GET /auth/me` (`AuthController`/`AuthService.me()`) retorna `MeResponse { user, company, ... }`, e o `CompanyResponse` do pacote `auth` **já inclui `slug`** (`id,name,slug,email,country,status`).
- `GET /public/tenant` resolve o `Host` **efetivo da própria requisição HTTP** (corrigido na revisão anterior — sem query param, sem `X-Forwarded-Host`) para um slug, via `TenantResolutionService`: extrai o rótulo de `{slug}.{app.platform.base-domain}`, ou cai no fallback `PLATFORM_DEFAULT_TENANT_SLUG` se configurado, ou `404`.
- `app.platform.base-domain` (env `PLATFORM_BASE_DOMAIN`, default `localhost`) só existe hoje como propriedade **backend**, nunca exposta em nenhuma resposta de API.
- `getPublicSite()` já rejeita `Company.status != ACTIVE` com `404` (sem vazar que o tenant existe).

**Frontend:**
- `frontend/.env.local`/`.env.example`: **não existe mais** `NEXT_PUBLIC_COMPANY_SLUG`. Restam `NEXT_PUBLIC_API_BASE_URL` (obrigatório) e `NEXT_PUBLIC_SITE_URL` (opcional) — ambos platform-wide, não específicos de tenant.
- `(public)/page.tsx` não recebe mais slug nenhum como prop — delega inteiramente a `PublicSiteIntegrationShell`.
- `usePublicTenant()` (`public-site-hooks.ts`) chama `fetchPublicTenant()` → `GET /public/tenant` **sem nenhum parâmetro** — a chamada é feita pelo próprio browser (`"use client"`), então o header `Host` real da requisição já é o domínio que o visitante está de facto a visitar (chamada same-origin através de `NEXT_PUBLIC_API_BASE_URL`, que por sua vez é o próprio domínio público quando existir Caddy — Sprint 11A.3). `window.location.host` só é usado como **chave de cache do React Query**, nunca é enviado ao backend.
- `middleware.ts` só intercepta `/dashboard/:path*` e `/admin/:path*` — a landing pública (`/`) e qualquer subdomínio não passam pelo middleware.
- `AdminController`'s equivalente no frontend (`src/features/platform-admin/`) já tem `CompanyDetailPage.tsx` (tela `/admin/companies/{id}`) com ações existentes (ativar/desativar, convidar/reemitir/revogar owner) — mostra `company.slug` mas não tem link para a landing.
- Dashboard (`DashboardShell.tsx`) já exibe `session.company.name`; `session.company.slug` está disponível no mesmo objeto (`CompanyResponse` do `auth.ts`) mas não é usado ainda.
- `infra/caddy/Caddyfile`: um único bloco de site (`{$CADDY_HOST}` = `:80` hoje), sem wildcard/roteamento por domínio — inalterado desde 11A.7.
- `infra/compose/docker-compose.prod.yml`: build args do frontend hoje são só `NEXT_PUBLIC_API_BASE_URL`/`NEXT_PUBLIC_SITE_URL` (ambos platform-wide).

## 2. Problema

Depois de criar uma Company (via onboarding do SUPER_ADMIN) e depois do OWNER aceitar o convite e configurar a empresa, **não existe nenhum atalho na UI** para abrir a landing pública correspondente. O operador (SUPER_ADMIN) e o próprio OWNER precisam montar a URL manualmente (e hoje nem teriam como saber qual é o domínio correto, já que isso nunca foi um requisito antes do runtime tenant resolution existir).

## 3. Fluxo SUPER_ADMIN

Em `/admin/companies/{id}` (`CompanyDetailPage.tsx`), a resposta de `GET /admin/companies/{id}` já traz `company.slug` — nenhum dado novo é necessário. Adicionar um botão "Visualizar landing" que constrói a URL pública a partir desse `slug` (algoritmo no §7) e abre em nova aba (`target="_blank" rel="noopener noreferrer"`, ou `window.open`).

## 4. Fluxo OWNER

No dashboard, `session.company.slug` (de `GET /auth/me`, já carregado pelo `AuthProvider`/`useAuth()`) já está disponível — nenhum dado novo é necessário. Adicionar a ação "Visualizar site" no mesmo local onde o nome da empresa é exibido (`DashboardShell.tsx`), abrindo a landing do próprio tenant em nova aba, com a mesma construção de URL do §7.

## 5. Estratégia local

`*.localhost` resolve para loopback automaticamente (RFC 6761), sem editar `/etc/hosts` — já confirmado e em uso desde a Sprint 11A.7 (`TenantResolutionIntegrationTest`, testes locais com `jr-pinturas.localhost:3001`). Não há Caddy no caminho local (o frontend roda direto via `next dev`/`next start` na porta configurada em `.env.local`) — o servidor Next.js recebe a conexão diretamente e aceita qualquer valor de `Host` enviado pelo cliente, sem validação prévia. Isso já é exatamente o mecanismo usado pelos testes E2E de tenant resolution da sprint anterior; esta sprint não introduz nada novo aqui, só **usa o mesmo mecanismo para navegação manual via botão** em vez de apenas testes automatizados.

Local dev: `PLATFORM_BASE_DOMAIN=localhost` (já é o default do backend). O botão abre `http://{slug}.localhost:{porta-do-frontend}`.

## 6. Estratégia produção

Hoje (antes da Sprint 11C): não existe DNS real nem bloco wildcard no Caddy — uma URL `https://{slug}.{base-domain}` construída pelo botão **pode não ser alcançável ainda** se `base-domain` não for um domínio real com wildcard configurado. Isso é uma limitação transitória aceita (ver §20/riscos), não um defeito desta sprint — o botão calcula a URL **correta para a arquitetura final**, e passa a funcionar de fato assim que a Sprint 11C configurar domínio/wildcard real, **sem qualquer mudança de código nesta sprint ou na 11C do lado do botão**.

## 7. Como construir a URL pública

Algoritmo (client-side, puro, sem chamada de rede adicional):

```
url = new URL(NEXT_PUBLIC_SITE_URL ?? window.location.origin)
if (NEXT_PUBLIC_PLATFORM_BASE_DOMAIN configurado e não vazio):
    url.hostname = `${slug}.${NEXT_PUBLIC_PLATFORM_BASE_DOMAIN}`
else:
    // ainda não configurado (produção pré-11C, ou dev sem a variável) —
    // degrada graciosamente para a própria origem atual, sem tentar montar
    // um subdomínio que não seria resolvível de qualquer forma.
    (mantém url como está)
return url.toString()
```

Reaproveita **protocolo e porta** de `NEXT_PUBLIC_SITE_URL` (já configurado hoje, platform-wide) — só troca o **hostname** pela combinação `{slug}.{baseDomain}`. Resultado local: `http://jr-pinturas.localhost:3001/`. Resultado produção (pós-11C): `https://jr-pinturas.plataforma.com/`.

## 8. Fonte do slug

Contratos **já existentes**, sem nenhuma mudança:
- SUPER_ADMIN: `CompanyAdminDetail.slug` (resposta de `GET /admin/companies/{id}`, já consumida por `CompanyDetailPage.tsx`).
- OWNER: `CompanyResponse.slug` (dentro de `MeResponse`, já carregado por `useAuth()`/`AuthProvider` e disponível como `session.company.slug`).

## 9. Fonte do base domain

**Não existe hoje nenhuma exposição do `app.platform.base-domain` do backend para o frontend** — é uma propriedade puramente backend (usada só por `TenantResolutionService`). Avaliadas duas opções:

| Opção | Descrição | Prós | Contras |
|---|---|---|---|
| A | Novo campo numa resposta de API existente (ex.: incluir `baseDomain` em `CompanyAdminDetail` ou criar um endpoint de config pública) | Fonte única no backend | Viola a instrução explícita de não inventar endpoint/campo se não for necessário; acopla um dado de infraestrutura de plataforma a uma resposta de domínio de negócio |
| B | Nova variável de build **platform-wide** `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN`, análoga a `NEXT_PUBLIC_API_BASE_URL`/`NEXT_PUBLIC_SITE_URL` já existentes | Zero mudança de contrato backend; mesma natureza das duas variáveis platform-wide que já existem hoje (não determina qual tenant, é o mesmo valor para todos); simetria direta com `PLATFORM_BASE_DOMAIN` do backend | Precisa existir em dois lugares (backend e frontend) — mitigado abaixo |

**Decisão proposta: Opção B.** É crítico notar a diferença com `NEXT_PUBLIC_COMPANY_SLUG` (removida na 11A.7): aquela variável **determinava qual tenant** uma imagem servia (violava a regra 2 desta sprint). `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN` **não determina tenant nenhum** — é uma constante da plataforma, igual para todos os tenants, exatamente como `NEXT_PUBLIC_API_BASE_URL` já é hoje. Bakeá-la no build não reintroduz o problema que a 11A.7 resolveu.

Mitigação da duplicação: no `docker-compose.prod.yml`, o build-arg do frontend (`NEXT_PUBLIC_PLATFORM_BASE_DOMAIN`) deve ler da **mesma** variável de ambiente `PLATFORM_BASE_DOMAIN` que já configura o backend em `production.env` — uma única fonte de verdade no arquivo de configuração do operador, só repassada para dois destinos (`app.platform.base-domain` no backend, `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN` no build do frontend).

## 10. Comportamento localhost

Confirmado (reaproveita o que a 11A.7 já validou, nada novo): Chrome/Firefox/Safari e o resolvedor de nomes do macOS tratam `*.localhost` como loopback automaticamente (RFC 6761). O servidor Next.js local (`next dev`/`next start`, sem Caddy no caminho) aceita qualquer `Host` recebido sem validação. Nenhuma mudança em `/etc/hosts`, nenhuma mudança de infraestrutura local é necessária.

## 11. Interação com `GET /public/tenant`

**Nenhuma interação direta.** O botão só constrói uma URL e abre uma nova aba — não chama `/public/tenant` nem nenhum outro endpoint. Uma vez que a nova aba carrega essa URL, o fluxo padrão já existente (Host real → `usePublicTenant()` → `GET /public/tenant` → slug → `GET /public/sites/{slug}`) acontece exatamente como para qualquer visitante real, sem nenhum código especial para o caso "vim de um clique no admin/dashboard".

## 12. Segurança

- Nenhum dado novo é exposto: `slug` já é público por natureza (aparece na própria URL pública) e já está disponível nas duas respostas usadas.
- `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN` não é segredo — é, por definição, visível a qualquer visitante na barra de endereço de qualquer tenant.
- SUPER_ADMIN pode abrir a landing de qualquer Company, incluindo uma `INACTIVE` — o link resultante simplesmente resulta em `404` (mesmo comportamento de `getPublicSite` já existente, nenhuma informação extra vaza). Recomendação de UX (não bloqueante): desabilitar/anotar o botão quando `company.status !== "ACTIVE"`, para não confundir o operador com um link "morto" — decisão de implementação, não requisito de segurança.
- Nenhuma superfície de autenticação/autorização é tocada — a landing pública continua com as mesmas regras de acesso (`permitAll`, `/public/**`) já existentes.
- `window.open`/link com `target="_blank"` deve incluir `rel="noopener noreferrer"` (boa prática padrão, evita `window.opener` reverse tabnabbing) — nota de implementação para o frontend.

## 13. Impacto no middleware

**Nenhum.** `middleware.ts` só intercepta `/dashboard/:path*` e `/admin/:path*` (matcher explícito) — a landing pública em qualquer subdomínio nunca passa pelo middleware, hoje ou depois desta sprint.

## 14. Impacto em Caddy/Docker

**Nenhuma mudança de infraestrutura nesta sprint** (proibido pelas regras 6/7). Documentado para referência:
- Local: sem Caddy no caminho, nada a mudar.
- Produção hoje (pré-11C): Caddy com bloco único (`CADDY_HOST=:80`), sem wildcard — uma URL `{slug}.{base-domain}` só será de fato alcançável quando a Sprint 11C configurar o domínio real + bloco wildcard no Caddyfile. Isso é uma limitação aceita e documentada (§6/§20), não algo que esta sprint resolve.
- `docker-compose.prod.yml`: build args do frontend ganham `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN: ${PLATFORM_BASE_DOMAIN:?...}` (reaproveitando a mesma env var do backend) — implementação futura, não feita nesta tarefa de design.

- `GET /auth/me` → `MeResponse.company.slug` (já existente).

## 16. Endpoint novo é necessário?

**Não.** Os dois contratos acima já fornecem tudo que a UI precisa (slug). O único dado que falta (o base domain da plataforma) é resolvido com uma variável de build **platform-wide** no frontend (§9), não com um endpoint — decisão explícita para não acoplar um dado de configuração de infraestrutura a uma resposta de domínio de negócio (Company), e para manter o padrão já estabelecido por `NEXT_PUBLIC_API_BASE_URL`/`NEXT_PUBLIC_SITE_URL`.

## 19. Critérios de aceite

- SUPER_ADMIN consegue abrir a landing de qualquer Company a partir de `/admin/companies/{id}`, em nova aba.
- OWNER consegue abrir a própria landing a partir do dashboard, em nova aba.
- Nenhum endpoint backend novo foi criado.
- Nenhuma migration foi alterada.
- `NEXT_PUBLIC_PLATFORM_BASE_DOMAIN` é platform-wide (mesmo valor para todos os tenants) — nunca um valor por-tenant.
- A mesma imagem de frontend continua servindo múltiplos tenants sem rebuild (a nova variável não quebra esse critério da 11A.7, já que não é tenant-specific).
- Funciona localmente via `{slug}.localhost:{porta}` sem editar `/etc/hosts`.
- Constrói corretamente a URL de produção (`{slug}.{base-domain}`) mesmo antes de haver DNS real — fica pronta, latente, para a Sprint 11C, exatamente como o próprio `PLATFORM_DEFAULT_TENANT_SLUG` já ficou pronto/latente na 11A.7.

## 20. Fora de escopo

`company_domains`, DNS real, Cloudflare, TLS wildcard, bloco Caddy por domínio (tudo isso continua Sprint 11C). Reachability real da URL de produção antes da 11C (limitação aceita, documentada, idêntica em natureza à do `PLATFORM_DEFAULT_TENANT_SLUG` já aceita na 11A.7). Qualquer UX de "copiar link"/compartilhamento além do botão simples de abrir em nova aba. Desabilitar visualmente o botão para companies `INACTIVE` é uma melhoria de UX recomendada, não obrigatória.
