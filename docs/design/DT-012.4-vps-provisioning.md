# DT-012.4 — VPS Provisioning Plan (Design Only)

**Sprint:** 12.4
**Tipo:** Documento técnico (DT) — apenas design. Nenhum script, Dockerfile,
compose, workflow, Terraform, Ansible, ou recurso Hetzner foi criado por esta
tarefa. Nenhum comando remoto foi executado.
**Status:** Proposed
**Revisão:** sizing/custo do VPS atualizados — a Hetzner aplicou um reajuste de
preços em 15/06/2026 que descontinuou a linha CPX21/CPX31/CPX41 para novos
pedidos, substituindo-a por CPX22/CPX32/CPX42 a preços substancialmente mais
altos (consultado diretamente em `docs.hetzner.com`, Agosto/2026 — ver §4).
Também fecha as decisões humanas pendentes de região, usuário administrativo,
`fail2ban`, visibilidade do GHCR, estratégia de secrets desta fase e TTL de
DNS (§18). Nenhuma outra decisão arquitetural foi alterada nesta revisão.

## 1. Objetivo

Definir, por completo, como o primeiro VPS de produção real do Contractor
Platform será provisionado — especificação de hardware, estrutura de
diretórios, usuários, SSH, firewall, Docker, mecanismo de deploy, segredos,
backup, logs, observabilidade e segurança do host — de forma suficiente para
que qualquer engenheiro consiga executar o provisionamento seguindo apenas
este documento, sem decisões de arquitetura deixadas para serem inventadas no
momento da execução.

Este documento **não reabre** decisões de arquitetura de aplicação já tomadas
(`DT-011A.2`–`.5`, `DT-012.1`) — ele as adota, cita a fonte, e preenche
especificamente a lacuna que nenhuma DT anterior preencheu: **o host** em si
(a VPS), não os containers que rodam dentro dele.

## 2. Escopo e não-escopo

**Escopo:** os 14 itens listados na tarefa (especificação do VPS → checklist
de provisionamento), cada um como seção numerada abaixo, mais uma seção
consolidando decisões humanas pendentes.

**Não-escopo (explícito):**
- Nenhum script (`.sh`), Dockerfile, `docker-compose.yml`, workflow GitHub
  Actions, Terraform ou Ansible é criado por este documento.
- Nenhum recurso é criado na Hetzner (VPS, Storage Box, Cloud Firewall) nem em
  nenhum outro provedor.
- Nenhum comando é executado contra qualquer host, remoto ou local.
- Não redesenha a arquitetura de containers (`docker-compose.prod.yml`,
  `Caddyfile`, Dockerfiles) — já decidida e implementada (`DT-011A.1`–`.3`,
  `DT-012.1`, Sprints 12.2/12.3). Este documento assume essa arquitetura como
  dada e trata exclusivamente do host que a executa.
- Não resolve as pendências humanas já registradas em DTs anteriores
  (gerenciador de segredos dedicado, visibilidade do pacote GHCR) — apenas as
  cita onde afetam uma decisão desta DT, sem tentar decidi-las aqui.
- Não introduz alta disponibilidade, múltiplas réplicas, ou failover — fora de
  escopo por decisão já registrada (`DT-012.1 ADR-002`/`ADR-004`), reafirmada
  aqui sem mudança.

## 3. Fontes já decididas (não reabertas por este documento)

- **Topologia de containers** (`DT-011A.3`, `DT-012.1 §4`–`§9`): `Cloudflare →
  Caddy → {frontend, backend} → PostgreSQL`, tudo num único host via Docker
  Compose — este documento adota essa topologia como dada.
- **Especificação de custo/VPS estimada em `DT-012.1 §23` está desatualizada
  e é substituída por esta revisão (§4):** a estimativa original (CPX21 a
  €9.49/mês) refletia o preço da Hetzner antes do reajuste de 15/06/2026. Este
  documento não reabre a *arquitetura* (continua um único VPS, mesma
  topologia) — reabre exclusivamente o *dado de preço/plano*, que mudou por
  fato externo, não por decisão de design. Storage Box BX11 (1 TB) a
  €3.20/mês para backup permanece sem alteração (§4/§12) — o reajuste de
  junho/2026 não atingiu essa linha de produto.
- **Firewall de borda** (`DT-012.1 §5.1`): Hetzner Cloud Firewall com TCP
  80/443 abertos (restritos aos ranges Cloudflare quando o Proxy estiver ativo
  — já preparado em `infra/caddy/Caddyfile`, Sprint 12.3) + TCP 22 restrito ao
  IP do operador. Adotado sem mudança (§8).
- **Deploy por imagem publicada, não build na VPS** (`DT-011A.4`):
  `docker compose pull` + `docker compose up -d` usando `APP_VERSION=<sha
  completo>`, nunca `--build` na VPS, `:latest` nunca publicada. Adotado sem
  mudança (§10).
- **Backup** (`DT-011A.5`, `infra/backup/`): Restic, `pg_dump --format=custom`
  + backup de arquivos, diário às 03:15 UTC via systemd timer (template já
  versionado, não instalado ainda), retenção 7 diárias/4 semanais/6 mensais,
  destino Storage Box via SFTP, `production.env` incluído dentro do snapshot
  taggeado `postgres`. Adotado sem mudança (§12).
- **Logging dos containers** (`docker-compose.prod.yml`, `x-logging` anchor):
  driver `json-file`, `max-size: 10m`, `max-file: 5`, por serviço. Adotado sem
  mudança (§13).
- **Observabilidade** (`DT-012.1 §18`/`ADR-006`): Actuator (health/info) +
  healthchecks Docker, sem Prometheus/Grafana ainda. Adotado sem mudança
  (§14).
- **Secrets sem gerenciador dedicado** (`DT-012.1 §16`): decisão consciente de
  não introduzir Vault/equivalente nesta fase — pendência de "onde
  `RESTIC_PASSWORD`/chave SSH/`CLOUDFLARE_API_TOKEN` ficam guardados" segue em
  aberto, carregada aqui (§18), não resolvida por este documento.

## 4. Especificação do VPS

**Contexto da revisão:** a Hetzner aplicou um reajuste de preços em
15/06/2026 (`docs.hetzner.com/general/infrastructure-and-availability/
price-adjustment/`, consultado diretamente nesta revisão, Agosto/2026) que
**descontinuou a linha CPX21/CPX31/CPX41/CPX51 para novos pedidos** —
substituída por uma linha renumerada CPX22/CPX32/CPX42/CPX52/CPX62, com
specs de vCPU ligeiramente diferentes e preços 2,4×–2,75× mais altos (Alemanha/
Finlândia). A CPX21 (3 vCPU/4 GB/80 GB) que `DT-012.1 §23` estimava a
€9.49/mês simplesmente não existe mais como opção de compra — não é possível
"confirmar" aquele plano no provisionamento real. Esta seção substitui a
especificação anterior por completo.

### 4.1 Requisitos reais (derivados do que já está implementado, não estimados)

Antes de comparar planos, os requisitos abaixo vêm diretamente do que
`docker-compose.prod.yml` **já configura hoje** (Sprints 11A.2/12.2/12.3),
não de uma premissa nova:

| Serviço | `cpus` (limite) | `mem_reservation` | `mem_limit` | Por quê |
|---|---|---|---|---|
| `postgres` (17-alpine) | 1.0 | 500m | 900m | Banco relacional — beneficia-se de RAM extra do SO para cache de página além do `shared_buffers` |
| `backend` (Java 25, Spring Boot) | 1.0 | 900m | 1400m | JVM — `-XX:MaxRAMPercentage=70` já configurado; heap/metaspace/threads cabem no `mem_limit`, mas picos de GC/JIT warm-up se beneficiam de folga do host |
| `frontend` (Next.js/Node 22, standalone) | 0.5 | 350m | 700m | Processo Node único, sem SSR pesado por request |
| `caddy` (custom, Sprint 12.3) | 0.5 | 128m | 256m | Proxy leve, sem estado de aplicação |
| **Soma** | **3.0 vCPU** | **1.83 GB** | **3.18 GB** | — |

A isso soma-se margem para o próprio Ubuntu + Docker Engine (tipicamente
300–800 MB em repouso) e folga real para o SO cachear página do Postgres —
memória que não aparece em nenhum `mem_limit` de container, mas que é
justamente o que faz um Postgres com poucos GB de RAM se comportar bem sob
carga real.

**Arquitetura de CPU:** todas as imagens publicadas pelo pipeline GHCR
(`DT-011A.4 §12`) são `linux/amd64` exclusivamente — publicar `arm64` foi
avaliado e rejeitado (`DT-011A.4`: exigiria emulação QEMU no runner, sem
consumidor real da arquitetura). Isso **elimina a linha CAX (Arm/Ampere)**
da Hetzner como opção, apesar de ser a mais barata — as imagens do backend/
frontend/Caddy simplesmente não existem em `arm64` hoje; usar uma CAX
exigiria reabrir `DT-011A.4` para publicar multi-arch, fora de escopo desta
DT.

### 4.3 Decisão: CPX32

| Item | Decisão |
|---|---|
| Provedor | Hetzner Cloud (já adotado desde `DT-011A.3`, reafirmado `DT-012.1`) |
| Plano | **CPX32** — 4 vCPU AMD EPYC (compartilhado, linha "Regular Performance"), 8 GB RAM, 160 GB NVMe SSD, 20 TB tráfego incluído |
| Custo | **€35.49/mês** (excl. IVA; ≈€41.99 incl. IVA alemão) — preço pós-reajuste de 15/06/2026, consultado diretamente em `docs.hetzner.com`, Agosto/2026 |
| Sistema operacional | **Ubuntu 24.04 LTS** (imagem oficial Hetzner) — sem alteração desta revisão |
| Arquitetura | `linux/amd64` — obrigatório (§4.1), sem alternativa |
| Plano de expansão | CPX42 (8 vCPU, 16 GB RAM, €69.49/mês) — ver §4.4 |
| Região (datacenter) | **Nuremberg (NBG1), Alemanha** — decisão fechada nesta revisão (§18); sem impedimento técnico identificado, mesma faixa de preço que qualquer outro datacenter alemão/finlandês da Hetzner |

**Justificativa (não apenas o preço):** a CPX22 mais barata (€19.49/mês) fica
**abaixo** do que os 4 serviços já somam hoje em `cpus` (2 vCPU providos vs.
3.0 vCPU configurados como limite) — não é uma questão de folga apertada, é
literalmente insuficiente para o que o Compose já pede, mesmo antes de
considerar SO/Docker/cache do Postgres. A CPX32 entrega o dobro de vCPU (4)
e mais que o dobro de RAM (8 GB) do que a soma dos `mem_limit` atuais (3.18
GB) exige, deixando ≈4.3 GB de folga real após descontar os containers — essa
folga cobre margem de SO/Docker, cache de página do Postgres, e picos de JIT/
GC do backend sem depender de swap. O disco (160 GB, o dobro da CPX22) dá
folga adicional para camadas Docker + volumes crescerem sem pressão imediata.
A linha CX mais barata foi avaliada e não adotada por incerteza técnica
genuína sobre suas garantias de CPU (acima), não por preferência de custo —
exatamente o tipo de escolha que não deve ser feita só pelo menor preço.

### 4.4 Caminho de expansão vertical (sem mudança de arquitetura)

Reafirma `DT-012.1 ADR-004` ("escalar reativamente, não preventivamente"),
sem reabrir a decisão: se a CPX32 se mostrar insuficiente sob carga real, o
próximo passo é CPX42 (8 vCPU/16 GB, €69.49/mês) — um resize vertical da
mesma VPS (Hetzner permite redimensionar sem trocar de host, com uma janela
curta de reinício), não uma mudança de topologia. Nenhuma decisão de HA/
múltiplas réplicas é antecipada por este caminho.

### 4.5 Armazenamento

Os 160 GB de disco local da CPX32 hospedam o sistema operacional, as imagens/
camadas Docker, e os volumes nomeados do Compose (`postgres_data`,
`backend_storage`, `caddy_data`, `caddy_config` — ver §5 sobre onde eles
fisicamente residem). A Storage Box (1 TB, separada, €3.20/mês — **sem
alteração de preço no reajuste de junho/2026**) é **exclusivamente para
backup** (§12) — nunca para servir dados em produção. 160 GB é folgado para o
volume de dados atual (banco pequeno, poucos uploads); revisar quando o
volume de dados crescer (mesma lógica de escala vertical reativa acima).

## 5. Estrutura de diretórios

A arquitetura já implementada usa **volumes Docker nomeados** para todo dado
persistente (`postgres_data`, `backend_storage`, `caddy_data`,
`caddy_config` — `docker-compose.prod.yml`, decisão de `DT-011A.1` em diante,
**não revisitada por este documento**). Isso significa que não existe (nem
deveria existir) um diretório `/storage` bind-mounted diretamente no host —
o Docker já gerencia esse dado sob seu próprio data-root. A estrutura abaixo
reflete essa realidade em vez de forçar um layout genérico que contradiria o
que já está implementado e validado (Sprints 12.2/12.3).

| Diretório | Conteúdo | Gerenciado por | Observação |
|---|---|---|---|
| `/opt/contractor-platform/` | Checkout do repositório (`git clone`/`git pull` — ver §10) | Operador (via `git`) | Contém `infra/compose/`, `infra/caddy/`, `infra/env/`, `infra/backup/` — tudo que o deploy precisa |
| `/opt/contractor-platform/infra/env/production.env` | Segredos reais da aplicação | Operador (transferência manual segura, nunca `git`) | `chmod 600`, nunca versionado — ver §11 |
| `/opt/contractor-platform/infra/backup/env/backup.env` | Segredos do Restic (`RESTIC_REPOSITORY` real, credencial SFTP) | Operador | `chmod 600`, nunca versionado |
| `/etc/contractor-platform/restic-password` | Senha do repositório Restic | Operador | `chmod 600` — mesmo padrão já usado na validação local (`infra/backup/README.md`) |
| `/var/cache/contractor-platform/restic/` | Cache local do Restic (metadados, não os dados em si) | Restic (automático) | Existe mesmo com repositório remoto (Storage Box) |
| *(Docker data-root — não gerenciado manualmente)* | `postgres_data`, `backend_storage`, `caddy_data`, `caddy_config` | Docker | Fisicamente sob `/var/lib/docker/volumes/` por padrão — **nunca** acessado/editado diretamente pelo operador; toda interação passa por `docker compose`/`docker volume` |
| *(Docker — não gerenciado manualmente)* | Logs dos containers (`json-file`, já configurado) | Docker | Sob `/var/lib/docker/containers/.../*.json.log` por padrão — ver §13, não relocado |

**Por que não `/backups` e `/logs` como diretórios próprios do host:**
backups vão direto para a Storage Box via SFTP (o repositório Restic em si
não vive no host, exceto o cache leve acima); logs de aplicação vão para
stdout/stderr, capturados pelo driver `json-file` do Docker — introduzir
diretórios adicionais para "backups" ou "logs" no host duplicaria um destino
que já existe e já foi decidido, sem necessidade.

## 6. Usuários

- **`root`:** existe por padrão na imagem Hetzner. Usado **uma única vez**,
  no primeiro acesso (bootstrap), para criar o usuário administrativo — depois
  disso, login SSH como `root` é desabilitado (§7). `root` nunca é usado para
  operação do dia a dia.
- **Usuário administrativo (`deploy` — decisão fechada nesta revisão, §18):**
  único usuário humano nomeado, criado no bootstrap.
  Membro dos grupos:
  - `sudo` — necessário para operações privilegiadas (firewall, instalação de
    pacotes, unidades systemd).
  - `docker` — necessário para rodar `docker compose` sem prefixar `sudo` em
    cada comando. **Nota de segurança explícita:** pertencer ao grupo
    `docker` já equivale, na prática, a `root` no host (o daemon Docker roda
    como `root` e qualquer membro do grupo `docker` pode montar `/` dentro de
    um container) — isso não é uma redução de privilégio em relação a usar
    `sudo docker`, é apenas conveniência operacional. Documentado para não
    criar a falsa impressão de que `deploy` tem menos poder que `root`.
- **Sem contas compartilhadas:** hoje há um único operador humano — mesmo
  assim, cria-se um usuário nomeado (não se opera como `root` "porque é mais
  rápido"). Se a equipe crescer, cada humano recebe sua própria conta/chave,
  nunca uma credencial compartilhada.
- **Propriedade de arquivos:** toda a árvore `/opt/contractor-platform/` e os
  arquivos de segredo em `/etc/contractor-platform/` pertencem a `deploy`,
  nunca a `root` nem a um grupo amplo.

## 7. SSH

- **Autenticação:** somente por chave pública (`PasswordAuthentication no`).
  Nenhuma senha é aceita para nenhum usuário, em nenhum momento após o
  bootstrap inicial.
- **Login root:** desabilitado (`PermitRootLogin no`) assim que o usuário
  administrativo estiver criado e validado — não antes (evita ficar sem
  acesso caso o bootstrap falhe).
- **Porta:** mantida em **22** (padrão). Trocar a porta SSH para um valor
  não-padrão foi considerado e **rejeitado** como controle principal — é
  segurança por obscuridade, não uma redução real de superfície de ataque; o
  controle real já está decidido (`DT-012.1 §5.1`): o Hetzner Cloud Firewall
  restringe a porta 22 ao IP do operador, então a porta em si nunca fica
  exposta a varredura pública independentemente do número usado. Mudar a
  porta é aceitável como camada extra opcional, não como substituto dessa
  regra de firewall.
- **`fail2ban` — decisão fechada nesta revisão: não incluir no
  provisionamento inicial.** Com `PasswordAuthentication no` e
  `PermitRootLogin no` já decididos acima, não existe nenhuma credencial que
  uma tentativa de força bruta possa efetivamente adivinhar — a superfície de
  ataque que `fail2ban` mitigaria (adivinhação de senha) já está eliminada
  estruturalmente pela autenticação por chave, não apenas reduzida. O valor
  residual de `fail2ban` nesse cenário é só reduzir ruído de log de conexões
  recusadas — cosmético, não uma redução real de risco. Não é uma rejeição
  permanente: se o volume de tentativas de conexão gerar ruído operacional
  incômodo (não um risco de segurança), reavaliar a inclusão então.
- **Encaminhamento de agente SSH:** decisão do operador no momento da conexão,
  não uma configuração do servidor — não tratado por este documento.

## 8. Firewall

**Camada 1 — Hetzner Cloud Firewall (já decidida, `DT-012.1 §5.1`, adotada
sem mudança):**

| Porta | Protocolo | Origem | Motivo |
|---|---|---|---|
| 22 (SSH) | TCP | IP do operador/bastion, restrito | Nunca aberto ao público |
| 80 (HTTP) | TCP | Qualquer origem (ou ranges Cloudflare quando o Proxy estiver ativo) | Redirecionamento para HTTPS pelo Caddy; validação ACME local não usa esta porta (DNS-01, `DT-012.1 §9`) |
| 443 (HTTPS) | TCP | Qualquer origem (ou ranges Cloudflare quando o Proxy estiver ativo) | Tráfego real da aplicação |
| Qualquer outra | — | — | Fechada. Postgres/backend/frontend nunca publicam porta no host (decisão de `docker-compose.prod.yml` desde `DT-011A.3`) — não há necessidade de regra alguma para eles, nem de exceção |

**Camada 2 — firewall no próprio host (`ufw`) — decisão nova desta DT:**
espelhar exatamente as mesmas regras acima diretamente no host, como defesa
em profundidade contra uma eventual reconfiguração incorreta ou reset do
Cloud Firewall. Postura padrão: negar toda entrada, permitir apenas
22/80/443 conforme a tabela acima; toda saída permitida (sem necessidade de
restringir tráfego de saída neste estágio). Esta é uma decisão nova — nenhum
DT anterior havia definido firewall a nível de host, só o de borda (Hetzner
Cloud Firewall).

**Por que nenhuma porta de aplicação precisa de regra:** Postgres (5432),
backend (8080) e frontend (3000) só escutam na rede Docker interna
(`internal`, bridge) — nunca no `0.0.0.0` do host. Um firewall de host correto
não precisa negá-los explicitamente porque eles nunca estão de fato expostos
à interface pública para começar; a postura "negar tudo, permitir só o
necessário" cobre isso automaticamente.

## 9. Docker

- **Instalação:** repositório APT oficial da Docker (`download.docker.com`),
  não os pacotes `docker.io`/`docker-compose` do repositório padrão do
  Ubuntu. Motivo: os pacotes do Ubuntu tipicamente atrasam versões e, mais
  importante, o repositório padrão não garante o **plugin `docker compose`
  v2** (subcomando integrado) que todo comando já documentado em
  `runbook.md`/`infra/README.md` assume — usar `docker-compose` (v1,
  hifenizado, binário separado) quebraria silenciosamente a compatibilidade
  com a documentação existente.
- **Pacotes:** `docker-ce`, `docker-ce-cli`, `containerd.io`,
  `docker-buildx-plugin`, `docker-compose-plugin`.
- **Versão:** acompanha o canal estável do Docker — nenhuma versão específica
  é fixada por este documento (diferente do `CADDY_VERSION` pinado no
  Dockerfile do Caddy, que precisa ser reprodutível em build; o Docker Engine
  do host é infraestrutura, não um artefato versionado em build).
- **Política de atualização:** **manual e deliberada**, nunca automática. Um
  reinício do daemon Docker em produção (o que uma atualização não supervisionada
  poderia causar) derruba temporariamente todos os containers — inaceitável
  sem uma janela escolhida. Atualizações de segurança do **sistema operacional**
  (pacotes não relacionados ao Docker) via `unattended-upgrades` escopado
  a patches de segurança são aceitáveis e recomendadas; os pacotes Docker
  ficam explicitamente excluídos desse canal automático (held/pinned), para
  que uma mudança de versão do Docker seja sempre uma ação planejada — mesmo
  princípio já aplicado ao `CADDY_VERSION` (Sprint 12.3: "bump deliberately,
  not silently").

## 10. Estrutura de deploy

**Imagens de aplicação — já decidido (`DT-011A.4`, adotado sem mudança):**
`docker compose pull` (usando `APP_VERSION=<sha completo>` do GHCR) seguido
de `docker compose up -d`. Nunca `--build` na VPS; `:latest` nunca é
publicada, então nunca é uma opção por engano.

**Visibilidade do pacote GHCR — decisão fechada nesta revisão: privado.**
Isso resolve a pendência registrada em `DT-011A.4 §20`, mas tem uma
implicação direta que `DT-011A.4` já havia previsto como contingência: um
pacote privado exige autenticação para `docker pull`/`docker compose pull` a
partir da VPS. Concretamente:
- Gerar um GitHub PAT (fine-grained, preferível ao clássico) escopado
  **somente** a `read:packages` no repositório do pacote — nenhuma outra
  permissão.
- Rodar `docker login ghcr.io` uma vez no bootstrap da VPS com esse token; a
  credencial fica persistida em `~/.docker/config.json` do usuário `deploy`
  (mesma árvore de permissões restritas de §6/§11 — não é um arquivo world-
  readable por padrão do Docker, mas não deve ser tratado como menos sensível
  que `production.env`).
- Esse PAT é, na prática, mais um segredo a gerenciar (§11) — mesma ausência
  de gerenciador dedicado, mesma rotação manual.

**Configuração/scripts (o que este documento decide, pois nenhum DT anterior
havia definido isso explicitamente):** como `docker-compose.prod.yml`,
`Caddyfile`, `infra/env/production.env.example` e os scripts de backup
chegam à VPS, já que eles não são publicados como imagem.

Duas opções consideradas:

| Opção | Descrição | Decisão |
|---|---|---|
| **A — `git clone`/`git pull`** | Checkout completo do repositório (público) em `/opt/contractor-platform` | **Adotada** |
| B — pacote de deploy mínimo | Só `infra/` sincronizado via `rsync`/`scp` a partir do CI | Rejeitada |

**Justificativa da opção A:** o repositório já é público (`DT-011A.4 §5.1`,
`DT-011A.4 §20`) — um `git clone` de leitura não exige nenhuma credencial
nova. O template systemd já versionado (`infra/backup/systemd/*.service`) já
assume `WorkingDirectory=/opt/contractor-platform/infra/backup/scripts` —
opção A é a única que torna esse template correto sem editá-lo. A opção B
economizaria espaço em disco de forma desprezível (o repositório inteiro é
pequeno) ao custo de mais um mecanismo de sincronização para manter
consistente — não vale a complexidade adicional.

**Fluxo de deploy resultante (ordem):**
1. `git pull` em `/opt/contractor-platform` — atualiza compose/Caddyfile/scripts/docs.
2. `docker compose pull` — baixa as imagens do `APP_VERSION` alvo.
3. `docker compose up -d` — recria só os containers cujo `image:`/config mudou.

**Regra operacional explícita:** `infra/env/production.env` **nunca** faz
parte do conteúdo versionado (gitignored) — um `git pull` normal não o toca,
mas nenhum comando destrutivo de `git` (`git clean`, `git checkout .`,
`git reset --hard`) deve rodar nesse diretório na VPS sem antes confirmar que
`production.env` não seria afetado (ele é untracked, não deveria ser
removido por essas operações no uso normal, mas a regra é registrada aqui
para quem implementar o script de deploy numa sprint futura).

## 11. Secrets

**Estratégia desta fase — decisão fechada nesta revisão:** `production.env`
protegido diretamente no host (permissão de arquivo, sem gerenciador
dedicado), consistente com o que já estava proposto abaixo. Isso fecha "como
tratamos secrets *nesta fase*" — não fecha, e não pretende fechar, a pergunta
maior de "qual gerenciador de segredos adotar quando a operação crescer",
que continua registrada como pendência separada (`DT-012.1 §16`, reafirmada
em §18).

| Item | Decisão |
|---|---|
| Localização | `/opt/contractor-platform/infra/env/production.env` — mesmo caminho relativo (`../env/production.env`) que `docker-compose.prod.yml` já espera a partir de `infra/compose/` |
| Permissões | `chmod 600`, dono `deploy` — nunca legível por grupo ou outros |
| Quem acessa | Só o usuário `deploy` via SSH; o daemon Docker (roda como `root`) lê o arquivo ao subir os containers — característica inerente ao Docker, não um gap introduzido por este arquivo |
| Como chega à VPS | Transferência manual segura (`scp`/equivalente sobre o próprio SSH já hardenizado, §7) feita pelo operador — nunca por `git`, nunca por canal não criptografado, nunca colado em um comando que apareça em `history`/logs |
| Backup | **Já decidido** (`DT-011A.5`, `infra/backup/README.md`): incluído dentro do snapshot Restic taggeado `postgres`, backupeado diariamente junto do dump do banco, criptografado pelo próprio Restic. Este documento não redecide isso, só confirma que a VPS real herda esse comportamento sem mudança |
| Rotação | **Não há mecanismo automático** (consistente com a decisão já registrada de não introduzir um gerenciador de segredos dedicado, `DT-012.1 §16`). Processo manual: gerar novo valor (ex. `openssl rand -base64 48` para `JWT_SECRET`; painel Cloudflare para `CLOUDFLARE_API_TOKEN`; `ALTER USER` no Postgres + atualização da variável para `POSTGRES_PASSWORD`) → editar `production.env` → `docker compose up -d` (recria só os containers afetados). Documentado aqui como processo, **não implementado como script** por este documento |
| GHCR PAT (`read:packages`) | **Novo nesta revisão** (§10) — decorre da decisão de GHCR privado. Vive em `~/.docker/config.json` do usuário `deploy` (mecanismo do próprio `docker login`, não um arquivo desta árvore de secrets) — mesma disciplina de rotação manual e mesma ausência de gerenciador dedicado que os demais itens desta tabela |
| Gerenciador de segredos dedicado | Pendência já registrada (`DT-012.1 §16`) — **não resolvida por este documento**, carregada para §18 |

## 12. Backup

Integralmente já decidido (`DT-011A.5`, `infra/backup/`) — este documento não
redecide nada, apenas registra o que a Sprint que provisionar a VPS real
precisa **ativar** (hoje só validado contra um repositório Restic local):

- **Banco (`postgres_data`):** `pg_dump --format=custom` diário, via
  `backup-postgres.sh`.
- **Uploads (`backend_storage`):** backup de arquivos diário, mesma janela,
  via `backup-files.sh`.
- **`caddy_data`:** recomendado/operacional, incluído por `backup-all.sh`.
- **Frequência:** diária, 03:15 UTC (systemd timer, `RandomizedDelaySec=300`,
  `Persistent=true` — roda o backup perdido assim que o host voltar, se
  esteve desligado no horário agendado).
- **Retenção:** 7 diárias + 4 semanais + 6 mensais (`restic forget --prune`).
- **Destino real:** Hetzner Storage Box (BX11, 1 TB, €3.20/mês) via SFTP —
  **ainda não provisionada**; até aqui só validado contra um repositório
  Restic local de teste. Trocar para a Storage Box real é, por desenho já
  existente, **só uma variável** (`RESTIC_REPOSITORY`) — nenhum script muda.
- **RPO/RTO:** RPO ≤ 24h, RTO da ordem de poucas horas, dependente de
  execução manual do runbook (`DT-011A.5 §17`) — sem alta disponibilidade.
- **Bloqueador de go-live já registrado, reafirmado aqui:** um restore
  completo contra a infraestrutura real (Storage Box real, não o repositório
  local de teste) precisa ser executado com sucesso pelo menos uma vez antes
  do go-live (`DT-011A.6 §28`, `DT-012.1 §14`).

## 16. Recuperação de desastre

Adotado sem mudança de `DT-011A.5 §14`/`§17`/`§19`/`§20` e `DT-012.1 §14`:

- **RTO ≈ algumas horas**, dependente de um operador humano seguindo o
  runbook — não há automação de restore total.
- **Sem alta disponibilidade** — um único VPS, um único Postgres, sem
  standby/failover automático. Declarado explicitamente para não sugerir uma
  garantia que esta arquitetura não entrega (reafirmando `DT-011A.5 §17`).

**Sequência concreta para "VPS perdida inteira", calibrada contra a
especificação desta DT (não uma arquitetura nova — só a aplicação prática do
que `DT-011A.5 §19`/`§20` já desenhou, contra o host específico definido em
§4-§9 aqui):**

1. Provisionar uma nova CPX32 seguindo §4-§9 deste documento (mesma região,
   mesmo processo de bootstrap).
2. Restaurar `production.env` e os demais segredos (`backup.env`,
   `restic-password`, GHCR PAT — §11) a partir do backup do operador (nunca
   do snapshot Restic para a senha do próprio Restic — dependência circular
   óbvia; a senha do Restic precisa sobreviver fora do sistema que ela
   protege).
3. `git clone` do repositório em `/opt/contractor-platform` (§10);
   `docker login ghcr.io` com o PAT restaurado (pacote privado, §10).
4. `docker compose pull` + `docker compose up -d` para as imagens do
   `APP_VERSION` mais recente conhecido como bom.
5. Restaurar o dump do PostgreSQL a partir do Restic (Storage Box).
6. Restaurar `backend_storage` a partir do Restic.
7. Validar healthchecks dos 4 serviços e smoke test manual pelas rotas
   públicas via Caddy.
8. Reapontar DNS (se o IP mudou) — Cloudflare, TTL baixo já seria uma boa
   prática a considerar no provisionamento real (fora do escopo desta DT
   decidir o TTL exato).

**Bloqueador de go-live já registrado, reafirmado:** esta sequência precisa
ser executada com sucesso pelo menos uma vez contra infraestrutura real antes
do go-live (não apenas lida/revisada) — `DT-011A.6 §28`.
